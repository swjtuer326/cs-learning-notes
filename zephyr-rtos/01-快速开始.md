## 1. 概述：从源码到运行

> 上一篇建立了 Zephyr 的分层心智模型。一个自然的问题是：拿到一份 Zephyr 源码，从 `git clone` 到板子上 LED 真正闪烁，中间到底发生了什么？本章用 Blinky 这个最小工程回答这个问题——先看 `main` 函数里的 `k_sleep` 循环在做什么，再顺着工具链反推每一阶段的责任。后续章节再分别展开工具链安装与命令操作。

### 1.1 一个 Zephyr 工程从源码到运行经历了什么

抛开环境安装细节，一个 Zephyr 工程从源码到板子上运行，经历四个阶段：

1. **拉取源码**：West 按 `west.yml` 把 Zephyr 主仓库和若干外部模块（如 HAL、crypto、蓝牙协议栈）以**统一版本**拉到同一工作区
2. **配置生成**：CMake 读取板卡定义、处理设备树（生成 `devicetree_generated.h`）、运行 Kconfig（把 `prj.conf` 与板级默认合并为 `.config` 与 `autoconf.h`）
3. **编译链接**：Ninja 按 CMake 生成的规则编译 `.c → .o`，链接为 `zephyr.elf`，再 objcopy 出 `zephyr.bin`/`zephyr.hex`
4. **烧录运行**：`west flash` 调用 OpenOCD 或厂商工具把镜像写入 Flash，CPU 复位后从入口执行；调试时用 `west debug` 启动 GDB server 在线调试

### 1.2 Blinky 小例子：main → k_sleep 循环

为了把上面的抽象流程落到具体代码，看 Zephyr 自带的 Blinky 示例。完整源码见 [`samples/basic/blinky/src/main.c`](file:///home/pbw/rtos/cs-learning-notes/zephyr-project/zephyr/samples/basic/blinky/src/main.c)，核心循环只有几行：

```c
#include <stdio.h>
#include <zephyr/kernel.h>
#include <zephyr/drivers/gpio.h>

#define SLEEP_TIME_MS   1000                                    // 每次翻转后睡眠 1000ms
#define LED0_NODE DT_ALIAS(led0)                                // 从设备树 led0 别名取节点 ID

static const struct gpio_dt_spec led = GPIO_DT_SPEC_GET(LED0_NODE, gpios);  // 编译时解析为 {port, pin, flags}

int main(void)
{
    int ret;
    bool led_state = true;

    if (!gpio_is_ready_dt(&led)) {                              // 检查 GPIO 设备是否已完成初始化
        return 0;
    }

    ret = gpio_pin_configure_dt(&led, GPIO_OUTPUT_ACTIVE);      // 配置为输出，初始电平为"有效"
    if (ret < 0) {
        return 0;
    }

    while (1) {
        ret = gpio_pin_toggle_dt(&led);                         // 翻转电平
        if (ret < 0) {
            return 0;
        }

        led_state = !led_state;
        printf("LED state: %s\n", led_state ? "ON" : "OFF");
        k_msleep(SLEEP_TIME_MS);                                // 让出 CPU 1 秒，内核可调度其他线程
    }
    return 0;
}
```

这个工程要"跑起来"，对应到上面的四阶段：

- **拉取源码**：West 把 `zephyr/` 主仓库与 HAL 模块拉到 `~/zephyrproject/`，Blinky 的 `main.c` 在 `zephyr/samples/basic/blinky/src/`
- **配置生成**：CMake 读取 `samples/basic/blinky/CMakeLists.txt` 与 `prj.conf`（仅一行 `CONFIG_GPIO=y`），合并板级默认配置，再处理设备树把 `led0` 别名解析为具体 GPIO 端口与引脚
- **编译链接**：Ninja 编译 `main.c` 与依赖的内核/驱动源文件，链接出 `zephyr.elf`
- **烧录运行**：`west flash` 把 `zephyr.bin` 写入 Flash，复位后 `main` 执行，进入 `while(1)` 循环：翻转 LED → 打印状态 → `k_msleep(1000)` 让出 CPU

> **核心要点**：`k_msleep` 是这个例子的灵魂——它不是"忙等 1 秒"，而是把当前线程挂起、让调度器切到其他线程（这里只有 idle 线程）执行，1 秒后再唤醒。这就是 RTOS 的本质：**用线程抽象并发，用调度器管理时序**。如果换成裸机的 `for (int i=0; i<1000000; i++);`，CPU 会被完全占用，无法响应任何中断之外的事件。

> **设计洞察**：`k_msleep(1000)` 与裸机的 `for (volatile int i=0; i<N; i++);` 表面都是"等 1 秒"，本质却不同：前者是**协作式让出**（cooperative yield），后者是**忙等霸占**（busy wait）。`k_msleep` 内部把当前线程状态改为"睡眠"，挂到超时队列上，调用 `z_swap` 切到调度器选出的下一个线程——CPU 真正"腾出来"了。
>
> 这是 RTOS 与裸机最深的分野：**裸机的"并发"靠状态机+中断拼凑，RTOS 的并发靠"阻塞调用+调度器切换"自然组合**。裸机里"等 1 秒后做 X"只能用 `if (time_after(now, t0+1000)) { do_x(); }`；RTOS 里直接 `k_msleep(1000); do_x();`，代码结构与"想什么"完全对应。这种"代码形态=思考形态"的特性是高级抽象的标志。
>
> 对比 Linux：Linux 的 `sleep(1)` 在内核态走类似路径——挂到定时器树上，调用 `schedule()` 让出 CPU。Zephyr 的 `k_msleep` 与之概念一致，只是规模更小（没有 Linux 的 hrtimer、nohz 等优化机制，不过 Zephyr 也支持 `CONFIG_TICKLESS_KERNEL` 减少定时器 tick 开销）。**"阻塞调用让出 CPU"是所有多任务 OS 的基石**，理解这一点比记住任何 API 都重要。

对应的工程文件非常简洁。构建脚本只有 4 行（[`samples/basic/blinky/CMakeLists.txt`](file:///home/pbw/rtos/cs-learning-notes/zephyr-project/zephyr/samples/basic/blinky/CMakeLists.txt)）：

```cmake
cmake_minimum_required(VERSION 3.20.0)
find_package(Zephyr REQUIRED HINTS $ENV{ZEPHYR_BASE})    # 加载 Zephyr CMake 包，触发板卡/DTS/Kconfig 全套流程
project(blinky)

target_sources(app PRIVATE src/main.c)                   # 把 main.c 加到 app 目标
```

项目配置 [`samples/basic/blinky/prj.conf`](file:///home/pbw/rtos/cs-learning-notes/zephyr-project/zephyr/samples/basic/blinky/prj.conf) 只有一行：

```kconfig
CONFIG_GPIO=y
```

意思是"启用 GPIO 子系统"。其他诸如控制台、串口驱动等由板级默认配置自动启用。

## 2. 工具链选型：为什么是 West + CMake + Kconfig

> 上一章看到 Blinky 从源码到运行经过四个阶段，但还没解释为什么需要三个独立工具来协同。本章回答三个"为什么"——为什么用 West 而非 git submodule、为什么用 CMake 而非 Make、为什么用 Kconfig 而非 `#define`。理解这三个设计选择，才能在后续遇到构建异常时知道去哪里查。

### 2.1 为什么用 West 而非 git submodule

Zephyr 主仓库本身只有内核代码，但要构建一个完整固件还需要外部模块：HAL（如 NORDIC、ST 的厂商代码）、加密库（mbedTLS、psa-crypto）、蓝牙控制器、文件系统等。这些模块分散在各自仓库，版本必须与 Zephyr 主仓库匹配——Zephyr v3.6.0 的内核不能配 v3.4.0 的 HAL。

**git submodule 的痛点**：

- 子模块的版本信息散落在 `.gitmodules` 与各子目录的 commit 指针里，跨仓库的"原子化版本锁定"需要手动逐个 `git submodule update`，容易漂移
- 子模块路径固定在仓库内，无法把同一份 HAL 同时挂到多个不同工程的工作区
- 切换分支后子模块状态容易脏，需要 `git submodule sync` 才能恢复

**West 的 manifest 模型**：把所有外部仓库的 URL、revision、本地路径集中写在一个 YAML 文件（`zephyr/west.yml`）里。`west update` 一次性按 manifest 把所有项目拉到工作区的指定位置，所有仓库版本被同一个 manifest 锁定。

| 维度 | git submodule | West manifest |
|------|---------------|---------------|
| **版本锁定方式** | 各子目录 commit 指针 | 单个 `west.yml` 集中声明 |
| **多仓库同步** | 手动逐个 update | `west update` 一次完成 |
| **路径灵活性** | 固定在仓库内 | 可映射到工作区任意子目录 |
| **跨工程复用** | 需要每个仓库各自维护 | 一份 manifest 可服务多个工作区 |
| **额外能力** | 仅版本管理 | 还提供 build/flash/debug 命令入口 |

> **核心要点**：West 解决的不是"如何拉代码"，而是"如何让几十个外部仓库在版本上保持一致"。`west.yml` 是版本协同的**单一事实来源**，`west update` 是把这个事实落地到磁盘的原子操作。详见 [02-构建系统](./02-构建系统.md)。

> **设计洞察**：West manifest 模型本质上是把"软件供应链管理"作为一等公民。Linux 发行版用 `apt`/`yum` 锁定包版本，Node.js 用 `package-lock.json`，Python 用 `poetry.lock`，Rust 用 `Cargo.lock`——所有现代软件栈都在向"清单锁定版本"演进。West 的 `west.yml` 是这个模式在嵌入式领域的实现，关键价值是**可复现性**（reproducibility）：同一份 manifest 在任何机器上 `west update` 都得到完全一致的代码版本。
>
> 可复现性不只是工程整洁，更是**安全底线**。依赖版本漂移意味着今天的构建可能与昨天有微妙差异——某个 HAL 模块升级后引入了未审计的代码，可能成为供应链攻击入口。Zephyr 通过 `west.yml` + manifest revision 锁定，让供应链审计有明确的"快照点"，这与 Zephyr 的 MCUboot + secure boot 链路是同一思路的延伸——**从源码到镜像全链路可追溯**。
>
> 与 git submodule 的根本差异不在功能，而在**默认假设**：submodule 假设"子模块是主仓库的延伸"，路径固定在仓库内；West 假设"模块是独立项目，临时拼装到工作区"，路径与版本解耦。后者更适合"一个 HAL 服务多个 Zephyr 版本"的真实场景——Nordic 的 HAL 代码同时被 Zephyr v3.5、v3.6、v3.7 引用，submodule 模型做不到这种多版本并存。

### 2.2 为什么用 CMake 而非 Make

裸 Makefile 在跨平台、跨工具链场景下写作成本高：Windows 上没有原生 make，路径分隔符差异、shell 命令差异、增量依赖检查都要手写。CMake 把这些抽象为平台无关的描述文件（`CMakeLists.txt`），由 CMake 根据目标平台生成对应的底层构建文件（Unix Makefiles、Ninja、MSBuild 等）。

Zephyr 选择 CMake + Ninja 的组合原因：

- **跨平台**：同一份 `CMakeLists.txt` 在 Ubuntu/macOS/Windows 上都能生成可用的构建脚本
- **多构建后端**：默认用 Ninja（启动快、增量编译快），需要时也可切到 Make 或 IDE 项目文件
- **依赖发现**：`find_package(Zephyr REQUIRED)` 一行触发板卡定义、设备树、Kconfig、工具链的全套定位
- **变量与函数抽象**：可以把"添加一个驱动"封装为 `target_sources` / `zephyr_library` 等高层 API

### 2.3 为什么用 Kconfig 而非 #define

直接用 `#define` 控制功能裁剪，看似简单，但会立刻遇到三个问题：

1. **依赖关系无法表达**：`CONFIG_LOG=y` 需要先把 `CONFIG_PRINTK=y` 打开。`#define` 不表达"依赖"，开发者要手动按正确顺序写
2. **默认值与覆盖优先级**：板级默认、SoC 默认、用户 `prj.conf` 三层配置如何合并？`#define` 没有"优先级"概念
3. **选择空间**：某选项有 `y/n/m` 三态，或在某个数值范围内取值——`#define` 是裸文本替换，没有"取值约束"

Kconfig 用专门语法定义选项、依赖、默认值与约束，构建时按优先级合并多层配置，最终生成 `autoconf.h`（供 C 代码 `#ifdef`）与 `.config`（供人查看与 CMake 读取）。

```kconfig
config THREAD_NAME
    bool "Thread name support"
    default n
    help
      Enable thread name tracking.

config THREAD_MAX_NAME_LEN
    int "Maximum length of a thread name"
    default 32
    depends on THREAD_NAME         # 表达依赖：只有 THREAD_NAME 打开才可见
    range 1 256                    # 表达约束：取值范围
```

> **核心要点**：West 管"多仓库版本协同"，CMake 管"构建编排跨平台"，Kconfig 管"功能裁剪依赖解析"。三者解耦的关键是中间产物：`west.yml` → 工作区、`.config` → CMake 读取、`autoconf.h` → C 代码包含。详见 [02-构建系统](./02-构建系统.md)。

> **设计洞察**：Kconfig 的本质是**编译时策略分发**——把"用什么调度算法""开不开蓝牙""栈大小多少"这些决策在编译期固化到二进制中。这与桌面 Linux 的"模块可加载、运行时配置"哲学相反：Linux 内核的 `insmod` 可在系统运行时动态加载驱动，`sysctl` 可运行时调整参数；Zephyr 的 `CONFIG_XXX=y` 一旦编译完成就不可更改。
>
> 这个差异源于资源约束：Cortex-M 设备没有 MMU，加载 ELF 模块需要解析重定位表，开销远超嵌入式可接受范围。Zephyr 选择**编译时裁剪 + 链接时死代码消除**（`--gc-sections` 链接选项），未选中的 Kconfig 选项对应的代码根本不进 `.o` 文件，最终镜像只包含实际用到的功能。Blinky 工程 45KB Flash 占用就是这样"挤"出来的——如果像 Linux 那样保留所有功能，光蓝牙协议栈就要几百 KB。
>
> Kconfig 还体现了**策略与机制分离**的经典 OS 设计原则。机制（mechanism）是"如何做"——调度器能切换线程、串口能收发字节；策略（policy）是"做什么"——优先级数值、波特率数值。Kconfig 让策略声明在 `prj.conf` 中显式化，机制实现在内核代码中通用化。这与 Linux 的 `sysctl`（运行时策略）vs 内核代码（机制）的分层同构，只是 Zephyr 把策略评估时机放在编译期，让"裁剪"变成数据驱动而非代码删改。

## 3. 安装主机依赖

> 上一章解释了为什么需要三个工具。本章从零开始把三平台主机依赖装好——这些是构建任何 Zephyr 工程的前置条件。完成后你的机器应当能跑 `cmake --version`、`python3 --version`、`dtc --version` 且都满足最低版本要求。

### 3.1 最低版本要求

按 [官方 Getting Started](../zephyr-project/zephyr/doc/develop/getting_started/index.rst) 的当前要求：

| 工具 | 最低版本 | 说明 |
|------|---------|------|
| **CMake** | 3.20.5 | 构建系统编排 |
| **Python** | 3.12 | West 与构建脚本运行时 |
| **Devicetree compiler (dtc)** | 1.4.6 | 设备树编译 |
| **Git** | 2.x | 版本控制与 West 拉取 |
| **Ninja** | 任意发行版默认 | 默认构建后端 |

> **如何读这张表**：这是 Zephyr 上游主线的最低要求。Linux 发行版自带的版本可能更低（如 Ubuntu 22.04 的 Python 是 3.10），此时需要通过 PPA 或官方源升级。Ubuntu 24.04 LTS 自带的 Python 3.12、CMake 3.28 已满足要求。

### 3.2 Ubuntu

官方指南覆盖 Ubuntu 24.04 LTS 及以上。先更新系统：

```bash
sudo apt update
sudo apt upgrade
```

一次性安装全部依赖：

```bash
sudo apt install --no-install-recommends git cmake ninja-build gperf \
  ccache dfu-util device-tree-compiler wget python3-dev python3-venv python3-tk \
  xz-utils file make gcc gcc-multilib g++-multilib libsdl2-dev libmagic1
```

> **注意**：在 AArch64（ARM64）主机上 `gcc-multilib` 与 `g++-multilib` 不可用，需要从上面的命令中删掉。

验证版本：

```bash
cmake --version
python3 --version
dtc --version
```

如需在 QEMU 上无硬件运行（推荐学习路径），额外装 RISC-V 与 ARM 版 QEMU：

```bash
sudo apt install qemu-system-riscv64 qemu-system-arm
```

### 3.3 macOS

先装 [Homebrew](https://brew.sh/)：

```bash
/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"
```

按提示把 Homebrew 加到 PATH：

```bash
(echo; echo 'eval "$(/opt/homebrew/bin/brew shellenv)"') >> ~/.zprofile
source ~/.zprofile
```

安装依赖（含 QEMU 与 OpenOCD，便于无硬件调试）：

```bash
brew install cmake ninja gperf python3 python-tk ccache qemu dtc libmagic wget openocd
```

把 Homebrew 的 Python 加到 PATH，使 `python` 与 `pip` 命令可用：

```bash
(echo; echo 'export PATH="'$(brew --prefix)'/opt/python/libexec/bin:$PATH"') >> ~/.zprofile
source ~/.zprofile
```

> **注意**：x86-64 macOS 不被官方支持。Apple Silicon（M1/M2/M3/M4）原生支持，无需 Rosetta。

### 3.4 Windows

> **注意**：Zephyr 不推荐使用 WSL（Windows Subsystem for Linux），因为 WSL 在访问 USB 设备（烧录/调试）上有问题。直接在 Windows 原生命令行环境下安装。

推荐用 Windows 10/11 自带的 [winget](https://learn.microsoft.com/en-us/windows/package-manager/) 包管理器。打开 `cmd.exe` 或 PowerShell：

```bat
winget install Kitware.CMake Ninja-build.Ninja oss-winget.gperf Python.Python.3.12 Git.Git oss-winget.dtc wget 7zip.7zip
```

安装完成后**关闭并重新打开终端**，让 PATH 生效。如需 7zip 解压 SDK，可能要手动把 7zip 安装目录加到 PATH。

> **核心要点**：三平台依赖的差异主要在包管理器（apt / brew / winget），但工具链版本要求一致。装完先用 `cmake --version` 等命令确认版本，再继续后续步骤——这一步出错最常见，提前发现能省下后面排查时间。

## 4. Python 虚拟环境与 West 安装

> 主机依赖装好后，下一阶段是把 West 装进一个隔离的 Python 虚拟环境，再用它初始化 Zephyr 工作区。本章回答两个实践问题：为什么要用虚拟环境？`west init` 与 `west update` 各做了什么？

### 4.1 Python 虚拟环境最佳实践

直接用 `pip install west` 装到系统 Python 会污染系统包，在某些发行版上还会触发 PEP 668 "externally-managed-environment" 错误。Zephyr 官方推荐为每个 Zephyr 工作区建一个独立的 Python 虚拟环境：

```bash
python3 -m venv ~/zephyrproject/.venv
```

激活虚拟环境：

```bash
# Ubuntu / macOS
source ~/zephyrproject/.venv/bin/activate
```

```bat
:: Windows cmd.exe
cd %HOMEPATH%
zephyrproject\.venv\Scripts\activate.bat
```

```powershell
# Windows PowerShell（首次需放开脚本执行权限）
Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser
zephyrproject\.venv\Scripts\Activate.ps1
```

激活后 shell 提示符会带上 `(.venv)` 前缀。**之后每次开始 Zephyr 工作前都要先激活这个虚拟环境**，否则 `west`、`pip` 命令会落到系统 Python 而非隔离环境。

退出虚拟环境用 `deactivate`。

> **核心要点**：虚拟环境隔离的不只是 west，还包括 Zephyr 构建脚本依赖的几十个 Python 包（pyelftools、yaml、clang-format 等）。把 `.venv` 放在 `~/zephyrproject/` 下意味着工作区与虚拟环境绑定——多个工作区可以并存且互不干扰。

### 4.2 安装 West

虚拟环境激活后，安装 West（参见 [West 安装文档](../zephyr-project/zephyr/doc/develop/west/install.rst)）：

```bash
pip install west
```

验证：

```bash
west --version
```

### 4.3 工作区初始化

`west init` 创建工作区并克隆 manifest 仓库（即 Zephyr 主仓库），`west update` 按 manifest 拉取所有外部模块。这两个命令的分工见 [West 基础](../zephyr-project/zephyr/doc/develop/west/basics.rst)。

```bash
# 创建工作区（默认拉最新主线）
west init ~/zephyrproject
cd ~/zephyrproject
west update
```

如需指定版本（推荐，确保可复现）：

```bash
west init ~/zephyrproject --mr v3.7.0
cd ~/zephyrproject
west update
```

`west init` 做了四件事：

1. 创建 topdir（`~/zephyrproject/`）与 `.west/` 标记目录
2. 从 `https://github.com/zephyrproject-rtos/zephyr` 克隆 manifest 仓库到 `~/zephyrproject/zephyr/`
3. 检出 `--mr` 指定的 tag 或分支
4. 在 `.west/config` 写入 `manifest.path=zephyr`、`manifest.file=west.yml`

`west update` 读取 `zephyr/west.yml`，按其中声明的 URL、revision、path 把所有项目拉到工作区指定位置（`modules/`、`tools/` 等）。首次执行会下载几个 GB，耐心等待。

接下来导出 Zephyr CMake 包，让 CMake 能通过 `find_package(Zephyr)` 加载：

```bash
west zephyr-export
```

最后安装 Zephyr 构建脚本依赖的 Python 包（注意：这一步会改写虚拟环境中的包版本）：

```bash
west packages pip --install
```

工作区最终结构（参见 [West basics](../zephyr-project/zephyr/doc/develop/west/basics.rst)）：

```
zephyrproject/              # topdir
├── .west/                  # 标记 topdir 位置
│   └── config              # 工作区本地配置
├── zephyr/                 # manifest 仓库（含 west.yml）
├── modules/                # west 管理的外部模块
│   └── lib/
│       └── zcbor/
├── tools/
│   └── net-tools/
└── [其他项目...]
```

> **核心要点**：`west init` 只创建骨架并克隆 manifest 仓库，`west update` 才是真正下载大部分代码的步骤。切换 Zephyr 版本时（如从 v3.6 切到 v3.7），先在 `zephyr/` 里 `git checkout v3.7.0`，再跑 `west update` 让其他模块跟随升级——这是保持多仓库版本一致的标准流程。

## 5. 安装 Zephyr SDK

> 工作区建好了，但还缺交叉编译工具链。Zephyr SDK 把所有支持架构（ARM、RISC-V、x86、ARC、Xtensa）的工具链、QEMU、OpenOCD 打包在一起，是大多数开发者的首选。本章用 `west sdk install` 一键完成。

### 5.1 用 west sdk install

确保虚拟环境已激活，进入 zephyr 目录后执行（参见 [官方指南](../zephyr-project/zephyr/doc/develop/getting_started/index.rst) 的 "Install the Zephyr SDK" 章节）：

```bash
cd ~/zephyrproject/zephyr
west sdk install
```

`west sdk install` 会自动：

1. 下载最新版 Zephyr SDK 到默认位置（`~/zephyr-sdk-<version>/`，例如 `~/zephyr-sdk-1.0.1/`）
2. 解压并运行 setup 脚本
3. 把 Udev 规则安装到 Linux 系统（需 sudo）

如需指定安装路径或仅装某些架构的工具链：

```bash
west sdk install --help                # 查看所有选项
west sdk install -b /opt/zephyr-sdk    # 指定安装基目录（最终装到 /opt/zephyr-sdk/zephyr-sdk-<version>）
```

### 5.2 手动安装（可选）

若 `west sdk install` 在网络受限环境下失败，可手动下载安装。以 v0.16.x 为例：

```bash
mkdir ~/zephyr-sdk && cd ~/zephyr-sdk
wget https://github.com/zephyrproject-rtos/sdk-ng/releases/download/v0.16.10/zephyr-sdk-0.16.10_linux-x86_64.tar.xz
tar xvf zephyr-sdk-0.16.10_linux-x86_64.tar.xz
cd zephyr-sdk-0.16.10
./setup.sh
sudo cp ~/zephyr-sdk-<version>/hosttools/sysroots/x86_64-pokysdk-linux/usr/share/openocd/contrib/60-openocd.rules /etc/udev/rules.d
sudo udevadm control --reload
```

> **待确认**：上述 URL 中的具体版本号请以 [Zephyr SDK Releases](https://github.com/zephyrproject-rtos/sdk-ng/releases) 页面最新稳定版为准，本文写成时为 v0.16.x 系列。

### 5.3 验证工具链

Zephyr SDK 安装后无需手动设置环境变量——构建系统通过 `ZEPHYR_TOOLCHAIN_VARIANT=zephyr` 自动定位。若机器上装了多个 SDK 或工具链，可显式指定：

```bash
export ZEPHYR_TOOLCHAIN_VARIANT=zephyr
export ZEPHYR_SDK_INSTALL_DIR=~/zephyr-sdk-0.16.10
```

> **核心要点**：Zephyr SDK 把"工具链 + QEMU + OpenOCD"三件套打包，避免了分别装交叉编译器与调试器的麻烦。`west sdk install` 是当前推荐方式，比早期版本的手动下载+setup.sh 更可靠。

## 6. Blinky 示例：构建 + 烧录 + 调试三步走

> 工具链装齐，现在回到第 1 章的 Blinky 例子，把"构建 → 烧录 → 调试"三步走通。没有真实硬件的读者，可按 6.4 节用 QEMU 跑 Hello World 验证环境。完成后你应当具备在任意支持板卡上构建 Zephyr 应用的能力。

### 6.1 第一步：构建

构建 Blinky 示例（参见 [官方 Getting Started](../zephyr-project/zephyr/doc/develop/getting_started/index.rst) 的 "Build the Blinky Sample" 章节）：

```bash
cd ~/zephyrproject/zephyr
west build -p always -b <your-board-name> samples/basic/blinky
```

- `-p always`：强制 pristine 构建（清空 build 目录从头来）。对新用户最稳妥；熟悉后可用 `-p auto` 让 west 根据配置变化自动判断是否需要 pristine
- `-b <your-board-name>`：指定目标板卡。不知道板卡名时跑 `west boards` 列出所有支持的板卡
- `samples/basic/blinky`：要构建的源码目录

例如，构建 Nordic nRF52840 DK：

```bash
west build -p always -b nrf52840dk_nrf52840 samples/basic/blinky
```

构建成功后产物在 `build/zephyr/`：

```
build/
└── zephyr/
    ├── zephyr.elf              # 完整 ELF（含调试信息，GDB 用）
    ├── zephyr.bin              # 纯二进制镜像（烧录用）
    ├── zephyr.hex              # Intel HEX 格式
    ├── zephyr.map              # 链接器生成的内存映射
    └── include/generated/
        ├── autoconf.h                  # Kconfig 生成的 #define
        └── devicetree_generated.h      # 设备树生成的宏
```

构建过程中会先输出 CMake 配置阶段信息，再输出 Ninja 编译链接进度。一个典型成功结尾：

```
[1/1] Linking C executable zephyr/zephyr.elf
Memory region         Used Size  Region Size  %age Used
           FLASH:       45632 B        1 MB     4.35%
            RAM:        12288 B       256 KB     4.69%
        IDT_LIST:          0 B         2 KB     0.00%
```

> **如何读这段输出**：`FLASH` 与 `RAM` 的 Used Size 是镜像实际占用，Region Size 是该板卡的可用容量。`%age Used` 给出占用比例——Blinky 这种小工程通常在 5% 以下，复杂应用可能逼近上限。若 RAM 超限，链接器会报错，需通过 `prj.conf` 关闭不必要的子系统。

> **设计洞察**：构建输出的 `FLASH` 与 `RAM` 两行揭示了嵌入式系统与传统 OS 的根本差异——**内存不再是统一地址空间**，而是两类物理介质：Flash（非易失，断电保留，但写入慢、有寿命限制）和 RAM（易失，掉电丢失，但随机访问快）。Cortex-M 采用哈佛架构变种（指令与数据总线分离），代码常驻 Flash 执行，变量放 RAM；而 x86 桌面 Linux 一切在统一 DRAM 中。
>
> 这个差异决定了固件工程的两个核心约束：**Flash 容量决定能塞多少功能**，**RAM 容量决定能跑多少并发**。Blinky 的 45KB Flash / 12KB RAM 看似宽裕，但加一个 BLE 协议栈 Flash 涨到 200KB，加一个 LwIP 网络栈 RAM 涨到 40KB——这是为什么 Zephyr 的 Kconfig 选项粒度如此细：每多一个 `CONFIG_XXX=y` 都是实打实的 Flash/RAM 占用。
>
> 链接脚本（linker script）控制这些区域如何映射：`.text` 段进 Flash（代码 + 常量），`.data` 段的初始值在 Flash 但运行时拷到 RAM（启动时由初始化代码复制），`.bss` 段清零放 RAM。理解这个布局是优化嵌入式 footprint 的前提——`const` 关键字不只是类型修饰，而是把数据从 RAM 搬到 Flash；`static const` 数组是嵌入式省 RAM 的第一手段。同样一个查找表，去掉 `const` 就吃 RAM，加上 `const` 就只占 Flash。

### 6.2 第二步：烧录

把板子用 USB 接上电脑（如有电源开关打开），跑：

```bash
west flash
```

`west flash` 会自动选择与板卡匹配的烧录工具（OpenOCD、pyOCD、nrfjprog、JLink 等），把 `zephyr.bin` 写入 Flash 并复位。

**OpenOCD**（Open On-Chip Debugger，开源片上调试器）是这些工具中最常见的一个，值得单独说明。它通过目标芯片的调试端口与硬件通信，对上暴露一个 GDB server 接口。Zephyr 工作流中它同时承担两个职责：把固件镜像写入目标 Flash（`west flash` 的底层实现），以及把目标 CPU 的调试寄存器暴露给 GDB（`west debug` 的底层实现）。SDK 默认打包 OpenOCD，多数 ARM/RISC-V 板卡开箱即用；JLink（SEGGER）、nrfjprog（Nordic）等是厂商提供的商业替代，原理类似但绑定自家芯片。

**Linux 首次使用调试探针**需要配置 udev 规则。udev 是 Linux 的设备管理器，设备插入时按规则文件创建 `/dev/` 节点并赋予权限——调试探针作为 USB 设备默认只有 root 能访问，规则文件让普通用户也有读写权限。Zephyr SDK 安装时已自动把规则文件复制到 `/etc/udev/rules.d/`，但若仍报权限错误，手动重载：

```bash
sudo udevadm control --reload
sudo udevadm trigger
```

**Windows / macOS** 通常无需此步骤，但需要安装调试探针厂商的驱动。

烧录成功后板子上 LED 应当开始按 1 秒周期闪烁，串口终端（如 `minicom -D /dev/ttyACM0 -b 115200`）会看到：

```
*** Booting Zephyr OS build v3.7.0 ***
LED state: ON
LED state: OFF
LED state: ON
LED state: OFF
```

### 6.3 第三步：调试

`west debug` 启动 GDB 连接到板子上的调试器（通常通过 OpenOCD 或 JLink GDB server）：

```bash
west debug
```

这会启动交叉 GDB（如 `arm-zephyr-eabi-gdb`），加载 `zephyr.elf`，连接到本地的 GDB server，停在 `main` 入口。常用 GDB 命令：

| 命令 | 说明 |
|------|------|
| `break main` | 在 `main` 设断点 |
| `break gpio_pin_toggle_dt` | 在 LED 翻转函数设断点 |
| `continue` | 继续执行到下一断点 |
| `next` | 单步（不进入函数） |
| `step` | 单步（进入函数） |
| `print led_state` | 打印变量 |
| `info threads` | 查看所有线程 |
| `thread 2` | 切换到线程 2 |
| `bt` | 查看调用栈 |
| `quit` | 退出 GDB |

若想用 IDE 或独立 GDB 客户端，先启动调试服务器：

```bash
west debugserver    # 终端 1：启动 GDB server，监听 localhost:3333
```

另一终端：

```bash
arm-zephyr-eabi-gdb build/zephyr/zephyr.elf    # 终端 2：架构名按实际板卡替换
(gdb) target remote localhost:3333
(gdb) break main
(gdb) continue
```

### 6.4 无硬件替代方案：QEMU

没有真实板卡也能跑通 Zephyr——用 QEMU 模拟。Blinky 依赖具体板卡的 LED 设备树节点，QEMU 板卡没有，所以换成 Hello World 示例：

```bash
cd ~/zephyrproject/zephyr
west build -p always -b qemu_cortex_m3 samples/hello_world
west build -t run
```

`-t run` 让 west 在编译后直接启动 QEMU 运行镜像。预期输出：

```
*** Booting Zephyr OS build v3.7.0 ***
Hello World! qemu_cortex_m3
```

按 `Ctrl-A X` 退出 QEMU。

QEMU 也支持调试。一个终端启 debugserver，另一个终端连 GDB：

```bash
# 终端 1
west build -t debugserver_qemu

# 终端 2
arm-zephyr-eabi-gdb build/zephyr/zephyr.elf
(gdb) target remote localhost:1234
(gdb) break main
(gdb) continue
```

注意 QEMU 默认 GDB 端口是 1234，与真实硬件 OpenOCD 的 3333 不同。

> **核心要点**：构建、烧录、调试三步分别对应 `west build`、`west flash`、`west debug`——这是 Zephyr 工作流的"标准三件套"。无硬件时用 QEMU 替代，命令几乎一致（`west build -t run` 一步完成编译+运行）。后续日常开发中，90% 的操作就是这三条命令的组合。

## 7. 常见问题排查

> 三步走通后，最后一章列几个新手最常踩的坑。每条给出根因与解决方案，避免重复排查。

### 7.1 找不到 Zephyr CMake 包

**症状**：构建时报 `Could not find a package configuration file provided by "Zephyr"`。

**根因**：未运行 `west zephyr-export`，或当前目录不在工作区内，或虚拟环境未激活导致 west 不可用。

**解决**：

```bash
source ~/zephyrproject/.venv/bin/activate    # 激活虚拟环境
cd ~/zephyrproject/zephyr                    # 进入工作区
west zephyr-export                            # 重新导出 CMake 包
```

### 7.2 Python 包版本不匹配

**症状**：构建时报 `ModuleNotFoundError: No module named 'elftools'` 或类似错误。

**根因**：未运行 `west packages pip --install`，或装到了系统 Python 而非虚拟环境。

**解决**：确保虚拟环境已激活（shell 提示符有 `(.venv)` 前缀），再跑：

```bash
west packages pip --install
```

### 7.3 SDK 未找到

**症状**：构建时报 `ZEPHYR_TOOLCHAIN_VARIANT or ZEPHYR_SDK_INSTALL_DIR not set` 或 `No toolchain found`。

**根因**：Zephyr SDK 未安装，或环境变量冲突。

**解决**：

```bash
# 检查是否装好
ls ~/zephyr-sdk-0.16.*/sysroots/        # 应能看到架构子目录

# 若装在非默认位置，显式指定
export ZEPHYR_TOOLCHAIN_VARIANT=zephyr
export ZEPHYR_SDK_INSTALL_DIR=/path/to/zephyr-sdk
```

### 7.4 Linux 上烧录权限不足

**症状**：`west flash` 报 `Permission denied: '/dev/ttyACM0'` 或 OpenOCD 无法打开 USB 设备。

**根因**：当前用户无 USB 设备访问权限，udev 规则未生效。

**解决**：

```bash
# 重载 udev 规则（Zephyr SDK 安装时已复制规则文件）
sudo udevadm control --reload
sudo udevadm trigger

# 拔插 USB 重新识别设备
```

### 7.5 Windows 上 WSL 烧录失败

**症状**：在 WSL 中能编译，但 `west flash` 找不到板子。

**根因**：WSL 默认不暴露 USB 设备，调试探针访问需要额外配置（usbipd-win）。

**解决**：官方不推荐 WSL 进行烧录调试。改用 Windows 原生 `cmd.exe` 或 PowerShell，按 §3.4 装 winget 依赖。

> **核心要点**：90% 的"环境问题"集中在三类——虚拟环境未激活、west zephyr-export 未跑、SDK 路径未设。养成"每次开新终端先激活虚拟环境"的习惯能省下大量排查时间。
