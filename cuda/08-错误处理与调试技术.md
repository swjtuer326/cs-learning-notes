## 1. 错误处理机制

> CUDA 的异步执行模型让错误处理变得复杂——错误可能延迟到下次同步才暴露。本节深入错误码体系、同步/异步错误、以及最佳实践。

### 1.1 错误码体系

**Runtime API 错误码**(参考 CUDA Runtime API §Error Handling):

```c
typedef enum cudaError {
    cudaSuccess = 0,
    cudaErrorInvalidValue = 1,
    cudaErrorMemoryAllocation = 2,
    cudaErrorInitializationError = 3,
    cudaErrorLaunchFailure = 4,
    cudaErrorLaunchOutOfResources = 6,        // 注意:不是 5
    cudaErrorInvalidSymbol = 13,
    cudaErrorECCUncorrectable = 39,
    cudaErrorInvalidKernelImage = 47,         // 旧别名,新代码用 cudaErrorInvalidPtx
    cudaErrorInvalidDevice = 101,             // 与 Driver API 对齐,不是 10
    cudaErrorStartupFailure = 0x7f,           // 127,启动失败
    cudaErrorUnknown = 999,                   // 未知错误
    // ... 共约 100 种错误码,完整列表见 cudaTypedefs.h
} cudaError_t;
```

> **如何读这张表**:Runtime 与 Driver API 的错误码数值并不一一对应——如 `cudaErrorMemoryAllocation = 2` 对应 `CUDA_ERROR_OUT_OF_MEMORY = 2`,数值一致;但 `cudaErrorInvalidDevice = 101` 才与 `CUDA_ERROR_INVALID_DEVICE = 101` 对齐,而 `cudaErrorInvalidKernelImage = 47` 与 Driver API 的 `CUDA_ERROR_INVALID_KERNEL_IMAGE = 200` 数值不同。跨层错误码转换由 Runtime 内部完成,用户代码不应假设数值相等。

**Driver API 错误码**(参考 CUDA Driver API §Error Handling):

```c
typedef enum CUresult {
    CUDA_SUCCESS = 0,
    CUDA_ERROR_INVALID_VALUE = 1,
    CUDA_ERROR_OUT_OF_MEMORY = 2,
    CUDA_ERROR_NOT_INITIALIZED = 3,
    CUDA_ERROR_DEINITIALIZED = 4,
    CUDA_ERROR_NO_DEVICE = 100,
    CUDA_ERROR_INVALID_DEVICE = 101,
    CUDA_ERROR_INVALID_KERNEL_IMAGE = 200,
    CUDA_ERROR_INVALID_PTX = 218,             // CUDA 10.1+ 引入,替代 INVALID_KERNEL_IMAGE
    // ... 完整列表见 cudaTypedefs.h / cudaResult.h
} CUresult;
```

### 1.2 同步错误 vs 异步错误

**同步错误**：API 调用立即返回错误，通常由参数错误引起。

```c
// 同步错误：立即返回
float *d_data;
cudaError_t err = cudaMalloc((void **)&d_data, (size_t)-1);  // 无效大小
// err = cudaErrorInvalidValue

if (err != cudaSuccess) {
    printf("Error: %s\n", cudaGetErrorString(err));
}
```

**异步错误**：错误延迟到下次同步才暴露，通常由 Kernel 执行错误引起。

```c
// 异步错误：Kernel 启动不报错
myKernel<<<blocks, threads>>>(d_data);

// 错误延迟到下次同步
cudaError_t err = cudaDeviceSynchronize();  // 此处才暴露错误
// err = cudaErrorLaunchFailure
```

**为什么异步错误难以捕获？** Kernel 启动是异步的，启动时只检查参数合法性，不等待执行完成。如果 Kernel 执行时发生错误（如非法内存访问），错误被记录在上下文中，直到下次同步才暴露。

### 1.3 错误捕获 API

**cudaGetLastError**：获取最后一次错误（不等待同步）

```c
myKernel<<<blocks, threads>>>(d_data);
cudaError_t err = cudaGetLastError();
if (err != cudaSuccess) {
    printf("Kernel launch error: %s\n", cudaGetErrorString(err));
}
```

**注意**：`cudaGetLastError` 只能捕获启动时的错误（如参数无效），不能捕获 Kernel 执行时的错误。

**cudaDeviceSynchronize**：等待所有任务完成，可以捕获 Kernel 执行错误

```c
myKernel<<<blocks, threads>>>(d_data);
cudaError_t err = cudaDeviceSynchronize();
if (err != cudaSuccess) {
    printf("Kernel execution error: %s\n", cudaGetErrorString(err));
}
```

### 1.4 错误检查宏

CUDA Samples 的 [helper_cuda.h](./src/cuda-samples/Common/helper_cuda.h) 提供了错误检查宏：

```c
/* 摘自 [src/cuda-samples/Common/helper_cuda.h](./src/cuda-samples/Common/helper_cuda.h) 中的 checkCudaErrors 宏（简化版） */
#define checkCudaErrors(val) check_cuda_errors((val), #val, __FILE__, __LINE__)

void check_cuda_errors(cudaError_t err, const char *func, const char *file, int line) {
    if (err != cudaSuccess) {
        fprintf(stderr, "CUDA error at %s:%d: %s (%d)\n",
                file, line, cudaGetErrorString(err), err);
        exit(EXIT_FAILURE);
    }
}
```

**使用示例**：

```c
// Runtime API
checkCudaErrors(cudaMalloc((void **)&d_data, size));
checkCudaErrors(cudaMemcpy(d_data, h_data, size, cudaMemcpyHostToDevice));
myKernel<<<blocks, threads>>>(d_data);
checkCudaErrors(cudaGetLastError());
checkCudaErrors(cudaDeviceSynchronize());
```

> **核心要点**：CUDA 错误分同步和异步两种。同步错误立即返回，异步错误延迟到下次同步。使用 `cudaGetLastError` 捕获启动错误，`cudaDeviceSynchronize` 捕获执行错误。建议使用宏封装错误检查，确保每个 CUDA 调用都检查返回值。

## 2. CUDA_LAUNCH_BLOCKING：强制同步调试

> 调试异步错误时，定位错误位置很困难——错误可能延迟到几行代码后才暴露。本节介绍 CUDA_LAUNCH_BLOCKING 环境变量，强制 Kernel 同步执行。

### 2.1 启用同步模式

**环境变量**：

```bash
# 启用同步模式（Kernel 立即执行，不排队）
export CUDA_LAUNCH_BLOCKING=1

# 运行程序
./my_program
```

**效果**：
- Kernel 启动后立即同步等待执行完成
- 异步错误变为同步错误，立即返回
- 错误位置精确到 Kernel 启动行

### 2.2 使用场景

**场景 1：定位非法内存访问**

```c
// 不启用 CUDA_LAUNCH_BLOCKING
myKernel1<<<...>>>(d_data);  // 这里访问越界
myKernel2<<<...>>>(d_data);  // 这里报错（延迟暴露）
cudaDeviceSynchronize();     // 错误在这里才暴露

// 启用 CUDA_LAUNCH_BLOCKING=1
myKernel1<<<...>>>(d_data);  // 这里立即报错，定位到这一行
```

**场景 2：调试死锁**

```c
// 协作组同步可能导致死锁
myKernel<<<blocks, threads>>>(d_data);  // 如果死锁，程序卡住
cudaDeviceSynchronize();  // 永远不返回
```

### 2.3 性能影响

**注意**：`CUDA_LAUNCH_BLOCKING=1` 会显著降低性能，仅用于调试，不要在生产环境使用。

**影响**：
- Kernel 串行执行，无法并发
- CPU 必须等待每个 Kernel 完成
- 适合定位错误，不适合性能分析

> **核心要点**：`CUDA_LAUNCH_BLOCKING=1` 强制 Kernel 同步执行，让异步错误立即暴露，便于定位。仅用于调试，不要在生产环境使用。

## 3. cuda-gdb：源码级调试器

> cuda-gdb 是 CUDA 的源码级调试器，支持在 GPU 代码中设置断点、单步执行、查看变量。本节介绍 cuda-gdb 的基本用法。

### 3.1 编译时生成调试信息

**nvcc 选项**：

```bash
# 生成调试信息
nvcc -g -G my_kernel.cu -o my_kernel
```

**选项说明**：
- `-g`：生成主机代码调试信息
- `-G`：生成设备代码调试信息（必须，否则 cuda-gdb 无法调试 GPU 代码）

### 3.2 基本用法

**启动 cuda-gdb**：

```bash
cuda-gdb ./my_kernel
```

**基本命令**：

```
(cuda-gdb) break my_kernel.cu:47      # 在 GPU 代码第 47 行设置断点
(cuda-gdb) break myKernel             # 在 Kernel 函数设置断点
(cuda-gdb) run                        # 运行程序
(cuda-gdb) continue                   # 继续执行
(cuda-gdb) next                        # 单步执行（不进入函数）
(cuda-gdb) step                        # 单步执行（进入函数）
(cuda-gdb) print threadIdx.x          # 查看线程索引
(cuda-gdb) print blockIdx.x           # 查看 Block 索引
(cuda-gdb) print data[tid]            # 查看变量
(cuda-gdb) info threads               # 查看所有线程
(cuda-gdb) thread 1                   # 切换到线程 1
(cuda-gdb) backtrace                  # 查看调用栈
(cuda-gdb) quit                        # 退出
```

### 3.3 聚焦特定线程

**问题**：GPU 有数千个线程，全部停止会导致 cuda-gdb 卡死。

**解决方案**：只聚焦特定线程。

```
# 只在特定线程的断点停止
(cuda-gdb) break my_kernel.cu:47 if blockIdx.x == 0 && threadIdx.x == 0

# 切换到特定 Warp
(cuda-gdb) cuda device 0 sm 0 warp 0 lane 0

# 查看当前线程的硬件位置
(cuda-gdb) cuda thread
# 输出: device 0 sm 0 warp 0 lane 0
```

### 3.4 调试技巧

**技巧 1：检查 Warp 发散**

```
# 查看当前 Warp 内的线程状态
(cuda-gdb) info cuda warps
# 输出 Warp 内活跃/停顿的线程

# 查看分支预测寄存器
(cuda-gdb) print $p0
```

**技巧 2：检查共享内存**

```
# 查看共享内存
(cuda-gdb) print sharedData[0]
(cuda-gdb) print sharedData[1]
```

**技巧 3：条件断点**

```
# 只在特定条件停止
(cuda-gdb) break my_kernel.cu:47 if tid == 100 && data[tid] == 0
```

> **核心要点**：cuda-gdb 是 CUDA 的源码级调试器，支持在 GPU 代码中设置断点、查看变量、单步执行。调试时聚焦特定线程，避免数千线程同时停止导致卡死。

## 4. compute-sanitizer：内存错误检测

> compute-sanitizer 是 CUDA 的内存错误检测工具，类似 Valgrind，可以检测内存越界、未初始化、竞态条件。本节介绍其使用方法。

### 4.1 工具模式

compute-sanitizer 有四种工具模式：

| 模式 | 说明 | 检测内容 |
|------|------|----------|
| `memcheck` | 内存检查 | 越界访问、未初始化、内存泄漏 |
| `racecheck` | 竞态检查 | 共享内存数据竞争 |
| `initcheck` | 初始化检查 | 未初始化内存使用 |
| `synccheck` | 同步检查 | 同步错误、死锁 |

### 4.2 memcheck：内存错误检测

**基本用法**：

```bash
# 检测内存错误
compute-sanitizer --tool memcheck ./my_program
```

**输出示例**：

```
========= COMPUTE-SANITIZER
========= Invalid __global__ read of size 4 bytes
=========     at 0x00000080 in myKernel(int*, int)
=========     by thread (0,0,0) in block (0,0,0)
=========     Address 0x7f4321000100 is out of bounds
=========     Saved host backtrace up to driver entry point
=========     Program hit cudaErrorLaunchFailure (error 719) due to out-of-bounds memory access on the GPU
```

**解读**：
- 第 2 行：错误类型（越界读）
- 第 3 行：出错位置（myKernel 函数）
- 第 4 行：出错线程（block (0,0,0), thread (0,0,0)）
- 第 5 行：越界地址

### 4.3 racecheck：竞态条件检测

**基本用法**：

```bash
# 检测竞态条件
compute-sanitizer --tool racecheck ./my_program
```

**输出示例**：

```
========= COMPUTE-SANITIZER
========= Race reported between Write and Read
=========     Write at 0x00000040 in myKernel(int*, int)
=========     Read at 0x00000080 in myKernel(int*, int)
=========     Shared memory address: 0x00001000
```

**典型竞态场景**：

```c
// 错误：缺少 __syncthreads()
__global__ void raceKernel(float *data) {
    __shared__ float sharedData[256];
    int tid = threadIdx.x;
    
    sharedData[tid] = data[tid];
    // 这里需要 __syncthreads();
    
    data[tid] = sharedData[255 - tid];  // 可能读到未写入的数据
}
```

### 4.4 高级选项

**检测内存泄漏**(参考 Compute Sanitizer Documentation §Command-Line Options):

```bash
# 启用泄漏检测(memcheck 模式专用)
compute-sanitizer --tool memcheck --leak-check yes ./my_program
```

**生成报告**：

```bash
# 生成 XML 报告
compute-sanitizer --tool memcheck --log-file report.xml ./my_program
```

**只检测第一个错误**：

```bash
# 检测到第一个错误就退出
compute-sanitizer --tool memcheck --exit-on-error 1 ./my_program
```

> **核心要点**：compute-sanitizer 是 CUDA 的内存错误检测工具，类似 Valgrind。memcheck 检测越界访问，racecheck 检测竞态条件，initcheck 检测未初始化内存，synccheck 检测同步错误。建议在开发阶段经常运行，捕获隐藏的内存问题。

## 5. Nsight Compute：Kernel 级性能分析

> Nsight Compute 是 CUDA 的 Kernel 级性能分析工具，提供详细的性能指标和优化建议。本节介绍其使用方法和关键指标。

### 5.1 基本用法

**命令行模式**：

```bash
# 分析特定 Kernel
ncu --set full ./my_program

# 只分析特定 Kernel
ncu --kernel myKernel ./my_program

# 只分析前 10 次调用
ncu --launch-count 10 ./my_program
```

**GUI 模式**：

```bash
# 启动 GUI
ncu-ui
```

### 5.2 关键性能指标

**Occupancy（占用率）**：

```
Theoretical Occupancy: 75%
Achieved Occupancy: 70%
```

- **Theoretical Occupancy**：理论占用率，基于资源使用计算
- **Achieved Occupancy**：实际占用率，基于运行时统计

**计算资源使用**：

```
Registers per Thread: 32
Shared Memory per Block: 2048 bytes
Max Threads per SM: 2048
Max Blocks per SM: 32
```

**内存带宽**：

```
Memory Throughput: 1200 GB/s
Theoretical Peak: 1555 GB/s
Bandwidth Utilization: 77%
```

**计算吞吐量**：

```
Compute Throughput: 15 TFLOPS
Theoretical Peak: 19.5 TFLOPS
Compute Utilization: 77%
```

### 5.3 性能瓶颈分析

**Stall Reasons（停顿原因）**：

| 停顿原因 | 说明 | 优化方向 |
|----------|------|----------|
| `stall_long_scoreboard` | 等待内存访问 | 优化内存访问模式 |
| `stall_short_scoreboard` | 等待共享内存 | 优化 Bank 冲突 |
| `stall_wait` | 等待同步 | 减少同步 |
| `stall_imc_miss` | 指令缓存未命中 | 减小 Kernel 体积 |
| `stall_no_instruction` | 无指令可执行 | 增加 ILP（指令级并行） |

### 5.4 Roofline 模型

**概念**：Roofline 模型把性能表示为算术强度（FLOPS/Byte）的函数，帮助判断是计算受限还是内存受限。

```
性能（FLOPS）= min(峰值算力, 带宽 × 算术强度)
```

**示例分析**：

```
Kernel: matrixMul
算术强度: 256 FLOPS/Byte
峰值算力: 19.5 TFLOPS
带宽: 1555 GB/s

理论性能 = min(19.5, 1555 × 256 / 1000) = min(19.5, 398) = 19.5 TFLOPS
→ 计算受限
```

```
Kernel: vectorAdd
算术强度: 0.25 FLOPS/Byte
峰值算力: 19.5 TFLOPS
带宽: 1555 GB/s

理论性能 = min(19.5, 1555 × 0.25 / 1000) = min(19.5, 0.39) = 0.39 TFLOPS
→ 内存受限
```

> **核心要点**：Nsight Compute 是 Kernel 级性能分析工具，提供 Occupancy、带宽利用率、计算吞吐量等指标。通过 Stall Reasons 分析瓶颈原因，通过 Roofline 模型判断是计算受限还是内存受限。

## 6. Nsight Systems：系统级性能分析

> Nsight Systems 是 CUDA 的系统级性能分析工具，提供整个程序的时间线视图，帮助发现 GPU 空闲、传输瓶颈等问题。

### 6.1 基本用法

**命令行采集**：

```bash
# 采集 trace
nsys profile -o my_report ./my_program
```

**GUI 查看**：

```bash
# 启动 GUI
nsys-ui my_report.nsys-rep
```

### 6.2 时间线分析

**典型时间线**：

```
CPU:    [Init] [H2D] [Kernel1] [H2D] [Kernel2] [D2H] [Verify]
GPU:           [H2D] [Kernel1] [H2D] [Kernel2] [D2H]
```

**关键观察**：
1. **GPU 空闲**：CPU 在准备数据，GPU 等待
2. **传输瓶颈**：H2D/D2H 占用大量时间
3. **Kernel 串行**：多个 Kernel 串行执行，没有并发

### 6.3 优化方向

**问题 1：GPU 空闲**

```
CPU:    [Prepare Data 100ms] [Kernel 10ms] [Prepare Data 100ms] [Kernel 10ms]
GPU:                          [Kernel 10ms]                    [Kernel 10ms]
```

**优化**：使用异步传输 + 多流，重叠 CPU 计算和 GPU 执行

```c
cudaMemcpyAsync(d_data, h_data, size, cudaMemcpyHostToDevice, stream1);
kernel<<<blocks, threads, 0, stream1>>>(d_data);
prepareNextData(h_data);  // CPU 与 GPU 并发
```

**问题 2：传输瓶颈**

```
CPU:    [H2D 50ms] [Kernel 10ms] [D2H 50ms]
GPU:    [H2D 50ms] [Kernel 10ms] [D2H 50ms]
```

**优化**：使用固定内存、减小传输数据量

**问题 3：Kernel 串行**

```
GPU: [Kernel1 10ms] [Kernel2 10ms] [Kernel3 10ms]
```

**优化**：使用不同 Stream，让 Kernel 并发执行

```c
kernel1<<<blocks, threads, 0, stream1>>>(args1);
kernel2<<<blocks, threads, 0, stream2>>>(args2);
kernel3<<<blocks, threads, 0, stream3>>>(args3);
```

> **核心要点**：Nsight Systems 提供整个程序的时间线视图，帮助发现 GPU 空闲、传输瓶颈、Kernel 串行等问题。通过多流、异步传输、固定内存等优化，可以最大化 GPU 利用率。

## 7. 常见问题诊断

> 本节总结 CUDA 开发中常见的问题和诊断方法。

### 7.1 内存访问错误

**症状**：Kernel 启动失败，`cudaErrorLaunchFailure`

**原因**：
1. 全局内存越界访问
2. 共享内存越界访问
3. 空指针解引用
4. 对齐错误

**诊断方法**：

```bash
# 用 compute-sanitizer 检测
compute-sanitizer --tool memcheck ./my_program
```

**常见修复**：

```c
// 错误：越界访问
__global__ void kernel(float *data, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    data[i] = data[i] * 2.0f;  // 如果 i >= n，越界
}

// 正确：边界检查
__global__ void kernel(float *data, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) {  // 边界检查
        data[i] = data[i] * 2.0f;
    }
}
```

### 7.2 同步问题

**症状**：结果不确定，每次运行结果不同

**原因**：
1. 缺少 `__syncthreads()`
2. 共享内存数据竞争
3. 全局内存数据竞争

**诊断方法**：

```bash
# 用 compute-sanitizer racecheck 检测
compute-sanitizer --tool racecheck ./my_program
```

**常见修复**：

```c
// 错误：缺少同步
__global__ void kernel(float *data) {
    __shared__ float shared[256];
    int tid = threadIdx.x;
    
    shared[tid] = data[tid];
    // 需要 __syncthreads();
    data[tid] = shared[255 - tid];  // 读到未写入的数据
}

// 正确：添加同步
__global__ void kernel(float *data) {
    __shared__ float shared[256];
    int tid = threadIdx.x;
    
    shared[tid] = data[tid];
    __syncthreads();  // 等待所有线程完成写入
    data[tid] = shared[255 - tid];
}
```

### 7.3 性能瓶颈

**症状**：Kernel 执行时间过长，未达到预期性能

**原因**：
1. 低 Occupancy
2. 内存访问未合并
3. 分支发散
4. Bank 冲突

**诊断方法**：

```bash
# 用 Nsight Compute 分析
ncu --set full ./my_program
```

**常见优化**：

```c
// 优化 1：增加 Occupancy
__global__ void __launch_bounds__(256, 4) kernel(float *data) {
    // 限制寄存器使用，确保 Occupancy >= 75%
}

// 优化 2：合并访问
__global__ void kernel(float *data) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    float x = data[i];  // 相邻线程访问相邻地址，合并访问
}

// 优化 3：减少分支发散
__global__ void kernel(float *data) {
    int tid = threadIdx.x;
    // 避免 if (tid % 2 == 0) { ... } else { ... }
    // 改用算术运算
}

// 优化 4：避免 Bank 冲突
__shared__ float shared[256 + 1];  // Padding 避免 Bank 冲突
```

### 7.4 调试流程总结

**通用调试流程**：

```
1. 启用 CUDA_LAUNCH_BLOCKING=1，定位错误位置
2. 用 compute-sanitizer memcheck 检测内存错误
3. 用 compute-sanitizer racecheck 检测竞态条件
4. 用 cuda-gdb 单步调试，查看变量
5. 用 Nsight Systems 查看时间线，发现性能瓶颈
6. 用 Nsight Compute 分析特定 Kernel，优化性能
```

> **核心要点**：CUDA 调试需要组合使用多个工具——`CUDA_LAUNCH_BLOCKING` 定位错误位置，`compute-sanitizer` 检测内存和竞态问题，`cuda-gdb` 单步调试，`Nsight Systems/Compute` 分析性能。掌握这套工具链是系统软件工程师的关键能力。
