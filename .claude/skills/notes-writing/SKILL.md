# 学习笔记写作规范

本仓库的笔记是给人(也给自己)读懂用的,不是操作手册。一篇好笔记把一个东西讲明白:**它解决什么问题、为什么这么设计、换来了什么代价、和别的做法比怎么样**。init 序列、bring-up、配置步骤是为讲明白服务的,不是主角——读完读者是理解了这个东西,而不是记住了"怎么操作"。

每条规则只为两件事服务:**读得下去**(不刻板、不突兀)、**读完有收获**(理解为什么、以及代价)。语气是"读者会困惑于什么",不是"必须/禁止";遵守某条的字面形式若让本节变刻板,就换更自然的方式达到该条目标。

## 0. 写作流程

1. **定类型**:Profile A(工程/系统/源码类)还是 B(科普/综述类)?见 §1,混用以主导面定。
2. **备事实**(A 类新专题):先把一手规范(spec/manual/datasheet,如 JEDEC 标准、厂商 datasheet)下载到专题 `reference/` 子目录。`reference/` 不编号、不进 HTML,是本地查证材料;正文以此为事实来源,防止写虚写错。
3. **写**:行文按 §2,内容按 §3,事实底线按 §4,排版细节查 `references/conventions.md`。
4. **自检**:按 §5 对应 profile 的清单过一遍。
5. **构建校验**:`python3 build_html.py <专题目录> --check` 零 error 后再构建,见 §6。

## 1. 两个 Profile,写前先定

| | **A:工程/系统/源码类** | **B:科普/综述类** |
| --- | --- | --- |
| 对象 | 固件、驱动、芯片、协议、源码走读 | 概念入门、领域脉络 |
| 底子 | 具体系统:点出它在系统里的位置 | 概念:多用小例子和类比 |
| 代码 | 贴,用源码引用语法(见 conventions) | 不必贴 |
| 对比 | 和别的实现/架构比 | 对照着讲,帮人理解 |
| 加分项 | 工程实践指导:怎么用、怎么调、怎么量、踩过什么坑 | 演进脉络:这概念从哪来、往哪去 |

判定:讲的是"某个具体系统里的东西"→ A;讲的是"概念本身"→ B。

## 2. 行文:读得下去(反刻板)

- **顺着一条主线写,别平铺维度**。读者要跟着一条问题链走,不想在几个维度间来回跳。
  - 刻板:`## 时间维度` → `## 结构维度` → `## 效率维度`(读者被迫换线)
  - 自然:序列变长记不住 → 注意力登场 → 代价 O(N²) → 怎么降下来
- **章节衔接有交代,但形式别重样**。过渡可以是一句承接、一个引子,或上一节末尾已埋好——已埋好就不必再写。
  - 刻板:每节开头都是"上一节建立了 X,一个自然的问题是 Y,本节用 Z 回答"
- **不为凑形式走全套**。本质→小例子→公式→算一遍,按需取舍;代价不必每个机制单起一段;核心要点不必每节收尾。哪处为凑形式写僵了,就换更自然的方式说清楚。
- **禁口癖套话**。"值得注意的是""本质上""不难发现""总的来说""换句话说""这正是……的价值"之类删掉;一句只说一件事,少用破折号串联的多重从句;同构排比(连续几段同一句式开头)必须打破。
- **单段 ≤4 行**。超了就拆段、转表格或转列表——步骤/对比/分类/字段这类枚举型内容默认表格或编号列表,不写成散文流水账。
- **每节开头 1-2 句给结论式概述**(这节回答什么问题、结论是什么),再展开;非关键的局部细节压成一行或挪进代码注释,不陷进去。
- **强调克制**:整段加粗短语超过 2 处要减;`> **核心要点**` 全篇 ≤3 个。

## 3. 内容:读完有收获

- **先让读者知道在干什么,再上公式/规范/代码**。形式化落地时读者跟得上,就算达标。
- **讲为什么,别只讲是什么**。引入一个机制要回答:它解决什么问题、不用它会怎样、为什么这样做而不是那样。**代价**(它换来了什么)、**什么时候反而不行**、**把什么麻烦留给了别处**——在某个地方说清,形式不限,能顺进去就行。只讲好处不讲代价是宣传,不是判断。
- **多方案对比要能用来选**。让读者看完答得出"什么情况下选谁",不是干列"A 有 X、B 有 Y"。B 类非选型场景时,弱化为"对照着讲帮人理解"。
- **复杂的公式用真实数字算一遍**,让读者能自己验;显然的、纯定义的公式就别硬算了。

## 4. 事实底线(不展开)

- 非通识缩写第一次出现给全称;引用官方文档/规格标章节号;数值标来源、不确定就写 `> **待确认**`、别编。
- 来源冲突取更可信的:规范 > 官方文档 > 论文 > 应用笔记 > 博客 > 推断。
- 排版上有客观对错的(代码块标语言、公式用 LaTeX、复用官方图标来源、Mermaid 主题由构建兜底等)查 `references/conventions.md`,写到哪查到哪。

## 5. 写完自检

### 通用两问(通读一遍)

- 顺着读下来通吗?有没有套同一句式开头、硬凑的段落、凑数的小结?
- 读完懂这个东西了吗(解决什么、为什么、代价、对比)?还是只记住了一堆"是什么"?

### Profile A 追加清单

- [ ] 概述建立上下文:开头交代了本篇在系统里的位置(它属于哪层、上下游是谁)?
- [ ] 关键代码用源码引用新语法(fence 头声明 `src="..." lines="..." anchor="..."`,构建时从源码拉取、防漂移,写法见 conventions)?
- [ ] 有跨实现/跨架构对比?
- [ ] 有工程实践指导(怎么调、怎么量、踩过什么坑),且事实来自一手规范(`reference/` 里有据可查)?
- [ ] 寄存器/时序/参数标了 spec 章节号?

### Profile B 追加清单

- [ ] 抽象概念配了小例子或类比?
- [ ] 演进脉络讲清了(这概念解决什么、之前怎么做、之后往哪走)?
- [ ] 没有为了"工程感"硬贴无关代码?

## 6. 构建校验(agent 工作流)

本仓库 md 用 `build_html.py` 构建成单文件 HTML(侧边栏/搜索/代码行号/源码追踪),比纯 md 渲染友好,优先构建后查看。agent 写完一篇笔记后:

1. `python3 build_html.py <专题目录> --check` 校验死链/缺图/坏 mermaid/源码引用问题;有 error 退出码非 0,据此修。
2. 通过后 `python3 build_html.py <专题目录>` 构建 HTML 查看效果。
3. 要看每篇渲染了多少图/代码块/源码引用,加 `--check --json`(机器可读)。

进 HTML 的文件范围、跨文档链接、源码引用两种写法、Mermaid/公式/表格/标题层级等语法细节,统一查 `references/conventions.md`。
