1. EDK2 是什么？

EDK II（EFI Development Kit II）是 UEFI（Unified Extensible Firmware Interface）规范与 PI（Platform Initialization）规范的开源参考实现。简单来说：

  • BIOS/UEFI 固件就是计算机启动时最先运行的软件，负责初始化硬件、加载操作系统。
  • EDK2就是用来编写这种固件的"SDK + 代码库"。
  • 你看到的 sophgo-edk2 就是基于 EDK2，为 SOPHGO 的 SG2046 RISC-V 芯片写的一套 UEFI 固件。

2. UEFI/PI 规范背景与 EDK2 的对应关系

EDK2 不是随意设计的，它实现了两套紧密相关的规范：UEFI 规范定义了 OS 与固件之间的接口，PI 规范定义了固件内部的启动阶段与模块交互机制。

2.1 UEFI 规范：操作系统看到的接口

UEFI 规范（目前常见 2.8/2.9/2.10）主要规定：

  • System Table：OS Loader 进入时收到的第一个数据结构，包含指向 Boot Services、Runtime Services、Configuration Tables 的指针。
  • Boot Services：内存分配、Handle/Protocol、加载镜像、启动设备枚举等。
  • Runtime Services：变量读写、复位、时间、虚拟地址映射等。
  • Protocols：设备驱动化的接口标准，如 Block I/O、Simple File System、Graphics Output。

在 EDK2 中，这些定义主要位于 MdePkg/Include/Uefi/ 与 MdePkg/Include/Protocol/。

2.2 PI 规范：固件内部怎么启动

PI（Platform Initialization）规范是 UEFI 联盟发布的另一套规范，它不关心操作系统看到什么，只关心固件内部如何从零开始把硬件初始化到可以加载 OS 的状态。PI 规范把启动过程抽象为 SEC、PEI、DXE、BDS 等阶段，并定义了阶段之间传递数据、调用服务的机制。

PI 规范目前分为 5 卷，每一卷解决一个独立的问题域。下面逐卷说明它们的目的、包含的核心内容、与 EDK2 源码的对应关系，以及在 SG2046 平台上的具体体现。

Volume 1：Pre-EFI Initialization Core Interface（PEI 核心接口）

解决什么问题：系统上电后，DRAM 往往还没初始化，C 语言运行环境也不完整。Volume 1 定义了在这个"资源极度匮乏"的早期阶段，固件如何完成最基本初始化并把控制权交给下一阶段。

核心内容：

  • PEI 阶段划分：SEC 之后、DXE 之前的阶段称为 PEI。Volume 1 规定了 PEI Core 的入口、PEIM（PEI Module）的加载与调度方式。
  • SEC Handoff：定义 EFI_SEC_PEI_HAND_OFF 结构，SEC 把临时内存、栈、Boot Firmware Volume（BFV）信息传给 PEI Core。这是 SEC→PEI 切换的核心数据结构，定义在 Volume 1 第 5 章（PEI Foundation）。
  • 临时内存支持 PPI：定义 EFI_TEMPORARY_RAM_SUPPORT_PPI，PEI Core 在发现永久内存后调用它完成栈和 HOB 从临时内存到永久内存的迁移。
  • PPI（PEIM-to-PEIM Interface）：PEI 阶段模块之间的接口契约。一个 PEIM 通过 PeiServicesInstallPpi 注册 PPI，其他 PEIM 通过 PeiServicesLocatePpi 查找并使用。
  • HOB（Hand-Off Block）：PEI 向 DXE 传递信息的唯一标准化机制。Volume 1 定义了 HOB 通用头、PHIT HOB、Memory Allocation HOB、Resource Descriptor HOB、GUID Extension HOB 等。
  • PEI Services：PEIM 可调用的系统服务表，包括 PPI 管理、HOB 分配、内存分配（永久内存发现前/后）、FV 遍历、启动模式查询、状态码报告等。
  • Boot Mode：定义了 NORMAL_BOOT、BOOT_ON_FLASH_UPDATE、BOOT_IN_RECOVERY_MODE 等启动模式，平台 PEIM 根据 BootMode 决定初始化路径。
  • SEC 阶段信息：Volume 1 第 13 章（Security (SEC) Phase Information）定义 SEC 阶段的职责和 SEC→PEI 切换约定。

对应 EDK2 源码：

  • 接口定义：MdePkg/Include/Pi/PiPeiCis.h（PEI Services）、MdePkg/Include/Pi/PiHob.h（HOB）、MdePkg/Include/Ppi/*.h（PPI）。
  • PEI Core 实现：edk2/MdeModulePkg/Core/Pei/，负责调度 PEIM、维护 PPI 数据库、HOB 列表。
  • SG2046 平台 PEIM：Silicon/Sophgo/Modules/CpuPei/CpuPei.c、MemoryInitPei/MemoryInitPei.c、PlatformPei/PlatformInitPei.c、FvParserPei/FvParserPei.c。

SG2046 实例：MemoryInitPei.c 在 DRAM 初始化完成后，调用 BuildResourceDescriptorHob 把系统 RAM 注册到 HOB 列表；FvParserPei.c 安装 gEfiFirmwareVolumeInfoPpiGuid，让 PEI Core 能遍历压缩后的 DXE FV。

Volume 2：Driver Execution Environment Core Interface（DXE 核心接口）

解决什么问题：PEI 阶段结束后，DRAM 已经可用，但操作系统还需要大量标准服务（内存分配、设备枚举、变量存储、启动管理）。Volume 2 定义了如何在一个"服务丰富"的环境中加载驱动、建立协议、最终把系统交给 OS Loader。

核心内容：

  • DXE 阶段划分：DXE 又分为 DXE Foundation、DXE Dispatcher、BDS 等子阶段。Volume 2 重点描述 DXE Foundation 和 Dispatcher。
  • Protocol 与 Handle：DXE 阶段模块之间的接口称为 Protocol。Protocol 通过 GUID 标识，挂到 Handle 上。DXE Core 维护 Handle 数据库，提供 InstallProtocolInterface、LocateHandleBuffer、OpenProtocol 等 Boot Services。
  • Boot Services：内存分配（AllocatePages/AllocatePool）、事件（Events/Timers）、镜像加载（LoadImage/StartImage）、设备连接（ConnectController）等。
  • Runtime Services：变量读写（GetVariable/SetVariable）、时间、复位、Capsule、虚拟地址映射等，这些服务在 OS 运行后仍然可用。
  • DXE Dispatcher 与 DEPEX：DXE Driver 通过依赖表达式（DEPEX）声明自己需要哪些 Protocol。Dispatcher 根据 Protocol 安装情况决定加载顺序。

对应 EDK2 源码：

  • 接口定义：MdePkg/Include/Uefi/UefiSpec.h（System Table、Boot/Runtime Services）、MdePkg/Include/Protocol/*.h（Protocol）。
  • DXE Core 实现：edk2/MdeModulePkg/Core/Dxe/，负责 Handle/Protocol 数据库、Dispatcher、Boot Services 表。
  • SG2046 平台 DXE Driver：UefiCpuPkg/CpuDxeRiscV64/CpuDxe.c、EmbeddedPkg/Drivers/FdtClientDxe/FdtClientDxe.c、Silicon/Sophgo/SG2046Pkg/Drivers/AcpiPlatformDxe/AcpiPlatformDxe.c。

SG2046 实例：CpuDxe.c 安装 gEfiCpuArchProtocolGuid，这是 DXE 中大量驱动 DEPEX 依赖的"关键 Protocol"；FdtClientDxe.c 从 HOB 中读取 FDT 并注册 gFdtClientProtocolGuid，供其他驱动查询设备树。

Volume 3：Shared Architectural Elements（共享架构元素）

解决什么问题：有些机制既不在 PEI 也不在 DXE 独占，而是跨阶段共享（例如 SMBIOS、ACPI、变量、固件卷格式）。Volume 3 把这些"公共基础设施"标准化，避免各卷重复定义。

核心内容：

  • Firmware Volume（FV）格式：定义 FV 头、文件头、节（Section）格式、GUID 命名、属性标志。EDK2 的 GenFds 工具按此格式生成固件。
  • SMBIOS / ACPI：定义系统信息表（SMBIOS）和高级配置电源接口（ACPI）如何在 PI 架构中生成、安装、暴露给 OS。
  • 变量（Variables）：定义非易失变量（Non-Volatile Variables）和易失变量的存储模型、属性、接口，Runtime Services 中的 GetVariable/SetVariable 最终依赖此模型。
  • Status Code / Report Status Code：跨阶段的状态码报告机制，PEI 和 DXE 都通过 ReportStatusCode 输出调试/错误信息。
关于 FDT（Flattened Device Tree）：FDT 不是 PI 规范定义的内容，它由独立的 Devicetree Specification 维护。EDK2 中通过 HOB 传递 FDT 的做法是 EDK2 的实现约定，而非 PI 规范要求。SG2046 在 SEC 阶段将 OpenSBI 传入的 FDT 复制到 HOB 中，DXE 阶段由 FdtClientDxe 解析。

对应 EDK2 源码：

  • FV 定义：MdePkg/Include/Pi/PiFirmwareVolume.h、MdePkg/Include/Pi/PiFirmwareFile.h。
  • 变量实现：MdeModulePkg/Universal/Variable/RuntimeDxe/VariableRuntimeDxe.inf。
  • SMBIOS/ACPI 实现：MdeModulePkg/Universal/SmbiosDxe/SmbiosDxe.inf、MdeModulePkg/Universal/Acpi/AcpiTableDxe/AcpiTableDxe.inf。
  • SG2046 平台 ACPI：Silicon/Sophgo/SG2046Pkg/AcpiTables/SG2046-FPGA/SG2046-FPGA-AcpiTables.inf。

SG2046 实例：SG2046 的 FDF 文件（SG2046-FPGA.fdf）定义了 [FD.SG2046-FPGA]、[FV.DXEFV]、[FV.FVMAIN_COMPACT]，这些 FV 的布局严格遵循 Volume 3 的 FV 格式。

Volume 4：Management Mode Core Interface（管理模式核心接口，MM/SMM）

解决什么问题：定义一种高特权级、对 OS 透明的执行环境（Management Mode，MM），用于处理平台特定事件（如电源管理、安全监控、硬件纠错）。在 x86 上对应 SMM 模式；在 ARM 上对应 TrustZone。PI 1.7 起将标题从 "System Management Mode" 改为 "Management Mode Core Interface"，以涵盖更广义的管理模式抽象。

在 SG2046 / RISC-V 上的情况：RISC-V 架构目前没有与 x86 SMM 完全对等的机制，因此 SG2046 EDK2 不实现 Volume 4 的内容。RISC-V 的 M-mode（由 OpenSBI 占用）承担了一部分底层平台管理职责，但它对 S-mode 的 EDK2/OS 不是"透明"的，而是通过 SBI 调用显式服务。

对应 EDK2 源码：对 SG2046 不适用，x86 平台可参考 MdeModulePkg/Core/PiSmmCore/、UefiCpuPkg/PiSmmCpuDxeSmm/。

Volume 5：Standards（平台总线协议标准）

解决什么问题：定义 PI 架构中平台级总线/主机控制器协议的标准接口，使不同厂商的硬件可以遵循统一的驱动模型。

核心内容（PI 1.9）：

  • Super I/O Protocol：标准化的超级 I/O 芯片接口。
  • Super I/O 与 ISA Host Controller 交互：定义 Super I/O 与 ISA 总线主控的交互方式。
  • CPU I/O Protocol：提供 CPU 级别的 I/O 端口访问抽象。
  • Legacy Region Protocol：管理传统 x86 兼容内存区域（如 0xA0000–0xFFFFF）。
  • I2C Protocol Stack：I2C 总线协议栈。
  • SPI Protocol Stack：SPI 总线协议栈。
  • Appendix: Error Codes：错误码附录。
重要澄清：Volume 5 不包含 SEC Handoff、临时内存迁移或信任链内容。这些内容属于 Volume 1（Pre-EFI Initialization Core Interface）：
  • EFI_SEC_PEI_HAND_OFF 结构定义在 Volume 1 第 5 章（PEI Foundation），对应源码 MdePkg/Include/Pi/PiPeiCis.h。
  • EFI_TEMPORARY_RAM_SUPPORT_PPI 同样定义在 Volume 1，对应源码 MdePkg/Include/Ppi/TemporaryRamSupport.h。
  • SEC 阶段信息和 SEC→PEI 切换约定在 Volume 1 第 13 章（Security (SEC) Phase Information）。

对应 EDK2 源码：Volume 5 的协议主要对应 MdeModulePkg/Universal/ 下的各总线驱动。对 SG2046 RISC-V 平台，大部分 Legacy/ISA 相关内容不适用，I2C/SPI 协议栈在需要时才引入。

SG2046 实例：SG2046 的 SEC→PEI 切换在 PeilessSec.c 中实现：填充 EFI_SEC_PEI_HAND_OFF，设置临时内存基址 0x81000000（PcdEfiMemoryBottom）、栈基址 0x84FF0000（PcdTemporaryRamBase = EFI_STACK_BASE）、BFV 指向 0x80200000（PcdRiscVPeiFvBase = FW_BASE_ADDRESS），然后跳转到 PeiCore。这些地址值来源于 SG2046.fdf.inc。

2.3 为什么 PI 规范要分成五卷？

PI 规范的分卷不是随意为之，而是按照问题域隔离和实现可替换性设计的：

  • Volume 1 与 Volume 2 分别对应"早期初始化"和"服务环境"：PEI 阶段内存受限、没有完整服务；DXE 阶段内存充裕、服务完整。两者需要的抽象截然不同，所以分别成卷。SEC Handoff、临时内存迁移等 SEC→PEI 切换机制也在 Volume 1 中定义。
  • Volume 3 提取公共机制：FV 格式、ACPI/SMBIOS、变量等既被 PEI 使用也被 DXE 使用，单独成卷避免重复定义。
  • Volume 4 针对管理模式：SMM/MM 是 x86/特定架构的概念，RISC-V 不需要实现，因此可以整卷忽略。PI 1.7 起将名称从 "System Management Mode" 改为 "Management Mode Core Interface"。
  • Volume 5 统一总线协议：将平台级总线（Super I/O、I2C、SPI 等）的驱动接口标准化，便于跨厂商复用。

对 SG2046 这样的 RISC-V 平台来说，重点关注 Volume 1（PEI + SEC Handoff）、Volume 2（DXE）、Volume 3（FV/ACPI/SMBIOS/变量），Volume 4 和 Volume 5 大部分内容可跳过。

3. EDK2 核心概念（新手必读）

3.1 UEFI 启动的 7 个阶段

UEFI 把启动过程标准化为 7 个阶段，每个阶段有明确职责：

阶段英文职责类比

3.2 三个最重要的抽象

HOB

Hand-Off Block（传递块）

PEI 阶段产生的各种信息（内存大小、CPU 信息、FDT 地址等）通过 HOB 列表传递给 DXE 阶段。可以把它理解为阶段之间的快递单。

PPI / Protocol

接口契约

PPI 是 PEI 阶段模块之间的接口；Protocol 是 DXE 阶段驱动之间的接口。它们都是"我提供什么服务"的声明。

PCD

Platform Configuration Database

平台配置数据库。把硬件相关的常量（内存基址、CPU 数量、串口地址等）从代码中抽离出来，方便不同平台复用同一份代码。

  • FVMAIN_COMPACT：主 FV，通常包含 SEC、PEI Core、压缩后的 DXE FV

3.6 RISC-V 特权模式与 EDK2 的关系

SG2046 基于 RISC-V，EDK2 运行在 S-mode（Supervisor mode），依赖 OpenSBI 提供 M-mode 服务：

模式名称EDK2 中的角色
M-modeMachine modeOpenSBI 运行，处理底层硬件、PLIC/CLINT、ECALL
S-modeSupervisor modeEDK2、GRUB2、OS 内核运行
U-modeUser mode用户态应用，固件阶段基本不涉及
EDK2 通过 SBI ecall 使用 OpenSBI 提供的 M-mode 服务，例如串口输出（sbi_console_putchar）、系统复位（sbi_system_reset）等。

3.7 为什么 EDK2 要分阶段？

UEFI 分阶段的核心目的是在系统内存和服务尚未完全就绪时，仍能逐步完成硬件初始化：

  1. SEC 使用临时内存：此时没有 DRAM 或 DRAM 未初始化，只能用 SRAM/预分配的小块内存。
  2. PEI 初始化永久内存：DRAM 就绪后，HOB/栈迁移到永久内存，后续阶段才能大规模分配内存。
  3. DXE 建立完整服务：内存、中断、MMU 就绪后，才能加载大量驱动和协议栈。
  4. BDS 才与用户交互：只有控制台、存储、显示都就绪后，才能选择启动设备。

这种分层让固件代码可以按依赖顺序组织，也便于不同平台复用通用模块。

3.8 PEI Services / Boot Services / Runtime Services

EDK2 在不同阶段提供不同的"服务表"，驱动/PEIM 通过它们访问系统能力：

服务表可用阶段核心能力
EFI_PEI_SERVICES **PeiServicesPEIPPI 安装/查找、内存分配（HOB/页）、状态码、FV 遍历、启动模式
EFI_BOOT_SERVICES *gBSDXE / BDS / TSL内存分配、Handle/Protocol、事件、加载镜像、连接控制器
EFI_RUNTIME_SERVICES *gRTDXE / BDS / TSL / RT变量读写、时间、复位、Capsule、虚拟地址映射

这些服务表由对应阶段的 Core（PeiCore、DxeCore）初始化并填充函数指针。例如 PeiServicesInstallPpi 最终调用 PeiServices->InstallPpi()；gBS->InstallProtocolInterface 由 DxeCore 实现。

3.9 DEPEX：模块依赖表达式

每个 PEIM / DXE Driver 都可以声明依赖（Dependency Expression）。构建工具 GenDepex 把它编译成一段字节码，PEI/DXE Core 在调度前解析：

# 典型的 DXE DEPEX：必须等 CPU Arch Protocol 安装后才能加载
[Depex]
  gEfiCpuArchProtocolGuid AND gEfiPciIoProtocolGuid

DEPEX 语法支持 AND、OR、NOT、TRUE、FALSE。如果没有 [Depex] 段，构建工具会根据 [Protocols] 段自动生成。APRIORI 列表中的模块优先加载，不受 DEPEX 限制。

DEPEX 本质上是 Guid 的布尔表达式。DXE Core 维护一张"已安装 Protocol 的 Guid 表"，每安装一个新 Protocol 就重新评估所有未调度驱动的 DEPEX，满足条件立即加载。

3.10 Library Class / Library Instance：复用的关键

EDK2 用"库类 + 库实例"分离接口与实现：

  • Library Class：头文件 + API 契约，如 SerialPortLib、DebugLib、HobLib
  • Library Instance：具体实现，如 BaseSerialPortLibRiscVSbiLib（通过 SBI 输出串口）、BaseDebugLibSerialPort

同一 Library Class 在不同阶段可以绑定不同 Instance。例如 TimerLib 在 SEC/PEI 使用 BaseRiscV64CpuTimerSecLib，在 DXE 使用 BaseRiscV64CpuTimerLib；MemoryAllocationLib 在 PEI 使用 PeiMemoryAllocationLib，在 DXE 使用 UefiMemoryAllocationLib。

4. 关键数据结构详解

理解 EDK2 必须理解几个核心数据结构：HOB、PPI/Protocol 描述符、PCD、SEC Handoff。它们是整个启动流程的"骨架"。

与 PI 规范的对应：本章节的 HOB、PPI、SEC Handoff 由 PI 规范 Volume 1 定义；Protocol、Handle、System Table 由 PI 规范 Volume 2 定义。建议先阅读 第 2 节规范背景 建立整体概念。

4.1 HOB 通用头与 HOB 列表

4.4 SEC Handoff 数据结构

SEC 通过 EFI_SEC_PEI_HAND_OFF 把临时内存、栈、BFV 信息传给 PEI Core：

typedef struct {
  UINT16  DataSize;                // 本结构大小
  VOID    *BootFirmwareVolumeBase; // PEI FV 基址
  UINTN   BootFirmwareVolumeSize;  // PEI FV 大小
  VOID    *TemporaryRamBase;       // 临时内存基址
  UINTN   TemporaryRamSize;        // 临时内存总大小（含栈）
  VOID    *PeiTemporaryRamBase;    // 给 PEI Core 用的临时内存底
  UINTN   PeiTemporaryRamSize;     // 给 PEI Core 用的临时内存大小
  VOID    *StackBase;              // 栈底

SG2046 在 PeilessSec.c 中填充如下：

SecCoreData.StackBase = (VOID *)StackBase;                         // 0x84FF0000
SecCoreData.StackSize = StackSize;                                 // 0x10000
SecCoreData.TemporaryRamBase = (VOID *)UefiMemoryBase;             // 0x81000000

SecCoreData.PeiTemporaryRamBase = SecCoreData.TemporaryRamBase;

注意 StackBase 是栈底（低地址），栈向低地址生长；实际栈顶是 StackBase + StackSize。SEC 汇编已经把 sp 指向栈顶。

  EFI_GUID  *Guid;

4.6 Protocol 与 Handle 数据库

DXE 阶段通过 Handle（句柄）和 Protocol（协议）组织对象：

  • Handle：一个抽象对象，可以是一个驱动、一个控制器、一个设备
  • Protocol：挂到 Handle 上的一组接口函数和数据
  • 一个 Handle 可以安装多个 Protocol；多个 Handle 可以安装同一种 Protocol
// 安装 Protocol：把 Protocol 挂到自己的 ImageHandle 上
gBS->InstallProtocolInterface (
       &ImageHandle,
       &gEfiCpuArchProtocolGuid,
       EFI_NATIVE_INTERFACE,
       &gCpu
       );

// 消费 Protocol：按 GUID 查找系统里的某个 Protocol 实例
gBS->LocateProtocol (
       &gEfiAcpiTableProtocolGuid,
       NULL,
       (VOID **)&AcpiTable
       );

DXE Core 内部维护 Handle 数据库：每个 Handle 对应一个 Protocol 链表。查找 Protocol 时先搜索 Guid 索引，再返回对应 Protocol 实例。这种设计让驱动可以松散耦合。

6.1 OpenSBI → EDK2 的约定

OpenSBI 以 FW_PAYLOAD 形式打包 EDK2 固件，跳转时：

  • a0：Boot Hart ID（启动核编号）
  • a1：Flattened Device Tree 地址（FDT）
  • PC：跳转至 0x80200000（FW_BASE_ADDRESS）

EDK2 SEC 入口汇编从 a0/a1 接收参数，调用 C 函数 SecStartup(BootHartId, DeviceTreeAddress)。

6.2 为什么 SG2046 要前面有 OpenSBI？

RISC-V 把 CPU 初始化、PLIC/CLINT、SBI 规范实现放在 M-mode 的 OpenSBI 里。EDK2 作为 UEFI 固件运行在 S-mode，不需要也不应该直接操作 M-mode 寄存器。这样分层后，EDK2 可以专注于 UEFI 规范实现，OpenSBI 负责 RISC-V 特权层基础设施。

8. EDK2 内存管理专题

PI 规范定位：临时内存、永久内存迁移、HOB 内存分配由 PI 规范 Volume 1 定义；DXE 阶段的页式内存分配（AllocatePages/AllocatePool）由 PI 规范 Volume 2 定义。本章把这两条线索在 SG2046 上的实现串起来。

内存管理是 EDK2 平台移植中最容易出错的部分之一。SG2046 采用"临时内存 → 永久内存 → DXE 页表"三步走的策略。

8.1 为什么需要临时内存？

SEC 阶段刚进入 EDK2 时，系统内存尚未被 EDK2 接管。此时需要一段已经可用的内存作为栈和堆，让 C 代码能够运行。这段内存称为临时内存（Temporary RAM / CAR）。

在 SG2046 中，临时内存来自 FDF 预先分配的 0x81000000 ~ 0x85000000 区域，其中栈顶为 0x85000000。

8.2 SEC 阶段的内存初始化

文件：PeilessSec.c

8.3 SEC_MEMORY_OFFSET 的作用

在 PeilessSec.h 中定义：

#define SEC_MEMORY_OFFSET 0x1000

这 4KB 的偏移用于：

  • 保留 SEC 自身运行所需的数据/栈保护页
  • 避免 HOB 堆与 UEFI 内存底部完全重叠，防止对齐问题
  • 给后续 PEI Core 放置临时数据留出安全边界

9. FDT（设备树）在 EDK2 中的流转

PI 规范定位：FDT（Flattened Device Tree）不是 PI 规范定义的内容，它由独立的 Devicetree Specification 维护。EDK2 中通过 HOB 传递 FDT 是 EDK2 的实现约定（基于 HOB GUID Extension 机制），而非 PI 规范要求。SG2046 遵循了 EDK2 RISC-V 平台的通用做法。

FDT（Flattened Device Tree）是 ARM/RISC-V 平台描述硬件的标准格式。SG2046 的 FDT 从 OpenSBI 传入，贯穿 SEC/PEI/DXE。

11.1 PEI Core 的调度机制

PEI Core 维护一个 PPI 数据库和一个待调度 PEIM 列表：

  1. PEI Core 从 BFV 中找到所有 PEIM
  2. 解析每个 PEIM 的 PEI_DEPEX，确定依赖的 PPI
  3. 循环检查：如果某个 PEIM 的所有依赖 PPI 都已安装，就调度它
  4. PEIM 执行时可以通过 PeiServicesInstallPpi 安装新的 PPI，触发更多 PEIM 调度

PEIM 的 PeimInitialize 入口函数返回 EFI_SUCCESS 后，PEI Core 认为该 PEIM 完成。

PPI 数据库的内部结构

PEI Core 在内存中维护一个 PPI 记录数组，每个记录包含 Flags、Guid、Ppi 指针。当 PeiServicesInstallPpi 被调用时，Core 会：

  1. 把新 PPI 加入数据库
  2. 扫描所有已注册的 PPI Notify（通知回调），如果 GUID 匹配则调用回调
  3. 重新评估所有未调度 PEIM 的 DEPEX

这种"安装-通知-重新评估"机制让 PEIM 之间可以形成依赖链。例如 MemoryInitPei 安装 gEfiPeiMemoryDiscoveredPpiGuid 后，依赖该 PPI 的 PEIM 才会被调度。

PEIM 调度顺序示例（SG2046）

PEI Core 启动，SEC 已安装 SecHobDataPpi 和 TemporaryRamSupportPpi
CpuPei 无特殊依赖，先运行，安装 CPU HOB
MemoryInitPei 发布系统 RAM，安装 MemoryDiscoveredPpi
PlatformInitPei 发布永久内存，触发 TemporaryRamMigration
FvParserPei 解压 DXEFV，安装 FvInfoPpi
DxeIpl 安装 DxeIplPpi，最后被调用进入 DXE

注意实际调度顺序由 DEPEX 决定：需要 MemoryDiscoveredPpi 的 PEIM 必须等内存发布后才能运行。

  2. 其他驱动按 DEPEX（依赖表达式）决定加载时机

12.5 Handle/Protocol 数据库的内部机制

DXE Core 内部用一个双向链表维护所有 Handle，每个 Handle 又有一个 Protocol 链表。关键数据结构大致如下：

typedef struct {
  UINTN             Signature;
  LIST_ENTRY        AllHandles;       // 所有 Handle 的全局链表
  LIST_ENTRY        Protocols;        // 本 Handle 上安装的 Protocol 链表
} IHANDLE;

typedef struct {
  UINTN             Signature;
  LIST_ENTRY        Link;             // 挂到 Handle 的 Protocols 链表
  EFI_GUID          ProtocolGuid;
  PROTOCOL_ENTRY    *Protocol;        // 指向全局 Protocol 入口（含所有实例链表）
  VOID              *Interface;       // Protocol 实例指针
  LIST_ENTRY        OpenList;         // 打开本 Protocol 的 Consumer 列表
} PROTOCOL_INTERFACE;

当驱动调用 gBS->InstallProtocolInterface 时，DXE Core 会：

  1. 如果 Handle 不存在则创建新的 IHANDLE
  2. 创建 PROTOCOL_INTERFACE 并挂到 Handle 上
  3. 更新全局 Protocol 索引表
  4. 触发所有等待该 Protocol GUID 的事件通知
  5. 重新评估所有未调度驱动的 DEPEX

13. DXE 驱动模型：Protocol 的安装与消费

DXE 阶段的核心机制是 Protocol。驱动通过 Protocol 暴露接口，其他驱动通过 Protocol 使用服务。

13.1 Protocol 是什么？

Protocol 是一个 C 结构体，包含一组函数指针和数据。每个 Protocol 用一个 GUID 唯一标识。例如：

  • EFI_CPU_ARCH_PROTOCOL：CPU 架构服务（开关中断、cache 操作、内存属性设置）
  • EFI_BLOCK_IO_PROTOCOL：块设备读写（SD 卡、硬盘）
  • EFI_SIMPLE_FILE_SYSTEM_PROTOCOL：文件系统访问
  • EFI_ACPI_TABLE_PROTOCOL：ACPI 表安装

13.4 驱动绑定与 ConnectController

很多驱动实现 Driver Binding Protocol，包含 Supported、Start、Stop 三个接口：

  • Supported：检查某个 Handle 是否由本驱动管理
  • Start：初始化设备，安装子 Handle 和 Protocol
  • Stop：停止设备，释放资源

BDS 阶段调用 gBS->ConnectController() 触发驱动绑定：DXE Core 遍历所有 Driver Binding Protocol，对每个 Handle 调用 Supported()，成功者调用 Start()。这就是 PCI 设备枚举、USB 设备识别、SD 卡发现的本质。

13.5 ConnectController 的递归与非递归

在 PlatformBm.c 中可以看到：

Status = gBS->ConnectController (
                Handle, // ControllerHandle
                NULL,   // DriverImageHandle
                NULL,   // RemainingDevicePath -- produce all children
                FALSE   // Recursive
                );

第四个参数 Recursive 决定是否为递归连接。SG2046 BDS 通常使用非递归连接：先连接 PCI Root Bridge 产生 PciIo Handle，再连接显示设备产生 GOP Handle，最后再 EfiBootManagerConnectAll() 做全量递归连接。这样分阶段控制可以避免某些设备在控制台就绪前被错误初始化。

14. BDS 阶段：从固件到 OS Loader

PI 规范定位：BDS 通常被视为 DXE 阶段向 OS 移交前的最后一个子阶段，相关机制（Boot Services、Protocol、启动选项）由 PI 规范 Volume 2 定义。本章重点分析 SG2046 平台如何在这些标准接口之上实现具体启动策略。

BDS（Boot Device Selection）是 UEFI 启动流程中最后一个由固件主导的阶段。DXE 把系统初始化完毕后，把控制权交给 BDS；BDS 负责枚举启动设备、建立控制台、处理用户热键，并最终启动 OS Loader（如 GRUB2、systemd-boot 或 UEFI Shell）。

15. 变量存储与安全启动

PI 规范定位：UEFI 变量（Variable）的存储模型、属性、访问接口由 PI 规范 Volume 3（Shared Architectural Elements） 定义；Runtime Services 中的 GetVariable / SetVariable 由 PI 规范 Volume 2 暴露。安全启动（Secure Boot）则是 UEFI 规范内容。

15.1 UEFI 变量是什么？

UEFI 变量是固件与 OS Loader 之间持久化存储的键值对，通过 Runtime Service GetVariable() / SetVariable() 访问。常见变量包括：

  • BootOrder：启动顺序。
  • Boot####：具体启动项。
  • ConIn / ConOut / ErrOut：控制台设备路径。
  • SecureBoot / PK / KEK / db / dbx：安全启动相关。

15.2 VariableRuntimeDxe 与变量存储布局

EDK2 中变量服务由 MdeModulePkg/Universal/Variable/RuntimeDxe/VariableRuntimeDxe.inf 提供。SG2046 的变量存储区域在 SG2046.fdf.inc 中定义：

DEFINE VARS_OFFSET                   = 0x00800000
DEFINE VARS_SIZE                     = 0x00010000
DEFINE VARS_FTW_WORKING_OFFSET       = $(VARS_OFFSET) + $(VARS_SIZE)
DEFINE VARS_FTW_WORKING_SIZE         = 0x00010000
DEFINE VARS_FTW_SPARE_OFFSET         = $(VARS_FTW_WORKING_OFFSET) + $(VARS_FTW_WORKING_SIZE)

其中 VARS_SIZE 是变量存储区，FTW_WORKING 和 FTW_SPARE 是 FaultTolerantWriteDxe 用于掉电安全写入的冗余区。

15.3 安全启动（Secure Boot）

SG2046-FPGA 的 DSC 中默认启用 SECURE_BOOT_ENABLE = TRUE，会额外编译：

  • SecureBootConfigDxe：Setup 界面配置安全启动。
  • SecureBootDefaultKeysDxe：预置默认 PK/KEK/db/dbx。
  • AuthVariableLib：对安全启动变量做签名验证。

安全启动链：BootROM 验证 FW → FW 验证 OS Loader（通过 db 证书链）→ OS Loader 验证 OS Kernel。任一环节失败则拒绝启动。

当前 SG2046 平台把 FLASH_ENABLE 默认设为 FALSE，变量通常存于模拟变量存储（EmuVariableNvMode）中，掉电不保留；正式产品需开启 NOR Flash 变量支持。

16. ACPI 与 SMBIOS 表安装

PI 规范定位：ACPI 表和 SMBIOS 表属于跨阶段共享架构元素，由 PI 规范 Volume 3（Shared Architectural Elements） 定义如何在 PI 架构中生成、安装并通过 UEFI Configuration Table 暴露给 OS。

16.1 ACPI 表安装流程

ACPI（Advanced Configuration and Power Interface）表是 OS 识别硬件拓扑的重要数据结构。SG2046 的 ACPI 表在构建时编译进 FV，运行期由 AcpiPlatformDxe.c 安装：

1

定位 EFI_ACPI_TABLE_PROTOCOL

通过 gBS->LocateProtocol 找到负责管理 ACPI 表的通用驱动。

2

定位包含 ACPI 存储文件的 FV

遍历所有 FirmwareVolume2 Protocol 实例，查找 PcdAcpiTableStorageFile 指定的 GUID 文件。

3

读取并校验表

用 FwVol->ReadSection(..., EFI_SECTION_RAW, ...) 读取每个原始表，重新计算 checksum。

4

安装到系统

调用 AcpiTable->InstallAcpiTable(...)，最终由 AcpiTableDxe 把 RSDT/XSDT 指针写入 EFI System Table Configuration Tables。

16.2 什么是 SMBIOS？为什么操作系统需要它？

SMBIOS（System Management BIOS）是一种标准化的数据结构，固件通过它向操作系统描述硬件信息：BIOS 厂商、主板型号、CPU 型号、内存容量、序列号、UUID 等。它源自 DMI（Desktop Management Interface），现在由 DMTF 维护，最新版本为 3.6.x。

对 OS 和用户态工具来说，SMBIOS 是"只读硬件信息数据库"：

  • Linux 内核启动时读取 SMBIOS，生成 /sys/class/dmi/id/ 下的文件（如 product_name、board_serial、bios_version），也用于 dmi_scan 匹配驱动。
  • 用户态工具如 dmidecode、lshw、systemd-detect-virt 都解析 SMBIOS。
  • OS 安装程序 / 云初始化通过 UUID、序列号识别实例身份。

换句话说：ACPI 告诉 OS "有什么设备和资源"，SMBIOS 告诉 OS "这些设备是什么型号、序列号是什么"。

16.3 SMBIOS 物理结构：从 Entry Point 到字符串

SMBIOS 数据在内存中由两部分组成：Entry Point Structure（EPS）和表数据区。EPS 是 OS 寻找 SMBIOS 的"路标"，表数据区包含若干条记录。

16.3.1 Entry Point Structure

EFI 系统会同时安装两个 EPS（通过 EFI Configuration Table）：

版本Anchor StringGuid地址宽度
SMBIOS 2.x_SM_gEfiSmbiosTableGuid32 位物理地址（TableAddress）
SMBIOS 3.x_SM3_gEfiSmbios3TableGuid64 位物理地址（TableAddress）

EPS 包含：Anchor String、Entry Point Length、SMBIOS 主/次版本号、表数据区最大长度、校验和、以及最重要的 TableAddress（指向表数据区起始）。

16.3.2 单条记录结构

表数据区由若干条记录顺序排列组成，每条记录格式固定：

typedef struct {
  UINT8   Type;      // 记录类型，如 0=BIOS, 1=System, 4=Processor, 17=Memory Device
  UINT8   Length;    // 格式化区域长度（含本头）
  UINT16  Handle;    // 唯一句柄，用于记录间交叉引用（如 Cache 指向 Processor）
  // Length 之后是字符串区，由若干 \0 结尾的 ASCII 字符串组成，最后以双 \0 结束
} EFI_SMBIOS_TABLE_HEADER;

记录的字符串引用很有意思：格式化区域里的字符串字段只存一个 index（1 开始），真正的字符串在记录尾部的字符串区。index 为 0 表示"无字符串"。例如 Type 1 的 Manufacturer 字段如果是 1，就表示字符串区第 1 个字符串是厂商名。

为什么这样设计？字符串长度差异大，统一放在记录尾部可以避免结构体对齐浪费，也便于本地化（同一 Type 不同语言的记录只有字符串区不同）。

16.3.3 遍历方法

OS 从 EPS 拿到 TableAddress 后，按 Type/Length/Handle + 字符串区 逐条解析。每条记录长度 = Length + 字符串区长度（到双 \0 为止）。Type 为 127 的记录是表结束标记。

16.8 SmbiosDxe：把记录变成 OS 可见的表

平台驱动把记录添加完后，SmbiosDxe 在 DXE 后期做两件事：

  1. 构造 EPS：把所有记录按 SMBIOS 格式拼成连续内存，计算总长度和校验和，生成 SMBIOS_TABLE_ENTRY_POINT（2.x）和 SMBIOS_TABLE_3_0_ENTRY_POINT（3.x）。
  2. 注册到 System Table：调用 gBS->InstallConfigurationTable (&gEfiSmbiosTableGuid, Eps) 和 gBS->InstallConfigurationTable (&gEfiSmbios3TableGuid, Eps64Bit)。

之后，DXE Core 的 EfiGetSystemConfigurationTable、BDS 启动管理器、OS Loader 都能通过 System Table 找到 SMBIOS 入口。

16.9 操作系统怎么读 SMBIOS？

UEFI OS Loader（GRUB2、systemd-boot、Linux EFISTUB）进入内核时会把 EFI System Table 传给内核。Linux 内核在 drivers/firmware/dmi_scan.c 中：

  1. 调用 efi.get_system_config_table(gEfiSmbios3TableGuid) 或 gEfiSmbiosTableGuid 拿到 EPS 地址。
  2. 校验 Anchor String 和 checksum。
  3. 根据 EPS 中的 TableAddress 遍历所有记录，解析 Type/Length/Handle/Strings。
  4. 把信息暴露到 sysfs：/sys/firmware/dmi/tables/DMI（原始表）、/sys/firmware/dmi/tables/smbios_entry_point（EPS）。
  5. 在 /sys/class/dmi/id/ 下生成人类可读的文件，如 sys_vendor、product_name、product_version、product_serial、product_uuid、bios_vendor、bios_version 等。

17. PCD：平台配置数据库

17.1 PCD 是什么？

PCD（Platform Configuration Database）是 EDK2 的“配置中心”。它把平台相关的常量、开关、地址、GUID 等集中声明，模块通过统一宏访问，避免把平台细节硬编码到源码中。

17.2 PCD 类型

类型说明典型用途
FixedAtBuild构建时固定，运行期只读寄存器基址、内存大小、功能开关
PatchableInModule构建时固定，但可在二进制中补丁需要运行时 patch 的常量
Dynamic运行期可读写Flash 变量偏移等状态
DynamicEx跨 Token Space 访问的 Dynamic PCD多包共享的动态配置

17.3 Token Space 与 AutoGen

每个包声明自己的 Token Space GUID。SG2046 平台在 Sophgo.dec 中声明：

21. 关键设计决策与 rationale

21.1 为什么选择 PeilessSec？

SG2046 使用 PeilessSec（无独立 PEI SEC 库）模式，SEC 阶段的 C 入口 SecStartup 直接构建 HOB 并调用 PEI Core。相比传统 OVMF 的 PlatformSecLib 封装，这种方式：

  • 减少一层抽象，代码更直观。
  • 便于在 SEC 中直接复制 FDT、构建 RISC-V 专属 Handoff HOB。
  • 与 RiscVVirt 风格保持一致，降低 RISC-V 平台维护成本。

21.2 FDT 为什么要复制一份？

PeilessSec.c 中：

FdtSize  = FdtTotalSize (DeviceTreeAddress);
FdtPages = EFI_SIZE_TO_PAGES (FdtSize);
FdtCopy  = AllocatePages (FdtPages);
if (FdtCopy != NULL) {
  FdtOpenInto (DeviceTreeAddress, FdtCopy, EFI_PAGES_TO_SIZE (FdtPages));
  FdtHobData = BuildGuidHob (&gFdtHobGuid, sizeof *FdtHobData);
  if (FdtHobData != NULL) {
    *FdtHobData = (UINT64)(UINTN)FdtCopy;
  }
}

原因：Bootloader 传入的 FDT 可能位于后续会被 PEI/DXE 覆盖的内存区域。复制到 SEC 堆（HOB 内存）可确保 FDT 安全传递到 DXE，并避免原位置被内存分配破坏。

21.3 临时栈与永久内存的边界

SG2046 把临时栈放在 FW 之后 64MB 区域的最高端（EFI_STACK_BASE = EFI_MEMORY_TOP - EFI_STACK_SIZE），永久内存从 EFI_MEMORY_TOP 开始。这样：

  • SEC/PEI 早期有确定可用的栈空间。
  • PEI 发现永久内存后通过 TemporaryRamMigration 把 HOB 和栈迁移过去，再归还临时内存。

21.4 为什么默认 FLASH_ENABLE=FALSE？

FPGA 平台通常没有可靠的 SPI NOR Flash 或主要用于仿真验证，关闭 Flash 驱动可缩短构建时间、减少依赖；变量使用 EmuVariable，便于在内存中快速重置测试。ASIC 平台会改为 TRUE，把变量持久化到 NOR Flash。
