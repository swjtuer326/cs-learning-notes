# LLM 训练与推理全景导论

> 为什么 LLM 的优化必须全栈视角？因为瓶颈会跨层传递——算法选择决定计算模式，计算模式决定硬件需求，硬件约束反过来限制算法设计。不理解这根链条，优化就是盲人摸象。

### 关键术语

| 缩写 | 全称 | 含义 |
|------|------|------|
| MFU | Model FLOPs Utilization | 模型算力利用率，训练核心指标 |
| AI | Arithmetic Intensity | 算术强度，FLOPS/Byte，判断计算密集还是访存密集 |
| GEMM | General Matrix Multiply | 通用矩阵乘法，LLM 的核心计算 |
| KV Cache | Key-Value Cache | 推理时缓存的注意力键值对 |
| TP | Tensor Parallelism | 张量并行，按权重列/行切分到多卡 |
| PP | Pipeline Parallelism | 流水线并行，按层切分到多卡 |
| DP | Data Parallelism | 数据并行，每卡完整模型+不同数据 |
| HBM | High Bandwidth Memory | 高带宽内存，GPU 主存 |
| Tensor Core | — | GPU 内的矩阵乘加加速单元 |
| NVLink | — | NVIDIA GPU 间高速互连，900 GB/s (H100) |

## 1. 一个问题引出全栈视角

训练一个 70B 参数的 LLM，为什么需要 64 张 H100？

这个问题没有单一层面的答案。让我们一步步推导：

**第一步：算力需求**

训练一个 70B 模型处理 2T tokens，理论计算量：

```
FLOPS = 6 × P × T = 6 × 70×10⁹ × 2×10¹² = 8.4 × 10²³
```

系数 6 来自前向（2P）+ 反向（4P）。单张 H100 FP16 峰值 989 TFLOPS：

```
单卡理论时间 = 8.4×10²³ / (989×10¹² × 3600) ≈ 236,000 小时
```

**第二步：但单卡放不下模型**

70B 参数 BF16 需 140 GB，加上梯度和 AdamW 优化器状态：

| 组件 | 大小 |
|------|------|
| 参数 (BF16) | 140 GB |
| 梯度 (BF16) | 140 GB |
| 优化器状态 (FP32: 参数+m+v) | 840 GB |
| 激活值 (选择性重计算) | ~40 GB |
| **总计** | **~1160 GB** |

单张 H100 只有 80 GB HBM。**模型都放不进去，算力再高也没用。**

**第三步：所以需要分布式——但引入了通信开销**

把模型切分到多张卡上，卡之间必须通信同步梯度。通信量有多大？

以 8 卡张量并行（TP=8）为例，每个 Transformer 层需要 2 次 All-Reduce：

```
每层通信量 = 2 × 2 × S × d_model × sizeof(BF16)
           = 2 × 2 × 4096 × 8192 × 2
           = 268 MB

80 层总计: 80 × 268 MB = 21 GB/步
```

NVLink 带宽 900 GB/s，理论通信时间 ~23 ms。但实际还有延迟、同步、协议开销，通信占比约 5-10%。

**第四步：通信占比拉低了 MFU**

```
MFU = 实际算力利用 / 理论峰值
```

如果通信占比 10%，意味着 10% 的时间 GPU 在等数据而不是计算。加上流水线气泡、Kernel Launch 开销等，实际 MFU 约 50%。

**第五步：修正计算**

```
实际需要 = 理论时间 / MFU = 236,000 / 0.5 ≈ 472,000 单卡小时
64 张 H100: 472,000 / 64 ≈ 7,375 小时 ≈ 307 天
```

这就是为什么需要 64 张 H100——不是算力不够，而是**单卡放不下模型，分布式引入通信开销，通信拉低 MFU，MFU 降低意味着需要更多卡来补偿。**

这个推导链条跨越了算法（模型大小）、系统（分布式策略）、硬件（HBM 容量、NVLink 带宽）三个层面。**任何单层面的优化都无法回答这个问题。**

## 2. 全栈视角的核心：瓶颈跨层传递

上例展示了一个普遍规律：**瓶颈会从一层传递到另一层**。理解这根传递链，是全栈优化的前提。

### 2.1 传递链的三种典型模式

**模式一：算法选择 → 访存瓶颈**

```
选择自回归解码（逐 Token 生成）
  → 每步只处理 1 个 Token，但需读取全部权重和 KV Cache
  → GEMM 形状从 [S, d]×[d, d] 变为 [1, d]×[d, d]
  → 算术强度从 ~S/2 降到 ~1
  → 从计算密集变为访存密集
  → Tensor Core 利用率从 >50% 降到 <5%
  → HBM 带宽成为瓶颈
```

这就是为什么推理的 Decode 阶段优化方向与训练完全不同——训练优化算力利用率，推理优化带宽利用率。

**模式二：架构选择 → 通信瓶颈**

```
选择 MoE 架构（稀疏激活）
  → 每个 Token 路由到不同专家
  → 专家分布在不同 GPU 上
  → 需要 All-to-All 通信发送 Token
  → 通信占比可达 20-30%
  → 互连带宽成为瓶颈
```

DeepSeek-V3 (671B MoE) 的 All-to-All 通信占比约 20%，是 MFU 的主要损失来源。而 Dense 模型（如 LLaMA-2 70B）的通信占比仅 5-10%。

**模式三：硬件约束 → 算法设计**

```
HBM 带宽有限（3.35 TB/s on H100）
  → Decode 阶段读取权重受带宽限制
  → 推理并发数受 KV Cache 显存限制
  → 倒逼算法层做 KV Cache 压缩
  → MLA 将 KV 压缩到 512 维潜在空间
  → KV Cache 缩小 ~16×，并发数提升 4×
```

MLA 不是"先有算法再找应用场景"，而是**推理带宽压力倒逼出的架构创新**。

### 2.2 用一个具体场景验证传递链

以"LLaMA-2 70B 在 H100 上做推理"为例，完整追踪瓶颈传递：

**Decode 阶段，batch=1，生成 1 个 Token 需要多久？**

```
每步需要读取的数据:
  模型权重: 70 GB (BF16, TP=2 后每卡 35 GB)
  KV Cache: ~1 KB/token × 4096 tokens = 4 MB (可忽略)

瓶颈分析:
  HBM 带宽: 3.35 TB/s
  读取权重时间: 35 GB / 3.35 TB/s ≈ 10.4 ms

  Tensor Core 计算时间:
  FFN GEMM [1, 8192]×[8192, 28672]: 2×1×8192×28672 = 470 MFLOPS
  H100 FP16 峰值 989 TFLOPS → 计算时间 ≈ 0.5 μs

  计算时间 0.5 μs vs 读取时间 10.4 ms → 差 20,000 倍!
  → 完全访存密集，GPU 99.99% 时间在等数据
```

这个 20,000 倍的差距直接决定了优化方向：

| 优化 | 作用层面 | 效果 |
|------|----------|------|
| 增大 batch | 系统 | 4 个请求共享权重读取 → 带宽效率提升 4× |
| FP8 量化 | 算法+硬件 | 权重从 70 GB 降到 35 GB → 读取时间减半 |
| 投机解码 | 算法 | 1 次大模型前向验证多个 Token → 等效加速 2-3× |
| MLA | 架构 | KV Cache 缩小 16× → 更多请求共享带宽 |

每个优化都作用于不同层面，但**解决的是同一个瓶颈——HBM 带宽**。

## 3. 两个核心指标：MFU 和算术强度

全栈优化需要两个量化工具来定位瓶颈。

### 3.1 MFU：训练的核心指标

MFU (Model FLOPs Utilization) 衡量训练中 GPU 算力的实际利用效率：

```
MFU = 实际 FLOPS / 硬件理论峰值 FLOPS

实际 FLOPS = 6 × P × tokens_per_step / time_per_step
```

**为什么 MFU 不可能达到 100%？**

```
100% 意味着 GPU 每个时钟周期都在执行 Tensor Core 指令
→ 需要数据永远就绪（无访存延迟）
→ 需要零通信开销（无分布式同步）
→ 需要零 Kernel Launch 间隔
→ 不可能

实际 MFU 构成:
  Tensor Core 有效计算:  50-65%
  通信开销:              5-30% (取决于并行策略)
  流水线气泡:            5-15% (PP)
  非 GEMM 操作:          5-10% (Softmax, Norm, 激活)
  Kernel Launch + 同步:  3-5%
  数据加载:              1-3%
```

**不同场景的 MFU 基线**：

| 场景 | 典型 MFU | 主要损失 |
|------|----------|----------|
| 单卡 Dense 模型 | 55-65% | 非 GEMM + Kernel Launch |
| 8 卡 TP | 50-60% | +TP 通信 5-10% |
| 64 卡 3D 并行 | 45-55% | +跨节点通信 + PP 气泡 |
| 2048 卡 MoE | 40-52% | +All-to-All 通信 20-30% |

MFU 是训练优化的北极星指标——所有优化最终都体现为 MFU 的提升。

### 3.2 算术强度：判断计算密集还是访存密集

算术强度 (Arithmetic Intensity) = 计算量 / 访存量，单位 FLOPS/Byte。

**为什么这个指标重要？** 因为 GPU 有两个物理上限——算力峰值和带宽峰值。算术强度决定了你受哪个上限约束：

```
如果 AI > 算力峰值/带宽峰值 → 计算密集，受算力约束
如果 AI < 算力峰值/带宽峰值 → 访存密集，受带宽约束

H100 的临界点:
  FP16: 989 TFLOPS / 3.35 TB/s ≈ 295
  FP8:  1979 TFLOPS / 3.35 TB/s ≈ 590
```

**用具体算子验证**：

以 LLaMA-2 70B 的 FFN Gate 投影为例，`[S, d_model] × [d_model, d_ff]`：

```
计算量 = 2 × S × d_model × d_ff
访存量 = (S × d_model + d_model × d_ff + S × d_ff) × sizeof(dtype)

S=4096, d_model=8192, d_ff=28672, BF16:
  计算量 = 2 × 4096 × 8192 × 28672 = 1.93 × 10¹² FLOPS
  访存量 = (4096×8192 + 8192×28672 + 4096×28672) × 2 = 1.75 × 10⁹ Bytes
  AI = 1.93×10¹² / 1.75×10⁹ ≈ 1103

  1103 >> 295 → 计算密集 → 优化方向：提高 Tensor Core 利用率
```

同一个算子在 Decode 阶段（S=1）：

```
  计算量 = 2 × 1 × 8192 × 28672 = 470 × 10⁶ FLOPS
  访存量 = (1×8192 + 8192×28672 + 1×28672) × 2 = 470 × 10⁶ Bytes
  AI = 470×10⁶ / 470×10⁶ ≈ 1.0

  1.0 << 295 → 访存密集 → 优化方向：减少数据搬运量
```

**同一个算子，S 从 4096 变到 1，算术强度从 1103 降到 1——这就是训练和推理优化方向完全不同的根本原因。**

## 4. 七层架构与学习路线

### 4.1 七层模型

LLM 全栈可以划分为七层，每层有明确的职责边界：

```
Layer 7: 应用层       — 对话/RAG/Agent，定义用户需求
Layer 6: 推理服务层   — vLLM/TRT-LLM，调度和显存管理
Layer 5: 训练框架层   — Megatron/DeepSpeed，并行策略编排
Layer 4: 算子层       — FlashAttention/GEMM，核心计算优化
Layer 3: GPU 编程层   — CUDA/Triton，Kernel 实现
Layer 2: GPU 微架构层 — SM/Tensor Core/HBM，硬件物理约束
Layer 1: 互连层       — NVLink/IB，多卡/多节点通信
```

**层间接口**：每层只关心相邻层的接口，不需要理解所有层。但**优化时需要跨层思维**——因为瓶颈会跨层传递。

### 4.2 本系列的学习路线

| 序号 | 文档 | 核心问题 | 预计学时 |
|------|------|----------|----------|

| 02 | Transformer 计算特征第一性分析 | 每个算子到底算多少、访多少？ | 10h |
| 03 | GPU 架构：从 SIMT 到 Tensor Core | 硬件如何执行我的 Kernel？ | 8h |

## 5. 要点回顾

| 要点 | 说明 |
|------|------|
| 瓶颈跨层传递 | 算法选择→计算模式→硬件需求→优化方向，四者联动 |
| 训练 vs 推理 | 训练计算密集（MFU 是核心），推理 Decode 访存密集（带宽是核心） |
| MFU | 训练北极星指标，典型 40-55%，损失来自通信+气泡+非 GEMM |
| 算术强度 | AI = FLOPS/Byte，>295 计算密集，<295 访存密集（H100 FP16） |
| 同一算子不同阶段 | FFN 在 Prefill 时 AI≈1103（计算密集），Decode 时 AI≈1（访存密集） |
| 全栈优化的本质 | 不是每层做到最优，而是各层协调配合消除跨层瓶颈 |
