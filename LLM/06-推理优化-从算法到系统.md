# 推理优化：从算法到系统

> 训练优化算力利用率，推理优化带宽利用率——这个根本差异决定了推理优化的全部策略。本文从自回归解码的两个阶段（Prefill 和 Decode）出发，定量分析各自的瓶颈，然后逐层推导 KV Cache 管理、量化、投机解码、连续批处理等优化如何作用于这些瓶颈。

### 关键术语

| 缩写 | 全称 | 含义 |
|------|------|------|
| TTFT | Time To First Token | 首 Token 延迟，Prefill 阶段耗时 |
| ITL | Inter-Token Latency | Token 间延迟，Decode 阶段每 Token 耗时 |
| PagedAttention | — | 分页注意力，vLLM 的 KV Cache 管理机制 |
| PTQ | Post-Training Quantization | 训练后量化 |
| GPTQ | GPT Quantization | 基于近似二阶信息的训练后量化方法 |
| AWQ | Activation-aware Weight Quantization | 激活感知权重量化 |
| Speculative Decoding | — | 投机解码，用小模型预测+大模型验证 |
| Continuous Batching | — | 连续批处理，请求级调度 |
| P/D 分离 | Prefill/Decode Disaggregated | Prefill 和 Decode 分离到不同 GPU |

## 1. 推理的两个阶段：Prefill 和 Decode

### 1.1 自回归解码流程

LLM 推理是自回归的——逐个 Token 生成，每步依赖前面所有 Token 的结果：

```
输入: "今天天气"
  Prefill: 并行处理 "今天天气" → KV Cache[0:4]
  Decode Step 1: 读 KV Cache[0:4] → 生成 "真" → KV Cache[0:5]
  Decode Step 2: 读 KV Cache[0:5] → 生成 "好" → KV Cache[0:6]
  Decode Step 3: 读 KV Cache[0:6] → 生成 "，" → KV Cache[0:7]
  ...
```

**Prefill 和 Decode 的计算特征截然不同**：

| 对比维度 | Prefill | Decode |
|----------|---------|--------|
| 输入形状 | [S, d_model] | [1, d_model] |
| GEMM 形状 | [S, d]×[d, d] | [1, d]×[d, d] |
| 算术强度 | ~S/2 (高) | ~1 (极低) |
| 瓶颈 | 计算密集 | 访存密集 |
| 优化方向 | 提高 Tensor Core 利用率 | 减少数据搬运量 |

### 1.2 用数值验证瓶颈差异

以 LLaMA-2 70B 的 FFN Gate 投影为例：

```
Prefill (S=4096):
  计算: 2 × 4096 × 8192 × 28672 = 1.93 TFLOPS
  访存: (4096×8192 + 8192×28672 + 4096×28672) × 2 = 1.75 GB
  AI = 1.93T / 1.75G = 1103 → 计算密集
  H100 FP16 峰值 989 TFLOPS → 计算时间 ~2 ms
  HBM 带宽 3.35 TB/s → 访存时间 ~0.5 ms
  → 计算时间 >> 访存时间 → 算力是瓶颈

Decode (S=1, batch=1):
  计算: 2 × 1 × 8192 × 28672 = 470 MFLOPS
  访存: ~470 MB (权重主导)
  AI = 470M / 470M = 1.0 → 访存密集
  H100 FP16 峰值 989 TFLOPS → 计算时间 ~0.5 μs
  HBM 带宽 3.35 TB/s → 访存时间 ~10.4 ms (TP=2 后 ~5.2 ms)
  → 访存时间 >> 计算时间 → 带宽是瓶颈
```

**Decode 阶段，GPU 99.99% 的时间在等数据**。这个事实决定了推理优化的核心思路：**减少数据搬运量，或让更多请求共享同一次数据搬运**。

## 2. KV Cache 管理：推理并发的硬限制

### 2.1 KV Cache 的显存占用

02 篇推导过 LLaMA-2 70B 每 Token 的 KV Cache：

```
每 Token KV Cache = 2 × n_kv_heads × d_head × n_layers × sizeof
                  = 2 × 8 × 128 × 80 × 2 = 320 KB/Token
```

不同上下文长度和并发数下的 KV Cache 总量：

| 场景 | 每请求 KV | 并发数 (TP=2, 剩余 40 GB) |
|------|----------|--------------------------|
| 4K 上下文 | 1.25 GB | 32 |
| 16K 上下文 | 5 GB | 8 |
| 64K 上下文 | 20 GB | 2 |
| 128K 上下文 | 40 GB | 1 |

**KV Cache 是推理并发的硬限制**——不是算力不够，而是显存装不下更多请求的 KV Cache。

### 2.2 PagedAttention：解决显存碎片

传统 KV Cache 管理为每个请求预分配最大长度的连续显存：

```
传统方式:
  请求 A: 预分配 128K × 320 KB = 40 GB (实际只用了 4K → 1.25 GB)
  请求 B: 预分配 128K × 320 KB = 40 GB
  → 80 GB 用完, 但实际只存了 2.5 GB 数据 → 97% 浪费!

  问题: 预分配最大长度 → 大量显存碎片
        请求长度不确定 → 无法精确预分配
```

PagedAttention 借鉴操作系统虚拟内存的分页机制：

```
PagedAttention:
  将 KV Cache 分成固定大小的 Block (如 16 Token/Block)
  用 Block Table 映射逻辑 Block → 物理 Block
  按需分配: 生成新 Token 时才分配新 Block

  请求 A: 实际 4K → 256 Blocks × 5 KB = 1.25 GB
  请求 B: 实际 8K → 512 Blocks × 5 KB = 2.5 GB
  请求 C: 实际 2K → 128 Blocks × 5 KB = 0.625 GB
  → 40 GB 可服务 ~20 个请求 (vs 传统 2 个)
```

**PagedAttention 的代价**：Block Table 的间接寻址增加了一次 GPU 内存读取。但这个开销远小于显存碎片节省的收益。

### 2.3 KV Cache 压缩

| 方法 | 原理 | 压缩比 | 精度影响 |
|------|------|--------|---------|
| GQA | 减少 KV 头数 | 4-8× | 小 |
| MLA | 压缩到低维潜在空间 | 16-32× | 小 |
| KV 量化 | INT8/INT4 量化 KV | 2-4× | 中 |
| Token 剪枝 | 丢弃不重要的 Token | 2-8× | 中-大 |
| 跨层共享 | 浅层和深层共享 KV | 2× | 中 |

**KV 量化的实际效果**：

```
KV Cache FP8 量化:
  每 Token: 320 KB → 160 KB (2× 压缩)
  128K 上下文: 40 GB → 20 GB
  并发数: 1 → 2

  精度: 在大多数基准上损失 <0.5%
  实现: vLLM 和 TensorRT-LLM 均已支持
```

## 3. 模型量化：减少权重搬运量

### 3.1 量化的动机

Decode 阶段的瓶颈是读取模型权重。量化直接减少权重体积：

```
70B 模型权重:
  BF16: 140 GB → TP=2 每卡 70 GB → 读取时间 70/3350 ≈ 20.9 ms
  INT8:  70 GB → TP=2 每卡 35 GB → 读取时间 35/3350 ≈ 10.4 ms (2× 加速)
  INT4:  35 GB → TP=2 每卡 17.5 GB → 读取时间 17.5/3350 ≈ 5.2 ms (4× 加速)
```

### 3.2 Weight-only 量化 vs Weight+Activation 量化

| 类型 | 量化对象 | 代表方法 | 加速来源 | 精度影响 |
|------|----------|----------|----------|---------|
| Weight-only | 仅权重 | GPTQ, AWQ, INT4 | 权重体积减半 → 读取时间减半 | 小 |
| W8A8 | 权重+激活 | TensorRT-LLM FP8 | 权重+激活都减半 + INT8 GEMM | 中 |
| W4A4 | 权重+激活 | 实验性 | 4× 权重压缩 + 4× 计算 | 大 |

**Weight-only 量化的原理**：权重是静态的，可以离线量化；激活值是动态的，运行时仍然是 FP16/BF16。GEMM 变为：`Y = X(BF16) × W_dequantized(BF16)`，反量化在 Kernel 内完成。

```
GPTQ 核心:
  基于近似二阶信息 (Hessian) 逐列量化权重
  每量化一列, 调整剩余列补偿量化误差
  → 最小化量化对输出的影响

AWQ 核心:
  观察到: 不是所有权重同等重要
  激活值大的通道对应的权重更重要
  → 对重要通道保持更高精度 (混合精度量化)
  → 比均匀量化精度更高
```

### 3.3 FP8 推理

FP8 推理与 FP8 训练不同——推理可以更激进地使用 FP8：

```
FP8 推理 (TensorRT-LLM):
  权重: 离线量化到 FP8 (E4M3)
  激活: 运行时动态量化到 FP8
  GEMM: FP8 × FP8 → FP32 累加 → FP8 输出

  优势:
    1. 权重体积减半 → Decode 读取时间减半
    2. FP8 GEMM 吞吐是 BF16 的 2× → Prefill 加速
    3. 硬件原生支持 (H100+)

  精度:
    大多数模型在 FP8 推理下精度损失 <0.1%
    少数敏感层 (如 Embedding, LM Head) 保持 BF16
```

### 3.4 量化精度对比

以 LLaMA-2 70B 在 MMLU 上的表现为例：

| 量化方法 | 模型大小 | MMLU 分数 | 相对损失 |
|----------|---------|-----------|---------|
| BF16 (基线) | 140 GB | 68.9 | — |
| GPTQ-INT8 | 70 GB | 68.5 | -0.4 |
| GPTQ-INT4 | 35 GB | 67.8 | -1.1 |
| AWQ-INT4 | 35 GB | 68.1 | -0.8 |
| FP8 (W8A8) | 70 GB | 68.7 | -0.2 |

**INT4 量化损失约 1%**，在大多数应用场景下可接受。FP8 几乎无损。

## 4. 投机解码：用时间换空间

### 4.1 核心思想

Decode 阶段 GPU 大部分时间在等数据。投机解码利用这些空闲算力：

```
标准 Decode:
  大模型生成 1 Token → 等待 ~5 ms → 大模型生成 1 Token → ...

投机解码:
  1. 小模型快速生成 K 个候选 Token (利用空闲算力)
  2. 大模型一次前向验证 K 个 Token
  3. 接受匹配的 Token, 拒绝不匹配的
  4. 从第一个被拒绝的位置重新生成

  最好情况: K 个 Token 全部正确 → 一次前向生成 K Token → K× 加速
  最坏情况: 第一个就错 → 浪费小模型计算 → 略微变慢
```

### 4.2 接受率分析

投机解码的加速比取决于小模型的接受率 α：

```
平均接受 Token 数:
  E[accepted] = α + α² + α³ + ... + α^K = α(1-α^K)/(1-α)

  α=0.8, K=5: E = 0.8(1-0.328)/0.2 = 2.69 → 2.69× 加速
  α=0.6, K=5: E = 0.6(1-0.078)/0.4 = 1.38 → 1.38× 加速
  α=0.4, K=5: E = 0.4(1-0.01)/0.6 = 0.66 → 变慢!

关键: α 必须 > 0.5 才有收益 → 小模型必须足够好
```

### 4.3 投机解码的变体

| 变体 | 草稿来源 | 优势 | 劣势 |
|------|----------|------|------|
| 小模型草稿 | 独立小模型 (如 7B→70B) | 简单直接 | 需要额外显存 |
| N-gram | 统计 N-gram 频率 | 零额外显存 | 接受率低 |
| Medusa | 多头并行预测 | 无需额外模型 | 训练复杂 |
| EAGLE | 基于特征的预测 | 高接受率 | 需要微调 |
| 自投机 | 模型自身跳层 | 无额外模型 | 仅适用于特定架构 |

## 5. 连续批处理：提升吞吐的关键

### 5.1 静态批处理的问题

```
静态批处理:
  Batch = [请求A(100 Token), 请求B(50 Token), 请求C(200 Token)]

  时间 →  A: [生成100个Token.......................]
          B: [生成50个Token..........] [空闲.......]
          C: [生成200个Token..............................]

  请求 B 在第 50 步完成, 但必须等最慢的请求 C 完成
  → GPU 利用率低, 延迟高
```

### 5.2 连续批处理（Continuous Batching）

连续批处理在请求完成后立即替换为新请求：

```
连续批处理:
  时间 →  A: [生成100个Token]
          B: [生成50个Token][新请求D...]
          C: [生成200个Token............]

  请求 B 完成后, 立即插入新请求 D
  → GPU 始终满载, 吞吐提升 2-4×
```

**实现要点**：

```
1. Iteration-level 调度:
   每次 Decode 步后检查哪些请求完成
   完成的请求释放 KV Cache, 新请求加入

2. 抢占 (Preemption):
   如果显存不够, 可以抢占低优先级请求
   被抢占的请求的 KV Cache 可以换出到 CPU 或丢弃

3. KV Cache 分配策略:
   vLLM: 预留固定比例的 KV Cache 给 Prefill
   其余给 Decode → 避免长 Prefill 饿死 Decode
```

### 5.3 Chunked Prefill

长上下文的 Prefill 计算量巨大，会阻塞正在进行的 Decode：

```
问题:
  一个 128K 上下文的 Prefill 需要数百 ms
  期间所有 Decode 请求都在等待 → ITL 飙升

Chunked Prefill:
  将长 Prefill 拆成多个 Chunk (如 4K Token/Chunk)
  每个 Chunk 与 Decode 请求一起组成混合 Batch
  → Prefill 和 Decode 交替执行, ITL 保持稳定

  时间 →  [Chunk1+Decode] [Chunk2+Decode] ... [ChunkN+Decode]
          ↑ Prefill 进度    ↑ Decode 不被阻塞
```

## 6. Prefill/Decode 分离：极致优化

### 6.1 为什么分离

Prefill 和 Decode 的资源需求完全不同：

| 阶段 | 瓶颈 | 需要的硬件 | 优化方向 |
|------|------|-----------|---------|
| Prefill | 计算 | 高算力 GPU (H100) | 提高 MFU |
| Decode | 带宽 | 高带宽 GPU 或更多卡 | 提高带宽利用率 |

**分离架构**：用专门的 GPU 做 Prefill，专门的 GPU 做 Decode：

```
传统架构 (同一组 GPU):
  GPU 0: [Prefill A] → [Decode A] → [Prefill B] → [Decode B] → ...
  → Prefill 和 Decode 争抢同一组资源

分离架构:
  Prefill 实例 (少量高算力 GPU):
    GPU P0: [Prefill A] → [Prefill B] → [Prefill C] → ...
    → 专注计算密集任务, 保持高 MFU

  Decode 实例 (更多高带宽 GPU):
    GPU D0: [Decode A+B+C] → [Decode A+B+C] → ...
    → 专注访存密集任务, 大 batch 提高带宽利用率

  KV Cache 通过高速互连从 Prefill 传输到 Decode
```

### 6.2 分离的收益

```
场景: LLaMA-2 70B, TP=2, 4K 上下文

传统架构 (2×H100):
  Prefill: ~50 ms (计算密集, GPU 利用率高)
  Decode: ~5 ms/Token (访存密集, batch=1 时 GPU 利用率 <1%)
  吞吐: ~0.2 Token/s (batch=1)

  增大 batch 到 32:
  Decode: ~5 ms/Token (带宽饱和)
  吞吐: ~6.4 Token/s
  但 TTFT 增加 (等 batch 填满)

分离架构 (2×H100 Prefill + 4×H100 Decode):
  Prefill 实例: 专注处理 Prefill, TTFT 不受 Decode 影响
  Decode 实例: batch=64+, 带宽利用率 >50%
  吞吐: ~25 Token/s (4× 提升)
  TTFT: 降低 ~30% (Prefill 不被 Decode 打断)
```

## 7. 推理性能建模

### 7.1 Decode 吞吐量模型

Decode 阶段的吞吐量受 HBM 带宽约束：

```
每 Token 需要读取的权重: P × sizeof(dtype) / TP
每 Token 需要读取的 KV Cache: 2 × n_kv_heads × d_head × n_layers × S × sizeof / TP

理论吞吐上限 = BW / (权重 + KV Cache)

70B BF16, TP=2, S=4K:
  权重: 70GB/2 = 35 GB
  KV: 1.25GB/2 = 0.625 GB
  总读取: 35.625 GB
  带宽: 3.35 TB/s × 2 = 6.7 TB/s (双卡)
  吞吐上限: 6700 / 35.625 ≈ 188 Token/s

70B INT4, TP=1, S=4K:
  权重: 35 GB
  KV: 1.25 GB
  总读取: 36.25 GB
  带宽: 3.35 TB/s
  吞吐上限: 3350 / 36.25 ≈ 92 Token/s
```

### 7.2 Prefill 延迟模型

Prefill 受算力约束：

```
Prefill 计算量 = 2 × P × S (前向传播, 无反向)
               = 2 × 70 × 10⁹ × 4096 = 573 GFLOPS

H100 FP16 峰值: 989 TFLOPS
理论延迟: 573G / 989T ≈ 0.58 ms (TP=1)

实际: ~50 ms (TP=2)
  MFU ~50% → 1.16 ms
  TP 通信: ~5%
  非 GEMM: ~10%
  实际 ~1.3 ms × 80 层 = ~104 ms → 与实际 ~50 ms 量级一致
  (TP=2 后每卡算一半, 通信开销约 5-10%)
```

## 8. 要点回顾

| 要点 | 说明 |
|------|------|
| Prefill vs Decode | Prefill 计算密集 (AI≈1103)，Decode 访存密集 (AI≈1) |
| Decode 瓶颈 | GPU 99.99% 时间在等数据，优化方向是减少搬运量 |
| KV Cache | 推理并发的硬限制，128K 上下文只能并发 1-2 请求 |
| PagedAttention | 分页管理 KV Cache，消除显存碎片，并发提升 10×+ |
| 量化 | INT4 权重体积减 4×，Decode 吞吐提升 ~4×，精度损失 ~1% |
| FP8 推理 | 几乎无损 (MMLU -0.2)，同时加速 Prefill 和 Decode |
| 投机解码 | 小模型预测+大模型验证，接受率 >0.8 时 2-3× 加速 |
| 连续批处理 | 请求完成后立即替换，吞吐提升 2-4× |
| P/D 分离 | Prefill 和 Decode 分配到不同 GPU，吞吐提升 4×+ |
| 性能模型 | Decode 吞吐 ≈ 带宽/每Token读取量，Prefill 延迟 ≈ 计算量/算力 |
