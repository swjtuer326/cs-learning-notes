# 第一部分：背景与动机

## 1. 中断是什么？为什么需要中断？

### 1.1 一个生活中的类比

想象你在办公室工作：

**没有中断的世界（轮询模式）：**
- 你需要每隔 5 秒去前台看看有没有你的快递
- 即使没有快递，你也要跑一趟
- 如果快递到了但你没去前台，你就不知道

**有中断的世界：**
- 前台收到你的快递后，主动打电话通知你
- 你可以专心工作，不用频繁跑前台
- 收到通知后你再去处理

**中断的本质：** 外部事件发生时，硬件主动通知 CPU，让 CPU 暂停当前工作去处理紧急事件。

### 1.2 计算机中的中断

```
时间线：
CPU: [执行任务 A] -----> [收到中断] -----> [处理中断] -----> [继续任务 A]
                         ↑
设备：[数据准备好了] ────┘
```

常见的中断来源：
- **键盘/鼠标** — 用户输入
- **网卡** — 收到网络数据包
- **磁盘** — 数据读写完成
- **定时器** — 时间片到期，操作系统进行任务切换
- **错误** — 内存错误、设备异常等

### 1.3 为什么需要中断控制器？

现代计算机有几十甚至上百个设备可能产生中断。如果每个设备都直接连到 CPU：

```
问题 1：CPU 的中断引脚数量有限
问题 2：多个设备同时中断怎么办？
问题 3：如何知道是哪个设备中断？
问题 4：哪些中断更重要，应该优先处理？
```

**中断控制器**就是为了解决这些问题而存在的。它就像一个"前台秘书"：

```
设备1 ──┐
设备2 ──┤
设备3 ──┼──> 中断控制器 ──> CPU
 ...   ─┤                    (一个引脚)
设备N ──┘
```

中断控制器的职责：
1. **汇聚** — 收集所有设备的中断请求
2. **仲裁** — 决定哪个中断优先处理
3. **路由** — 把中断发送给合适的 CPU 核心
4. **通知** — 告诉 CPU 是哪个设备产生了中断

---

> 要理解 AIA 的设计选择，我们需要先了解中断控制器的演进脉络。RISC-V 的设计并非凭空而来，而是借鉴了 x86 和 ARM 多十年的经验教训。下面我们快速回顾这段历史，重点理解每个阶段的**核心矛盾**——这些矛盾正是 AIA 要解决的。

## 2. 中断控制器的演进历史

### 2.1 早期：PIC (Programmable Interrupt Controller)

```
┌──────────────────────────────────────┐
│         Intel 8259 PIC               │
│                                      │
│  8 个中断输入 ──> 1 个中断输出       │
│  可级联：最多 15 个中断              │
│  固定优先级                          │
└──────────────────────────────────────┘
```

**特点：**
- 只能管理少量中断（最多 15 个）
- 优先级固定，不可配置
- 单核时代够用

### 2.2 多核时代：APIC (Advanced PIC)

```
┌──────────────────────────────────────┐
│              Local APIC              │
│         (每个 CPU 核心一个)          │
│                                      │
│  IO APIC ──> Local APIC ──> CPU0     │
│            ──> Local APIC ──> CPU1   │
│            ──> Local APIC ──> CPU2   │
└──────────────────────────────────────┘
```

**改进：**
- 支持多核 CPU
- 可以配置中断发送给哪个核心
- 支持更多中断源（最多 256 个）

### 2.3 PCI 时代：引脚中断 → MSI

PCI 设备最初使用**引脚中断**（INTx）：

```
PCI 设备 ──> INTA/INTB/INTC/INTD 引脚 ──> 中断控制器 ──> CPU
```

**问题：**
- 多个设备共享同一个中断引脚
- CPU 收到中断后，需要逐个询问设备："是你中断的吗？"
- 效率低下

**解决方案：MSI (Message-Signaled Interrupt)**

```
PCI 设备 ──> 内存写入 ──> 直接触发 CPU 中断
           (不需要共享引脚)
```

### 2.4 RISC-V 的路线：PLIC → AIA

```
时间线：

2015-2020          2022-2024          未来
  │                  │                 │
  ▼                  ▼                 ▼
PLIC ──────────> AIA ──────────> 更高级的中断架构
(基础)           (高级)
```

## 3. RISC-V PLIC 的五大痛点

PLIC (Platform-Level Interrupt Controller) 是 RISC-V 最初的中断控制器标准。随着系统越来越复杂，PLIC 的问题逐渐暴露。

### 痛点 1：不支持 MSI

```
PLIC 只能处理有线中断：

设备 ──> 物理中断线 ──> PLIC ──> CPU

对于 PCIe 等现代设备：
- 设备本身支持 MSI（通过内存写入触发中断）
- 但 PLIC 无法接收 MSI
- 需要额外的硬件将 MSI 转换为有线中断
- 增加了复杂性和延迟
```

**实际影响：** PCIe 网卡、NVMe 固态硬盘等现代设备都优先使用 MSI，PLIC 无法直接支持。

> **背景知识**：RISC-V 有三个主要特权级——M-mode（Machine mode，最高特权级，通常运行固件/安全监控器）和 S-mode（Supervisor mode，通常运行操作系统内核）。不同特权级的中断需要隔离管理。

### 痛点 2：M-mode 和 S-mode 共享寄存器

```
PLIC 的全局寄存器同时被 M-mode 和 S-mode 访问：

┌──────────────────────────────────────┐
│         PLIC 全局寄存器              │
│                                      │
│  M-mode 读写 ◄────┐                  │
│                   ├──── 冲突！       │
│  S-mode 读写 ◄────┘                  │
└──────────────────────────────────────┘
```

**问题：**
- 两个特权级可能同时修改配置
- 需要软件加锁保护
- 增加了开销和复杂性

### 痛点 3：占用大量物理地址空间

PLIC 的寄存器布局：

```
PLIC 地址空间：
├── 优先级寄存器：1024 个 × 4 字节 = 4KB
├── Pending 位图：1024 位 = 128 字节
├── 使能寄存器：每个 hart（RISC-V 中的硬件线程，可以理解为一个 CPU 核心）128 字节 × hart 数量
├── 阈值寄存器：每个 hart 4 字节
├── Claim/Complete：每个 hart 4 字节
└── 总地址空间：可能达到数 MB
```

**问题：** 在嵌入式系统中，地址空间是宝贵资源。

### 痛点 4：不支持中断线触发方式配置

```
PLIC 无法配置中断是边沿触发还是电平触发：

边沿触发：中断信号从低变高时触发一次
         ┌─
         │
      ───┘

电平触发：中断信号为高期间持续触发
      ┌──────────
      │
──────┘

不同设备需要不同的触发方式，PLIC 无法灵活配置。
```

### 痛点 5：虚拟化支持几乎为零

这是 PLIC 最大的问题。在虚拟化场景中：

```
┌───────────────────────────────────────┐
│           Hypervisor                  │
│                                       │
│  ┌─────────┐  ┌─────────┐             │
│  │  VM1    │  │  VM2    │             │
│  │ (Guest) │  │ (Guest) │             │
│  └────┬────┘  └────┬────┘             │
│       │            │                  │
│       └────┬───────┘                  │
│            ▼                          │
│         PLIC (共享)                   │
└───────────────────────────────────────┘

问题：
1. PLIC 不知道中断属于哪个 VM
2. 所有中断必须先交给 Hypervisor
3. Hypervisor 再决定转发给哪个 VM
4. 每次中断都需要 Hypervisor 介入
5. 中断延迟大幅增加
```

**实际影响：** 在虚拟化环境中，设备中断延迟可能增加数倍，严重影响性能。

## 4. AIA 如何解决这些问题

AIA (Advanced Interrupt Architecture) 针对 PLIC 的每个痛点都提供了解决方案：

| PLIC 痛点 | AIA 解决方案 |
|-----------|-------------|
| 不支持 MSI | 引入 IMSIC，原生支持 MSI |
| M/S-mode 共享寄存器 | 每个特权级有独立的 CSR 和中断文件 |
| 占用大量地址空间 | 使用 CSR 间接访问，减少 MMIO 空间 |
| 不支持触发方式配置 | APLIC 的 sourcecfg 可配置边沿/电平触发 |
| 虚拟化支持差 | Guest 中断文件 + IOMMU 中断重映射 |

> **初读提示**：上表中的一些术语（如 CSR、中断文件、Guest 中断文件）将在后续章节中详细介绍。这里只需建立初步印象：AIA 通过让每个特权级拥有独立的中断管理单元（中断文件），解决了 PLIC 中不同特权级共享寄存器的冲突问题。

**AIA 的核心设计理念：**

```
1. 分离关注点
   - APLIC 处理有线中断
   - IMSIC 处理 MSI
   - 各司其职，互不干扰

2. 硬件级虚拟化
   - 每个 VM 有独立的中断文件
   - VM 可以直接处理设备中断
   - 减少 Hypervisor 介入

3. 灵活的优先级
   - IMSIC：中断 ID 即优先级（ID 越小优先级越高），软件通过分配 ID 控制优先级
   - APLIC：每个中断源有独立的可配置优先级字段（IPRIOLEN 位宽，实现定义）
   - 支持中断抢占
   - 本地中断和外部中断可以混合排序
```

> **背景知识**：在 RISC-V 特权规范中，`mip`（Machine Interrupt Pending）和 `sip`（Supervisor Interrupt Pending）寄存器记录哪些中断正在等待处理，其中 `MEIP`/`SEIP` 位表示外部中断。`mie`/`sie` 是对应的中断使能寄存器，`MEIE`/`SEIE` 位控制是否允许外部中断。

> **重要：APLIC 与 PLIC 不兼容**
>
> AIA 规范明确指出 "The APLIC is not backwards compatible with the PLIC"。
> 在一个系统中，外部中断控制器**要么使用 PLIC，要么使用 APLIC**，两者不能同时作为外部中断控制器使用。
> 不过，IMSIC 的 eidelivery 寄存器支持一个特殊值 `0x40000000`，表示中断来自 PLIC/APLIC 而非 IMSIC 本身，
> 这为从 PLIC 到 AIA 的迁移提供了一定的过渡路径。
>
> 无论使用 PLIC 还是 AIA/IMSIC，外部中断都通过 `mip.MEIP`（M-mode）和 `sip.SEIP`（S-mode）位通知 hart，
> `mie.MEIE` 和 `sie.SEIE` 位继续作为外部中断的全局使能开关。

# 第二部分：核心概念详解

## 5. 有线中断 (Wired Interrupt)

### 5.1 什么是"有线"？

"有线"指的是**物理信号线**。设备通过一根真实的电线连接到中断控制器。

```
┌──────────┐         ┌──────────┐         ┌──────┐
│  UART    │──IRQ──> │          │         │      │
│  设备    │         │  APLIC   │──IRQ──> │ CPU  │
├──────────┤         │          │         │      │
│  GPIO    │──IRQ──> │          │         │      │
│  设备    │         │          │         │      │
└──────────┘         └──────────┘         └──────┘
     ↑                    ↑
   物理线               物理线
```

### 5.2 有线中断的两种触发方式

**电平触发 (Level-triggered)：**

```
中断线电平：
高电平 ────────────────────────> 持续产生中断请求
         ┌─────────────
         │
低电平 ──┘

特点：
- 只要电平为高，中断就一直 pending
- 设备处理完后，设备拉低电平，中断自动清除
- 如果软件忘记处理，中断会持续触发
- 更可靠，不容易丢失中断
```

**边沿触发 (Edge-triggered)：**

```
中断线电平：
         ┌─ 上升沿触发
         │
─────────┘

特点：
- 只在电平变化时触发一次
- 软件必须清除中断状态
- 如果软件没及时处理，后续变化不会被记录
- 响应更快，但可能丢失中断
```

### 5.3 有线中断的局限性

```
问题 1：每增加一个设备，就需要一根中断线
        100 个设备 = 100 根线 = 芯片引脚不够用

问题 2：中断线只能连接到一个中断控制器
        设备移动到其他核心？需要重新布线

问题 3：中断线数量受硬件限制
        芯片设计时就确定了，无法动态增加

问题 4：多核系统中，路由复杂
        哪个核心处理哪个设备的中断？
```

**这就是为什么需要 MSI...**

## 6. MSI (Message-Signaled Interrupt)

### 6.1 MSI 的核心思想

MSI 的本质：**把中断变成一次内存写入操作**。

```
传统有线中断：
设备 ──> 拉高中断线 ──> 中断控制器检测到电平变化 ──> 通知 CPU

MSI 中断：
设备 ──> 向特定地址写入特定数据 ──> 硬件识别为中断 ──> 通知 CPU
```

> **关键术语**：在 RISC-V AIA 架构中，接收 MSI 中断的硬件组件叫做 **IMSIC（Incoming MSI Controller，入站 MSI 控制器）**。你可以把它想象成每个 CPU 核心上的一个"中断收件箱"——设备通过 MSI 写入的地址，实际上就是写入到某个核心的 IMSIC 中。我们会在第 11 节详细讲解 IMSIC 的内部结构。

### 6.2 MSI 是如何工作的？

**配置阶段（系统启动时）：**

```
1. 操作系统为设备分配一个 MSI 地址和数据：
   
   MSI 地址：0x28000040  (指向某个 hart 的 IMSIC)
   MSI 数据：0x00000015  (中断 ID = 21)

2. 操作系统把地址和数据写入设备的配置寄存器：
   
   设备配置空间：
   ├── MSI Address Low  = 0x28000040
   ├── MSI Address High = 0x00000000
   └── MSI Data         = 0x00000015
```

**运行阶段（设备需要中断时）：**

```
3. 设备需要中断时，执行一次内存写入：
   
   *(uint32_t *)0x28000040 = 0x00000015;
   
4. 这个写入被硬件识别为中断请求
5. IMSIC 接收到中断 ID = 21
6. IMSIC 通知对应的 CPU hart
```

### 6.3 MSI 地址和数据：一次写入如何变成一次中断？

回顾 §6.2 中的例子，设备执行了这样一次写入：

```c
*(uint32_t *)0x28000040 = 0x00000015;
```

这行代码包含两个关键信息：**写到哪里**（地址）和**写了什么**（数据）。我们分别来看。

#### MSI 地址：写给谁？

> **中断文件（interrupt file）** 是 IMSIC 中的核心数据结构。你可以把它理解为一个"中断邮箱"——它保存了所有 pending（待处理）的中断 ID。每个 hart 可以有多个中断文件，分别对应不同的特权级别（M-mode、S-mode）和不同的虚拟机（Guest）。这样设计是为了隔离：M-mode 的中断不会泄露给 S-mode，不同虚拟机的中断也互不干扰。

MSI 地址本质上是一个"收件地址"，告诉硬件这个中断应该投递到哪个 CPU 核心的哪个中断文件。

> **为什么说是 64-bit 地址，但示例中只看到 32 位？**
>
> AIA 规范中 MSI 地址始终是 64 位的，由设备配置空间中的两个 32 位寄存器组成：
> ```
> MSI Address Low  = 0x28000040   ← 低 32 位
> MSI Address High = 0x00000000   ← 高 32 位
> ```
> 完整地址 = `0x00000000_28000040`。示例中高 32 位为 0，是因为 IMSIC 通常被映射在
> 4GB 以下的地址空间（嵌入式和开发系统常见情况），所以只写低 32 位就够了。
> 只有当 IMSIC 被映射到 4GB 以上时（大型服务器系统），高 32 位才需要非零值。

```
MSI 地址 (64-bit)：

  ┌────────┬────────┬────────┬───────────┐
  │ BAPPN  │  HHX   │  LHX   │ 页内偏移  │
  │(基地址) │(hart   │(hart   │(12位,    │
  │ 12位   │ 高半部) │ 低半部) │ 0-4095) │
  └────────┴────────┴────────┴───────────┘

  其中 hart index 和 guest index 编码在 PPN（物理页号）的几个 bit 中，
  具体位置由 APLIC 的 mmsiaddrcfg/smsiaddrcfg 寄存器中的
  LHXW/LHXS/HHXW/HHXS 字段灵活配置。

  直观理解：
  - 页内偏移（低 12 位）：选择 4KB 文件内的具体寄存器
  - LHX（若干 bit）：编码 hart index 的低半部分
  - HHX（若干 bit）：编码 hart index 的高半部分（用于 group index）
  - BAPPN（高 12 位）：基地址的高位部分

  → hart index 只占几个 bit，所以所有 hart 的地址都在同一个连续区域
  → 例如 QEMU 中 Hart 0 在 0x28000000，Hart 1 在 0x28008000（仅差 32KB）
```

**为什么地址必须是 4KB 对齐的？**

因为每个中断文件恰好占用一页（4KB）的内存空间。4KB 对齐意味着地址的低 12 位全为零，
硬件可以通过高位快速识别目标 hart 和中断文件，而低 12 位用于选择文件内的具体寄存器。

> **特权级别说明**：RISC-V 有多个特权级别，最重要的是 **M-mode（Machine Mode，机器模式）**——拥有最高权限，通常运行固件；以及 **S-mode（Supervisor Mode，监管者模式）**——通常运行操作系统内核。每个 hart 为不同特权级别维护独立的中断文件，实现特权隔离。

```
4KB 对齐的直观理解（以 QEMU virt 机器为例）：

  物理内存布局（由硬件/设备树定义，不同芯片可能不同）：

  IMSIC 区域起始地址 = 0x28000000

  ┌──────────┬──────────────────────────────────────┐
  │ 0x28000000 │ Hart 0, M-mode 中断文件    │  ← 4KB│
  │ 0x28001000 │ Hart 0, S-mode 中断文件    │  ← 4KB│
  │ 0x28002000 │ Hart 0, Guest 0 中断文件   │  ← 4KB│
  │ 0x28003000 │ Hart 0, Guest 1 中断文件   │  ← 4KB│
  │   ...     │ ...                                 │
  │ 0x28008000 │ Hart 1, M-mode 中断文件    │  ← 4KB│
  │ 0x28009000 │ Hart 1, S-mode 中断文件    │  ← 4KB│
  │   ...     │ ...                                 │
  └──────────┴──────────────────────────────────────┘

  关键理解：
  → 这些地址是芯片设计时确定的，不是软件随便选的
  → 操作系统通过设备树（Device Tree）得知每个文件的具体地址
  → 操作系统把正确的地址配置给设备（写入设备的 MSI 配置寄存器）
  → 设备发中断时，只需向该地址写入数据即可
```

> **实际编码细节**：hart index 和 guest index 的具体编码方式由 APLIC 的
> `mmsiaddrcfg`/`smsiaddrcfg` 寄存器中的 LHXW/LHXS/HHXW/HHXS 字段控制，
> 可以灵活配置。这里展示的是概念模型，帮助理解地址的语义。

#### MSI 数据：什么中断？

MSI 数据就是中断 ID（也叫 EIID，External Interrupt Identity）：

```
MSI 数据 (32-bit)：
┌────────────────────────────────────────────────────────────────┐
│                    中断 ID (Interrupt Identity / EIID)         │
│                                                                │
│  MSI 写数据 = 中断 ID 本身                                     │
│  有效范围：1 到 N（N 为该中断文件实现的最大 ID，最大 2047）    │
│  0 = 无效/伪中断                                               │
│  高于 N 的值被忽略                                             │
└────────────────────────────────────────────────────────────────┘
```

> **规范原文（AIA v1.0 §3.2）**：
> "The MSI write data is simply the identity number of the interrupt to be made pending
> in that interrupt file."
>
> 即 MSI 写数据直接就是中断 ID，没有额外的字段封装。

> **重要：IMSIC 的优先级是隐式的！**【规范 §3.3】
>
> "Within a single interrupt file, interrupt priorities are determined directly from
> interrupt identity numbers. Lower identity numbers have higher priority."
>
> 与 x86 APIC 不同，IMSIC 的 MSI 数据中没有独立的优先级字段。
> **中断 ID 越小，优先级越高**（ID=1 优先级最高）。
> 软件在分配中断 ID 时需要考虑这一隐式优先级关系。
> 例如：定时器 = ID 1（最高），网卡 = ID 10，键盘 = ID 50。
>
> **注意**：这是 IMSIC 的行为。APLIC 在直接投递模式下有独立的可配置优先级字段，
> 两者的优先级机制不同，详见附录 A。

#### 完整流程回顾

把地址和数据合在一起，MSI 的工作流程就非常清晰了：

```
设备需要中断时：
  1. 向 MSI 地址写入 MSI 数据
     地址 = "投递到 Hart 0 的 S-mode 中断文件"
     数据 = "中断 ID = 21"

  2. 硬件根据地址找到目标 IMSIC 的中断文件
  3. 中断文件将 ID=21 标记为 pending
  4. 中断文件进行优先级仲裁（ID 越小优先级越高）
  5. 如果该中断优先级最高且使能，通知对应的 hart
  6. hart 收到外部中断，进入中断处理程序
```

## 7. 为什么 MSI 比有线中断更好？

### 7.1 对比表格

| 特性 | 有线中断 | MSI |
|------|---------|-----|
| 物理资源 | 需要中断线 | 不需要，使用内存写入 |
| 共享 | 多个设备可能共享中断线 | 每个设备有独立的中断向量 |
| 扩展性 | 受引脚数量限制 | 理论上无限（受地址空间限制） |
| 路由灵活性 | 硬件布线决定 | 软件配置地址即可改变路由 |
| 虚拟化 | 难以虚拟化 | 天然支持虚拟化 |
| 性能 | 需要逐个查询设备 | 直接知道是哪个中断 |
| 延迟 | 较高（共享时需要轮询） | 较低（直接定位） |

### 7.2 具体场景分析

**场景 1：高性能网卡**

```
有线中断方式：
网卡收到数据包 ──> 共享中断线 ──> CPU 收到中断
CPU 需要查询：是网卡中断吗？是其他设备吗？
→ 每次中断都要轮询，浪费 CPU 时间

MSI 方式：
网卡收到数据包 ──> 写入 MSI 地址 ──> CPU 直接知道是网卡中断
→ 无需轮询，直接处理
```

**场景 2：多队列 NVMe SSD**

```
现代 NVMe SSD 有多个 I/O 队列（通常 8-64 个）

有线中断：
- 所有队列共享一个中断
- CPU 收到中断后，需要检查所有队列
- 无法并行处理

MSI：
- 每个队列有独立的中断向量
- 可以分配到不同的 CPU 核心
- 多个核心并行处理不同队列
- 性能提升数倍
```

**场景 3：多核系统中的中断负载均衡**

```
有线中断：
设备的中断线连到固定的中断控制器
→ 中断总是发送给固定的 CPU 核心
→ 某个核心可能过载，其他核心空闲

MSI：
操作系统可以动态修改 MSI 地址
→ 把中断路由到不同的 CPU 核心
→ 实现负载均衡
```

> MSI 的优势不仅体现在基本性能上，它在**虚拟化场景**中更是不可或缺的基础。现代云计算广泛使用虚拟化技术，而中断是虚拟化中最难高效处理的子系统之一。接下来我们看看虚拟化给中断带来了什么挑战，以及 MSI 如何成为解决这些挑战的关键。

## 8. 虚拟化与中断的困境

### 8.1 虚拟化的基本概念

```
┌───────────────────────────────────────────────┐
│                  物理机器                     │
│                                               │
│  ┌─────────────────────────────────────┐      │
│  │          Hypervisor (VMM)           │      │
│  │                                     │      │
│  │  ┌──────────┐  ┌──────────┐        │       │
│  │  │   VM1    │  │   VM2    │        │       │
│  │  │ ┌──────┐ │  │ ┌──────┐ │        │       │
│  │  │ │vCPU1 │ │  │ │vCPU1 │ │        │       │
│  │  │ │vCPU2 │ │  │ │vCPU2 │ │        │       │
│  │  │ └──────┘ │  │ └──────┘ │        │       │
│  │  └──────────┘  └──────────┘        │       │
│  └─────────────────────────────────────┘      │
│                                               │
│  物理 CPU 核心 0    物理 CPU 核心 1           │
└───────────────────────────────────────────────┘

关键概念：
- vCPU (虚拟 CPU)：VM 看到的"CPU"，实际是物理 CPU 的时间片
- Hypervisor：管理多个 VM 的软件（如 KVM、Xen）
- Guest OS：VM 中运行的操作系统
- Host OS：物理机器上运行的操作系统
```

### 8.2 虚拟化中的地址转换问题

> 你可能会问：讨论虚拟化中的中断，为什么要先讲地址转换？因为 **MSI 的本质是一次内存写入**（还记得吗？），而虚拟化环境中的内存地址是"套娃"式的——Guest OS 看到的地址不是真实的物理地址。如果设备使用 MSI 写入了一个 Guest OS 认为的"物理地址"，但实际上这个地址是虚拟的，就会产生严重问题。理解了地址转换，才能理解后面的中断重映射。

```
三种地址：

1. GVA (Guest Virtual Address)
   - Guest OS 进程使用的虚拟地址
   - Guest OS 的页表转换为 GPA

2. GPA (Guest Physical Address)
   - Guest OS 看到的"物理地址"
   - 实际是虚拟的，需要 Hypervisor 转换为 HPA

3. HPA (Host Physical Address)
   - 真实的物理内存地址
   - 只有 Hypervisor 知道

转换过程：
GVA ──(Guest 页表)──> GPA ──(Hypervisor 页表)──> HPA
```

### 8.3 设备直通 (Device Passthrough)

> **IOMMU（Input-Output Memory Management Unit，I/O 内存管理单元）** 是一种硬件机制，用于控制设备对内存的访问。在设备直通场景中，IOMMU 确保直通设备只能访问分配给对应 VM 的内存。我们将在下一节详细介绍 IOMMU。

**为什么需要设备直通？**

```
传统虚拟化（设备模拟）：

VM ──> 虚拟设备 ──> Hypervisor ──> 物理设备 ──> 实际硬件
     (软件模拟)      (软件模拟)

问题：
- 每次 I/O 都需要 Hypervisor 介入
- 性能损失 30%-50%
- 对于高性能设备（网卡、GPU）不可接受

设备直通：

VM ──> 物理设备 (直接访问)
     (通过 IOMMU 保护)

优势：
- 性能接近原生（损失 < 5%）
- VM 直接使用物理设备驱动
- 适合高性能场景
```

### 8.4 直通设备的中断问题

```
问题场景：

物理设备支持 MSI，它要发送中断：

设备配置（在 VM 中设置）：
  MSI 地址 = 0x28000040  (这是 GPA！)
  MSI 数据 = 0x00000015

设备发送中断：
  设备写入地址 0x28000040

问题：
1. 这个地址是 GPA，不是真实的物理地址
2. 如果直接写入，会写到错误的内存位置
3. 可能破坏其他 VM 或 Host 的数据！
4. 即使地址正确，中断应该投递到哪个 VM？

这就是 IOMMU 中断重映射要解决的问题...
```

---

## 9. IOMMU：连接设备与虚拟化的桥梁

### 9.1 IOMMU 是什么？

```
MMU (Memory Management Unit)：
  CPU 虚拟地址 ──> 物理地址
  保护：进程 A 不能访问进程 B 的内存

IOMMU (I/O Memory Management Unit)：
  设备 DMA 地址 ──> 物理地址
  保护：设备 A 不能访问设备 B 的内存
       设备不能访问未授权的内存区域
```

### 9.2 IOMMU 的两大功能

**功能 1：DMA 重映射 (DMA Remapping)**

```
没有 IOMMU：
设备 DMA ──> 直接访问物理内存
问题：设备可以访问任何内存，不安全

有 IOMMU：
设备 DMA ──> IOMMU 页表转换 ──> 物理内存
优势：
- 设备只能访问授权的内存区域
- 可以把不连续的物理内存映射为连续的 DMA 空间
- 每个设备有独立的地址空间
```

**功能 2：中断重映射 (Interrupt Remapping)**

```
这就是解决 8.4 中问题的关键！

设备发送 MSI：
  设备写入 GPA 地址

IOMMU 拦截：
  1. 识别这是 MSI 写入
  2. 查中断重映射表
  3. 转换为正确的 HPA（目标 IMSIC 地址）
  4. 可能修改 MSI 数据（中断 ID）
  5. 转发到正确的目标

结果：
  - VM 配置的是 GPA，没问题
  - IOMMU 自动转换为 HPA
  - 中断正确投递到目标 hart 的 IMSIC
  - 不同 VM 的中断完全隔离
```

### 9.3 IOMMU 中断重映射详解

```

### 9.4 IOMMU 与 AIA 的关系

```
IOMMU 和 AIA 是互补的关系：

AIA 提供：
- IMSIC：接收 MSI 的硬件
- APLIC：管理有线中断并转换为 MSI
- Guest 中断文件：支持虚拟化

IOMMU 提供：
- DMA 重映射：保护内存访问
- 中断重映射：转换 MSI 地址，支持设备直通

两者结合：
- VM 可以直接控制物理设备
- 设备中断直接投递到 VM 的 guest 中断文件
- 无需 Hypervisor 介入每次中断
- 性能接近原生
```

### 10.2 数据流详解

**场景 1：有线中断处理流程**

```
1. UART 设备收到数据，拉高中断线
2. APLIC 检测到中断
3. APLIC 查配置：
   - 这个中断源的模式是什么？（边沿/电平）
   - 是否使能？
   - 投递模式是什么？（Direct/MSI）
   - 目标 hart 是哪个？
4. 如果是 Direct 模式：
   APLIC 直接驱动 hart 的外部中断引脚
5. hart 收到外部中断，进入中断处理程序
6. 中断处理程序读取 APLIC 获取中断详情
7. 处理完成后，清除 APLIC 中的 pending 状态
```

**场景 2：MSI 中断处理流程**

```
1. PCIe 网卡收到数据包
2. 网卡执行 MSI 写入：
   *(uint32_t *)0x28000040 = 0x00000015;
3. 写入到达 IMSIC（可能经过 IOMMU 转换）
4. IMSIC 的中断文件记录中断 ID 15 为 pending
5. IMSIC 进行优先级仲裁
6. 如果该中断优先级最高且使能：
   IMSIC 通知 hart 有外部中断
7. hart 进入中断处理程序
8. 读取 topei 获取中断 ID
9. 处理完成后，写入 topei 清除中断
```

**场景 3：APLIC 转换有线中断为 MSI**

```
1. GPIO 设备产生中断
2. APLIC 接收中断
3. APLIC 配置为 MSI 投递模式
4. APLIC 向目标 hart 的 IMSIC 写入 MSI：
   *(uint32_t *)target_imsic_address = interrupt_id;
5. 后续流程同场景 2
```

---

> 在整体架构中，IMSIC 是 AIA 接收 MSI 的核心组件，也是 AIA 最具创新性的部分。每个 CPU hart 都有自己的 IMSIC，IMSIC 内部通过"中断文件"来管理不同特权级和虚拟机的中断状态。理解中断文件是理解整个 AIA 的关键，所以我们先从 IMSIC 讲起。

## 11. IMSIC 详解【规范 §3】

> 本章内容对应 AIA 规范第 3 章（Incoming MSI Controller）。IMSIC 是 AIA 的核心组件，负责接收 MSI 并管理中断文件。

### 11.1 中断文件 (Interrupt File) 是什么？

中断文件是 IMSIC 的核心概念。它不是真正的文件，而是一组**寄存器集合**，用于管理一个特权级或一个虚拟机的中断状态。

```
想象中断文件是一个"中断邮箱"：

┌─────────────────────────────────────┐
│         Interrupt File              │
│                                     │
│  收件箱 (pending 寄存器)             │
│  ├── 中断 1: 有邮件 ☑               │
│  ├── 中断 2: 无邮件 ☐               │
│  ├── 中断 3: 有邮件 ☑               │
│  └── ...                            │
│                                     │
│  过滤器 (eie 使能寄存器)             │
│  ├── 中断 1: 接收 ☑                 │
│  ├── 中断 2: 拒收 ☐                 │
│  └── 中断 3: 接收 ☑                 │
│                                     │
│  优先级标签 (eithreshold)            │
│  ── 只处理优先级 >= 5 的邮件         │
│                                     │
│  最紧急邮件 (topei)                  │
│  ── 中断 3 (优先级 8)                │
│                                     │
│  投递开关 (eidelivery)               │
│  ── 开启：把邮件通知给 CPU           │
│  ── 关闭：暂存邮件，不通知           │
└─────────────────────────────────────┘
```

每个中断文件可以容纳的中断数量是**实现定义的**（由芯片厂商决定），但必须满足以下约束【规范 §3.1】：

```
  最小：63 个中断 ID（ID 1-63）
  最大：2047 个中断 ID（ID 1-2047）
  约束：数量必须是 "64 的倍数减 1"（即 63, 127, 191, ..., 2047）

  例如：
  - 某嵌入式芯片可能只实现 63 个（最小配置）
  - 某服务器芯片可能实现 2047 个（最大配置）
  - 具体数量软件通过设备树或 CSR 查询得知
```

> **规范原文**：
> "The number of interrupt identities supported by an interrupt file (and hence the number
> of active bits in each array) is one less than a multiple of 64, and may be a minimum of 63
> and a maximum of 2047."
>
> "The number zero is never a valid interrupt identity."

### 11.2 中断文件的寄存器详解

> 下面我们将逐一介绍中断文件中的关键寄存器。从功能上看，这些寄存器可以分为四类：(1) 投递控制（eidelivery、eithreshold）——决定中断是否以及何时通知 CPU；(2) 中断使能（eie）——软件开关，控制哪些中断源被接受；(3) 中断状态（eip）——硬件维护的 pending 状态；(4) 中断查询（topei/topi）——CPU 获取当前最高优先级中断的接口。一个典型的中断处理流程会依次用到以上所有寄存器。

#### eidelivery（External Interrupt Delivery Enable）— 投递使能

```
作用：控制中断是否可以通知到 CPU

值：
  0 = 关闭投递（中断仍然记录，但不通知 CPU）
  1 = 开启投递（中断通知 CPU）

使用场景：
- 初始化时设置为 1，使能中断
- 处理中断时临时设置为 0，防止嵌套中断
- 休眠时设置为 0，唤醒后恢复
```

#### eithreshold（External Interrupt Threshold）— 中断阈值

作用：设置最低优先级阈值，低于此优先级的中断不投递。
等价说法：设置最大中断 ID 阈值，ID 大于此值的中断不投递。

> **重要设计**：在 IMSIC 中，中断的优先级就等于其中断 ID（ID 越小优先级越高）。因此，"设置最低优先级阈值"和"设置最大中断 ID 阈值"是完全等价的两种说法。

> **规范原文**【§3.8.2】：
> "eithreshold is a WLRL register that determines the minimum interrupt
> priority (maximum interrupt identity number) allowing an interrupt to be signaled."

```
  0 = 所有使能的中断都投递
  N (非零) = 只投递 ID < N 的中断（ID >= N 的中断被屏蔽，无论是否使能）
```

**使用场景**：
- 关键代码段：提高阈值，屏蔽低优先级中断
- 正常执行：设置为 0，接收所有中断
- 类似 x86 的中断优先级掩码

#### eie[0..63]（External Interrupt Enable）— 中断使能寄存器

作用：每个位控制一个中断是否使能。

**结构**【规范 §3.8.4】：

```
  eie[0]: 位 0 对应 ID 0（无效，只读为 0），位 1-63 对应 ID 1-63
  eie[1]: 位 0-63 对应 ID 64-127
  ...
  eie[31]: 位 0-63 对应 ID 1984-2047（RV64 下 eie[32]-eie[63] 不存在）
```

> **注意**：ID 0 永远不是有效中断，所以 eie[0] 的 bit 0 是只读零。

**使用示例**：

- 使能中断 ID 21：设置 eie[0] 的位 21 为 1
- 禁用中断 ID 100：设置 eie[1] 的位 36（100-64）为 0

#### eip[0..63]（External Interrupt Pending）— 中断 pending 寄存器

作用：记录哪些中断 ID 已到达但未处理。

**结构**【规范 §3.8.3】：

```
  eip[0]: 位 0 对应 ID 0（无效，只读为 0），位 1-63 对应 ID 1-63
  eip[1]: 位 0-63 对应 ID 64-127
  ...
  eip[31]: 位 0-63 对应 ID 1984-2047（RV64 下 eip[32]-eip[63] 不存在）
```

> **注意**：ID 0 永远不是有效中断，所以 eip[0] 的 bit 0 是只读零。
> 当 MSI 写数据为 0 时，不会设置任何 pending 位（0 是无效 ID）。

#### topi / topei（Top Of Priority External Interrupt）— 如何获取当前最高优先级的中断？

**背景问题**：当 CPU 收到外部中断（`mip.MEIP` 或 `sip.SEIP` 被置位）进入中断处理程序后，
它需要知道**具体是哪个中断**。在 PLIC 时代，CPU 需要先读取 claim 寄存器获取中断 ID，
处理完后再写入 complete 寄存器完成该中断——这是两步操作。

AIA 将这两步合并为一步：**读取 topei CSR 就同时完成了 claim**。

---

**topei（IMSIC 模式下使用）**【规范 §3.9】：

这是最常用的方式。当 IMSIC 收到中断后，CPU 通过 topei 一步完成"查询 + claim"：

```
中断处理程序中的典型用法：

  // 1. CPU 因外部中断进入 trap
  // 2. 读取 topei，同时获取中断 ID 并自动 claim
  csrr t0, stopei        // t0 = 最高优先级的 pending+enabled 中断 ID
                          // 同时该中断的 pending 位被自动清除

  // 3. 根据 t0 中的 ID 分发处理
  li t1, 10
  beq t0, t1, handle_nic
  li t1, 21
  beq t0, t1, handle_timer
  ...

  // 4. 处理完毕，不需要额外的 complete 操作
  //    （读取 topei 时已经自动完成了）
```

> **为什么不需要单独的 complete？**
> 读取 topei 时，硬件自动完成了 claim（清除 pending 位）。
> 这与 x86 需要单独写 EOI（End Of Interrupt）寄存器的模式不同。

topei 读返回值的位布局【规范 §3.9】：

```
┌─────────────────────────────────────────────────────────────┐
│  bits 26:16    │  bits 10:0    │  其他位 = 0                 │
│  中断 ID        │  中断优先级     │                            │
│  (11-bit)       │  (11-bit)      │                            │
└─────────────────────────────────────────────────────────────┘
```

> 在 IMSIC 中，优先级 = 中断 ID（两者相同），这是隐式优先级的设计。
> 规范原文："bits 10:0 Interrupt priority (same as identity)"

---

**topi（APLIC 直接投递模式下使用）**【规范 §4.8.1.4】：

当 APLIC 工作在直接投递模式（domaincfg.DM=0）时，CPU 通过 APLIC 的 MMIO 寄存器
查询当前最高优先级的中断。与 topei 不同，topi **不会自动 claim**：

```
topi 读返回值的位布局：
┌─────────────────────────────────────────────────────────────┐
│  bits 25:16    │  bits 7:0     │  其他位 = 0                 │
│  中断 ID        │  中断优先级     │                            │
│  (10-bit)       │  (8-bit)       │                            │
└─────────────────────────────────────────────────────────────┘
```

> 在 APLIC 中，优先级是独立可配置的字段（与中断 ID 无关）。
> 规范原文："The two components being independent of one another."

---

**topei vs topi 对比**：

| 特性 | topei（IMSIC） | topi（APLIC 直接投递） |
|------|---------------|----------------------|
| **访问方式** | CSR 指令（`csrr t0, stopei`） | MMIO 内存读取 |
| **读取效果** | 返回中断 ID，**同时自动 claim** | 只返回信息，**不改变状态** |
| **写入效果** | 写入时 claim（忽略写入值） | 不支持写入 |
| **原子性** | 是（一条指令完成读+claim） | 否（需要额外的 claim 步骤） |
| **优先级来源** | 中断 ID（隐式） | 独立配置字段（显式） |
| **使用场景** | **最常用**：MSI 模式下的中断处理 | 调试/查询：查看当前最高优先级中断 |

> **命名含义**：TOPEI = **T**op **O**f **P**riority **E**xternal **I**nterrupt，
> 其中 EI = External Interrupt（外部中断），而非 "End Of Interrupt"。

> **实际开发中**：绝大多数情况下你只需要使用 topei（通过 `stopei`/`mtopei` CSR）。
> topi 主要用于调试场景，或者 APLIC 工作在直接投递模式时。

### 11.3 中断文件的间接访问机制

为什么需要间接访问？

```
问题：
仅 eie 和 eip 就各有 64 个寄存器（每个 64 位），加上 eidelivery、eithreshold 等，
一个中断文件就需要 130+ 个 CSR。而 RISC-V 规范为自定义 CSR 分配的地址空间有限，
不可能为每个寄存器分配独立的 CSR 编号。

解决方案：间接访问
使用两个 CSR 配合：
  xiselect（x = m/s/h）：选择要访问的内部寄存器（写入间接地址）
  xireg（x = m/s/h）：读写选中的寄存器（读取或写入数据）

类似"先拨分机号，再通话"：
  1. csrw siselect, 0x70    ← 选择 eidelivery
  2. csrr t0, sireg          ← 读取 eidelivery 的值
```

> **CSR 命名规则速记**：
> RISC-V AIA 的 CSR 名称遵循一致的命名规则，理解前缀后可以举一反三：
>
> | 前缀 | 含义 | 示例 |
> |------|------|------|
> | `m` | Machine 级别 | `miselect`、`mireg`、`mtopei` |
> | `s` | Supervisor 级别 | `siselect`、`sireg`、`stopei` |
> | `h` | Hypervisor 级别 | `hiselect`、`hireg`、`htopei` |
> | `vs` | Virtual Supervisor（VS-mode） | `vsiselect`、`vsireg`、`vstopei` |
>
> | 后缀 | 含义 | 示例 |
> |------|------|------|
> | `iselect` | **I**ndirect **Select**，间接选择寄存器 | `siselect` = Supervisor Indirect Select |
> | `ireg` | **I**ndirect **Reg**ister，间接数据寄存器 | `sireg` = Supervisor Indirect Register |
> | `topei` | **Top Of Priority External Interrupt**（可 claim） | `stopei` = Supervisor TOPEI |
> | `topi` | **Top Of Priority External Interrupt**（只读） | `stopi` = Supervisor TOPI（不自动 claim） |
> | `geie` | **G**uest **E**xternal **I**nterrupt **E**nable | `hgeie` = Hypervisor GEIE |
> | `geip` | **G**uest **E**xternal **I**nterrupt **P**ending | `hgeip` = Hypervisor GEIP |
> | `victl` | **V**irtual **I**nterrupt **C**ontr**ol** | `hvictl` = Hypervisor VICTL |
> | `vien` | **V**irtual **I**nterrupt **En**able | `hvien` = Hypervisor VIEN |
> | `viprio` | **V**irtual **I**nterrupt **Prio**rity | `hviprio1` = Hypervisor VIPRIO1 |
>
> 间接访问的内部寄存器命名规则：
> - `eidelivery` = **E**xternal **I**nterrupt **Delivery** Enable
> - `eithreshold` = **E**xternal **I**nterrupt **Threshold**
> - `eie` = **E**xternal **I**nterrupt **E**nable
> - `eip` = **E**xternal **I**nterrupt **P**ending
>
> 所有以 `e` 开头的寄存器（eidelivery、eithreshold、eie、eip）都属于 interrupt file 内部寄存器，通过 `*iselect`/`*ireg` 间接访问。而 `topei`/`topi` 是独立 CSR，直接访问。

常用间接寄存器地址：

```
0x70 — eidelivery     投递使能
0x71 — （保留）        读取返回 0，写入忽略
0x72 — eithreshold    中断阈值
0x73-0x7F — （保留）
0x80-0xBF — eip0-eip63  中断 pending 寄存器数组
0xC0-0xFF — eie0-eie63  中断使能寄存器数组
```

> **注意**：`topi` 和 `topei` 不是通过间接地址访问的寄存器，而是独立的直接访问 CSR（如 `stopei`、`mtopei`），详见第 17 节。

## 12. APLIC 详解【规范 §4】

> 本章内容对应 AIA 规范第 4 章（Advanced Platform-Level Interrupt Controller）。APLIC 是 AIA 中管理有线中断和 MSI 转发的组件，功能上可以看作 PLIC 的升级替代品。

### 12.1 APLIC 的角色

```
APLIC 是"有线中断的总管"：

┌───────────────────────────────────────────────────────────────┐
│                     APLIC                                     │
│                                                               │
│  输入：最多 1023 个有线中断源                                 │
│                                                               │
│  处理：                                                       │
│  ├── 检测中断（边沿/电平）                                    │
│  ├── 记录 pending 状态                                        │
│  ├── 优先级仲裁                                               │
│  ├── 查路由表                                                 │
│  └── 投递到目标 hart                                          │
│                                                               │
│  输出：                                                       │
│  ├── Direct 模式：驱动 hart 的外部中断引脚                    │
│  └── MSI 模式：向 IMSIC 写入 MSI                              │
└───────────────────────────────────────────────────────────────┘
```

### 12.2 中断域 (Domain) 概念【规范 §4.3】

```
中断域是 APLIC 中的逻辑分组：

┌───────────────────────────────────────────────────────┐
│              Root Domain (根域)                       │
│              特权级：M-mode 或 S-mode                 │
│                                                       │
│  管理中断源 1-512                                     │
│  投递到 Hart 0-3                                      │
│                                                       │
│  ┌────────────────────┐  ┌────────────────────┐       │
│  │  Child Domain 1    │  │  Child Domain 2    │       │
│  │  委托的中断源      │  │  委托的中断源      │       │
│  │  513-768           │  │  769-1023          │       │
│  │  投递到 Hart 4-7   │  │  投递到 Hart 8-11  │       │
│  └────────────────────┘  └────────────────────┘       │
│                                                       │
└───────────────────────────────────────────────────────┘

为什么需要域？
1. 权限隔离：不同域可以有不同的访问权限
2. 虚拟化：每个 VM 可以有自己的域
3. 灵活路由：不同域可以路由到不同的 hart
```

### 12.3 中断源配置 (sourcecfg)【规范 §4.4】

每个中断源有一个 32 位配置寄存器：

```
sourcecfg[x] 结构：

┌────────┬───────────┬────────┬────────┬─────────────────────┐
│   D    │    CI     │   SM   │  保留   │    其他配置        │
│ (委托) │ (子域索引) │(源模式) │         │                  │
│ 1-bit  │  10-bit   │ 3-bit  │         │                    │
└────────┴───────────┴────────┴────────┴─────────────────────┘

D (Delegation) 位：
  0 = 不委托，SM 字段有效，中断由当前域处理
  1 = 委托给子域，CI 字段指定子域索引

SM (Source Mode) 字段：
  0 = Inactive    中断屏蔽，不活跃
  1 = Detached    仅软件触发（写入 setip）
  4 = Edge1       上升沿触发
  5 = Edge0       下降沿触发
  6 = Level1      高电平触发
  7 = Level0      低电平触发
```

### 12.4 投递模式详解【规范 §4.5】

#### Direct Delivery 模式

```
适用场景：
- 简单系统，没有 IMSIC
- 不需要 MSI 支持
- 中断数量较少

流程：
APLIC ──> hart 外部中断引脚 ──> CPU 中断处理

特点：
- 类似传统 PLIC
- 实现简单
- 不支持虚拟化
```

#### MSI Delivery 模式

```
适用场景：
- 有 IMSIC 的系统
- 需要 MSI 支持
- 需要虚拟化

流程：
APLIC ──> MSI 写入 ──> IMSIC ──> 中断文件 ──> CPU 中断处理

特点：
- 性能更好
- 支持虚拟化
- 可以路由到任意 hart 的任意中断文件
```

### 12.5 APLIC 寄存器布局详解【规范 §4.6】

> 本节列出的寄存器布局基于 AIA 规范第 4 章中定义的 APLIC MMIO 寄存器空间。实际实现中保留区域的偏移量可能与规范建议值不同，具体以芯片厂商的手册为准。

```c
struct Aplic {
    // ===== 域配置 =====
    u32 domaincfg;              // 域配置：使能、投递模式、字节序
    u32 sourcecfg[1023];        // 1023 个中断源的配置

    u8 _reserved1[0xBC0];       // 保留区域

    // ===== MSI 地址配置 =====
    u32 mmsiaddrcfg;            // M-mode MSI 地址 (低32位)
    u32 mmsiaddrcfgh;           // M-mode MSI 地址 (高32位)
    u32 smsiaddrcfg;            // S-mode MSI 地址 (低32位)
    u32 smsiaddrcfgh;           // S-mode MSI 地址 (高32位)

    u8 _reserved2[0x30];

    // ===== Pending 操作 =====
    u32 setip[32];              // 批量设置 pending (位数组，32×32=1024 位)
    u8 _reserved3[92];
    u32 setipnum;               // 按编号设置 pending (写入中断号即可)

    u8 _reserved4[0x20];
    u32 in_clrip[32];           // 批量清除 pending
    u8 _reserved5[92];
    u32 clripnum;               // 按编号清除 pending

    // ===== 使能操作 =====
    u32 setie[32];              // 批量使能中断
    u8 _reserved7[92];
    u32 setienum;               // 按编号使能

    u32 clrie[32];              // 批量禁用中断
    u8 _reserved9[92];
    u32 clrienum;               // 按编号禁用

    // ===== 特殊操作 =====
    u32 setipnum_le;            // 设置 pending (小端序)
    u32 setipnum_be;            // 设置 pending (大端序)

    u8 _reserved11[4088];

    // ===== 目标配置 =====
    u32 genmsi;                 // 生成 MSI 的目标 hart 和中断文件
    u32 target[1023];           // 每个中断源的目标 hart 配置
};
```

## 13. 中断流转完整示例

> 前面各章节分别介绍了 AIA 的各个组件，但还没有将它们串联起来。本节通过两个完整的端到端示例，展示中断从产生到被 CPU 处理的全过程。建议读者先理解 §10（整体架构）和 §11-§12（IMSIC/APLIC 详解），再阅读本节。

### 13.1 场景：PCIe 网卡中断

> **阅读本节前你需要了解：**
> - **PCIe MSI-X**：PCIe 设备通过 MSI-X Capability 结构体告知驱动自己的 MSI 能力。驱动在初始化时，需要将 Hypervisor/OS 分配的 MSI 地址和数据写入设备的 MSI-X Table（一组 MMIO 寄存器）。设备在需要触发中断时，会向该地址写入该数据。
> - **谁在运行这些代码**：步骤 1 通常由 M-mode 固件（如 OpenSBI）或 S-mode OS 的启动代码执行；步骤 2 由 S-mode 的网卡驱动执行；步骤 3-5 是硬件自动行为。
> - **中断 ID 的分配**：中断 ID 由软件自由分配。在 MSI 模式下，APLIC 不参与 ID 分配——驱动直接将 ID 编码到 MSI Data 中。本例中假设网卡驱动选择 ID=50。

```
系统配置：
- 4 核 RISC-V 处理器
- 每个 hart 有 IMSIC（M-mode + S-mode 中断文件）
- APLIC 配置为 MSI 模式
- PCIe 网卡支持 MSI-X

步骤 1：系统初始化

  // 配置 APLIC
  aplic->domaincfg = (1 << 8) | (1 << 2);  // IE=1(使能) + DM=1(MSI模式)

  // 配置 MSI 地址
  aplic->smsiaddrcfg = 0x28000000;  // S-mode IMSIC 基地址
  aplic->smsiaddrcfgh = 0x00000000;

  // 配置网卡中断源
  aplic->sourcecfg[NET_IRQ] = 1;  // Edge1 = 上升沿触发（sourcecfg 编码：0=Inactive, 1=Edge1, 2=Level1, ...）
  aplic->target[NET_IRQ] = Hart1;     // 路由到 Hart 1

步骤 2：网卡驱动初始化

  // 配置 IMSIC S-mode 中断文件
  csrw siselect, 0x70;
  csrw sireg, 1;              // eidelivery = 1

  csrw siselect, 0x72;
  csrw sireg, 0;              // eithreshold = 0 (接收所有优先级)

  // 使能网卡中断 (假设中断 ID = 50)
  csrw siselect, 0xC0 + (50 / 64);  // 选择 eie[0]
  csrs sireg, (1ULL << (50 % 64));  // 使能位 50

  // 步骤 2d：将 MSI 地址和数据写入网卡的 MSI-X Table
  // （这是 PCIe 驱动编程设备的标准流程）
  // 网卡的 MSI-X Table 位于设备的 PCI 配置空间中（通过 BAR 映射到 MMIO）
  nic->msix_table[QUEUE_0].addr = 0x28001000;  // MSI 地址 = Hart1 S-mode IMSIC 地址
  nic->msix_table[QUEUE_0].data = 50;           // MSI 数据 = 中断 ID
  nic->msix_table[QUEUE_0].vector_ctrl = 0;     // 未屏蔽

  // 从此刻起，网卡收到数据包时会向 0x28001000 写入 50

步骤 3：网卡收到数据包

  网卡硬件：
    1. DMA 数据包到内存
    2. 执行 MSI 写入：
       *(uint32_t *)0x28001000 = 50;

步骤 4：IMSIC 处理

  IMSIC Hart1 S-mode 中断文件：
    1. 接收中断 ID 50
    2. 标记为 pending
    3. 检查 eie[0] 位 50 = 1 (已使能)
    4. 检查 eidelivery = 1 (已使能)
    5. 检查优先级 >= eithreshold (0 >= 0，满足)
    6. 更新 topei = 50
    7. 发送中断信号到 Hart1

步骤 5：CPU 处理中断

  Hart1 收到外部中断：
    1. 保存当前上下文
    2. 跳转到中断处理程序
    3. 读取 stopei 获取中断 ID
    4. 调用网卡驱动的中断处理函数
    5. 驱动处理数据包
    6. 写入 stopei = 50 清除中断
    7. 恢复上下文，继续执行
```

> **关键理解：MSI 写入的本质是什么？**
>
> 步骤 3 中 `*(uint32_t *)0x28001000 = 50` 只是便于理解的伪代码写法。实际上，网卡**并不通过 CPU 访问内存**，而是作为 PCIe 设备直接通过**系统总线**（PCIe Bus → Interconnect → SoC Bus）向物理地址 0x28001000 发起一次 **Memory Write 事务**。这个地址恰好映射到 Hart1 的 IMSIC S-mode 中断文件，所以 IMSIC 硬件会捕获这次写入，将写入数据 50 解析为中断 ID。
>
> **MSI 的本质就是：设备通过总线直接写内存，而 IMSIC 把特定地址范围的写入操作"拦截"为中断信号。CPU 完全不参与这个过程。**

> **非 PCIe 设备怎么办？**
>
> MSI 最初是 PCIe 规范定义的机制，但在 RISC-V AIA 中，MSI 的概念被泛化了：
>
> | 设备类型 | 如何产生 MSI | 说明 |
> |----------|-------------|------|
> | **PCIe 设备**（网卡、SSD 等） | 设备硬件直接通过 PCIe 总线发起 Memory Write | 最常见的 MSI 场景，设备内置 MSI Capability |
> | **非 PCIe 设备**（UART、GPIO、定时器等） | 通过 **APLIC 转换**：APLIC 检测到有线中断后，自动向 IMSIC 发起一次 MSI 写入 | 这就是 APLIC 的 MSI 投递模式（§12.4），APLIC 充当"有线中断 → MSI"的翻译器 |
> | **平台级中断控制器**（其他 SoC 中断源） | 同上，由 APLIC 统一转换 | 所有非 MSI 设备的中断都先进入 APLIC，再由 APLIC 以 MSI 形式转发给 IMSIC |
>
> 所以在完整 AIA 系统中，**所有中断最终都以 MSI 形式到达 IMSIC**——PCIe 设备自己发，非 PCIe 设备由 APLIC 代发。这也是为什么 AIA 规范说 APLIC 和 IMSIC 是互补的关系。

### 13.2 场景：虚拟机中的设备直通

> **阅读本节前你需要了解：**
> - **设备直通（Device Passthrough）**：将一个物理设备直接分配给虚拟机使用，VM 可以直接访问设备的 MMIO 寄存器和 DMA，无需 Hypervisor 代理。这需要 IOMMU 提供地址转换和保护。
> - **GPA vs HPA**：VM 看到的地址是"客户机物理地址"（GPA），而实际硬件使用的是"主机物理地址"（HPA）。IOMMU 负责两者之间的转换。
> - 本场景涉及 IOMMU 中断重映射和 Guest 中断文件，相关概念将在 §14 和 §15 中详细讲解。如果以下内容不太理解，可以先跳到 §14 阅读后再回来。

```
系统配置：
- Hypervisor (KVM)
- VM1 直通 PCIe 网卡
- IOMMU 启用中断重映射

步骤 1：Hypervisor 配置

  // 1a. 为 VM1 分配 Guest File 0（Hart0 的第一个 guest 文件）
  //     分配策略：Hypervisor 维护一个 guest 文件池，按需分配
  //     分配后需要：
  //       - 设置 hgeie 使能该文件（csrw 0xE12, (1 << 0)）
  //       - 记录 VM1 → Guest File 0 的映射关系

  // 1b. 配置 IOMMU 中断重映射表（MSI Page Table）
  //     这是核心步骤——告诉 IOMMU 如何转换 VM1 的 MSI 地址
  //
  //     VM1 的网卡驱动会使用 GPA 0x28000040 作为 MSI 地址
  //     （这个 GPA 是 VM1 从虚拟设备树中读取的）
  //
  //     Hypervisor 需要在 IOMMU 的 MSI 页表中建立映射：
  //       输入：GPA 0x28000040 + Data 0x15（中断 ID）
  //       输出：HPA 0x28000040（Guest File 0 的物理地址） + Data 0x15
  //
  //     GPA → HPA 的转换：IMSIC 地址计算公式为
  //       base + hart_index * 0x4000 + file_index * 0x1000
  //     本例中 Guest File 0 的 HPA 恰好也是 0x28000040
  //     （实际系统中 GPA 和 HPA 通常不同）

步骤 2：VM1 初始化网卡

  // VM1 看到的 MSI 地址 (GPA)
  MSI Address = 0x28000040
  MSI Data = 0x15

  // VM1 配置自己的中断处理
  // (VM1 不知道自己在虚拟机中)

步骤 3：网卡发送中断

  网卡写入：
    *(uint32_t *)0x28000040 = 0x15;

步骤 4：IOMMU 转换

  IOMMU 拦截写入：
    1. 识别为 MSI
    2. 查中断重映射表
    3. 转换为 Hart0 Guest File 0 的地址
    4. 转发

步骤 5：Guest 中断文件处理

  Guest File 0：
    1. 接收中断 ID 0x15
    2. 更新 topei
    3. 通知 vCPU

步骤 6：VM1 处理中断

  VM1 的中断处理程序：
    1. 读取 stopei
    2. 处理网卡中断
    3. 清除中断

  整个过程 Hypervisor 没有介入！
```

# 第四部分：虚拟化深入

前三部分我们了解了 AIA 的基本架构和核心组件（IMSIC、APLIC）。本部分将深入探讨 AIA 在虚拟化场景下的设计——这是 AIA 相比 PLIC 最核心的改进之一。我们将依次学习三个关键机制：

- **Guest 中断文件**（§14）：让虚拟机直接接收中断，无需 Hypervisor 介入
- **IOMMU 中断重映射**（§15）：将虚拟机的 MSI 地址转换为真实物理地址
- **MRIF**（§16）：当 guest 文件不够用时，将中断状态换出到内存

这三个机制构成了一个完整的虚拟化中断方案链：Guest 文件提供硬件支持 → IOMMU 提供地址转换 → MRIF 提供可扩展性。

## 14. Guest 中断文件【规范 §3.1】

### 14.1 为什么需要 Guest 中断文件？【规范 §3.1】

```
没有 Guest 中断文件时：

VM 中断流程：
设备 ──> Hypervisor ──> 注入虚拟中断 ──> VM
       (每次都要介入)

问题：
- 每次中断都需要 Hypervisor
- Hypervisor 需要保存/恢复上下文
- 延迟高（可能增加 10-100 倍）
- CPU 开销大

有 Guest 中断文件时：

VM 中断流程：
设备 ──> Guest 中断文件 ──> VM
       (Hypervisor 不参与)

优势：
- 中断直接投递到 VM
- Hypervisor 只在配置时介入
- 延迟接近原生
- CPU 开销小
```

### 14.2 Guest 中断文件结构【规范 §3.1】

```
每个 hart 的 IMSIC 可以有多个中断文件：

┌──────────────────────────────────────────────┐
│              IMSIC (per hart)                │
│                                              │
│  ┌─────────────────────────────────────┐     │
│  │  Machine Interrupt File             │     │
│  │  - 供 M-mode Hypervisor 使用        │     │
│  │  - 处理机器级中断                   │     │
│  └─────────────────────────────────────┘     │
│                                              │
│  ┌─────────────────────────────────────┐     │
│  │  Supervisor Interrupt File          │     │
│  │  - 供 HS-mode Hypervisor 使用       │     │
│  │  - 处理监管级中断                   │     │
│  └─────────────────────────────────────┘     │
│                                              │
│  ┌─────────────────────────────────────┐     │
│  │  Guest Interrupt File 0             │     │
│  │  - 供 VM1 (VS-mode) 使用            │     │
│  │  - VM1 直接管理自己的中断           │     │
│  └─────────────────────────────────────┘     │
│                                              │
│  ┌─────────────────────────────────────┐     │
│  │  Guest Interrupt File 1             │     │
│  │  - 供 VM2 (VS-mode) 使用            │     │
│  └─────────────────────────────────────┘     │
│                                              │
│  ...                                         │
│                                              │
│  ┌─────────────────────────────────────┐     │
│  │  Guest Interrupt File 62            │     │
│  │  - 最多支持 63 个 guest 文件       │      │
│  │    (RV64, 由 GEILEN 决定)          │      │
│  └─────────────────────────────────────┘     │
│                                              │
└──────────────────────────────────────────────┘
```

每个 guest 文件有独立的：
- eidelivery
- eithreshold
- eie[0..63]
- topi / topei

> **关于最大数量**：每个 hart 最多支持的 guest interrupt file 数量由 **GEILEN**（Guest External Interrupt Length）决定，这是实现定义的参数。RV64 系统中 GEILEN 的理论最大值为 **63**（受 `hstatus.VGEIN` 字段 6-bit 宽度限制），RV32 系统中最大值为 **31**。GEILEN=0 也是合法的（表示不支持 guest external interrupt）。
>
> **注意**：不要将 guest interrupt file 的数量（最多 63 个）与每个 file 内部的中断 ID 数量（最多 2047 个）混淆。
>
> **规范原文**【规范 §3.1】：
> "Assuming a hart implements supervisor mode, its IMSIC has at least two interrupt files,
> one for machine level and the other for supervisor level. When a hart also implements the
> H extension, its IMSIC may have additional interrupt files for virtual harts, called guest
> interrupt files. The number of guest interrupt files an IMSIC has for virtual harts is
> exactly GEILEN, the number of supported guest external interrupts, as defined by the H
> extension."

### 14.3 Guest 中断文件的访问【规范 §3.8】

> **阅读本节前，你需要了解以下背景知识：**
>
> **什么是 H 扩展？**
> RISC-V 的 H（Hypervisor）扩展是可选的 CPU 扩展，为 RISC-V 添加了硬件虚拟化支持。
> 启用 H 扩展后，RISC-V 的特权级模型从原来的两级（M-mode + S-mode）变为**两级半**：
>
> ```
> 没有 H 扩展时：
>   M-mode（机器模式）── 最高特权级，运行固件/Bare-metal 程序
>   S-mode（监管模式）── 运行操作系统
>   U-mode（用户模式）── 运行用户程序
>
> 有 H 扩展时：
>   M-mode（机器模式）── 不变，最高特权级
>   HS-mode（Host Supervisor）── 运行 Hypervisor（如 KVM、Xvisor）
>     ↑ 这就是原来的 S-mode，但现在它运行的是 Hypervisor 而非普通 OS
>   VS-mode（Virtual Supervisor）── 运行虚拟机中的操作系统
>     ↑ 这是 H 扩展新增的"虚拟 S-mode"，VM 的 OS 以为自己运行在 S-mode
>   VU-mode（Virtual User）── 运行虚拟机中的用户程序
> ```
>
> **关键机制**：CPU 通过 `mstatus` 寄存器中的 **V 位**（Virtualization bit）来区分
> 当前是 HS-mode（V=0）还是 VS-mode（V=1）。当 V=1 时，原本的 S-mode CSR 访问
> 会被硬件自动重定向到对应的"虚拟"版本。
>
> **`hstatus` 是什么？**
> `hstatus`（Hypervisor Status，CSR 0x600）是 H 扩展引入的 CSR 寄存器，
> 用于 Hypervisor 控制虚拟化行为。它只在 M-mode 或 HS-mode（V=0 时的 S-mode）下可访问。
> 其中 **VGEIN**（bits 17:12）字段用于选择当前 VM 使用的 guest interrupt file。
>
> **`csrs` vs `csrw` 的区别**：
> - `csrw`（CSR Write）：直接覆盖写入 CSR 的全部值
> - `csrs`（CSR Set Bits）：原子读-修改-写，只将指定位置 1，其他位不变
> 所以 `csrs hstatus, (1 << 12)` 的含义是"将 hstatus 的 bit 12 置 1，其他位保持不变"。
>
> 如果你想深入了解 H 扩展的完整设计，推荐阅读：
> - RISC-V 特权规范 v1.12 第 8 章（Hypervisor Extension）
> - [RISC-V H Extension 快速入门](https://github.com/riscv-software-src/riscv-isa-manual/blob/main/src/hypervisor.tex)

---

**场景：Hypervisor 为 VM1 配置并切换 guest 中断文件**

以下是 Hypervisor（运行在 HS-mode）管理 guest 文件的完整生命周期：

```
阶段 1：VM 创建时 —— Hypervisor 分配 guest 文件

  // 假设 Hypervisor 决定将 Guest File 1 分配给 VM1
  // （分配策略由 Hypervisor 自行决定，通常在 VM 创建时完成）

  // 步骤 1a：使能 Guest File 1 的外部中断
  // hgeie（Hypervisor Guest External Interrupt Enable）控制哪些 guest 文件可以产生中断
  // 写入 CSR 0xE12，bit N 对应 Guest File N
  csrw 0xE12, (1 << 1)    // 使能 Guest File 1（bit 1 = 1）

  // 步骤 1b：配置 IOMMU 中断重映射（详见 §15）
  // 将 VM1 的 MSI 地址（GPA）映射到 Guest File 1 的物理地址（HPA）
  // （此处省略 IOMMU 配置细节，详见 §15）

阶段 2：VM 调度进入时 —— Hypervisor 切换到 VM1

  // 步骤 2a：设置 VGEIN = 1，选择 Guest File 1
  // hstatus.VGEIN（bits 17:12）决定 VS-mode 使用哪个 guest 文件
  csrs hstatus, (1 << 12)    // VGEIN = 1（bit 12 置 1，因为 VGEIN 从 bit 12 开始）

  // 步骤 2b：（可选）检查 Guest File 1 是否有 pending 的中断
  csrr t0, hgeip             // 读取各 guest 文件的 pending 状态
  andi t0, t0, (1 << 1)      // 检查 bit 1（Guest File 1）
  bnez t0, inject_interrupt  // 如果有 pending 中断，可以先注入虚拟中断

  // 步骤 2c：执行 SRET 进入 VS-mode
  // SRET（Supervisor Return）指令会：
  //   1. 将 mstatus.V 置 1（进入虚拟化模式）
  //   2. 从 hstatus.VGEIN 读取 guest 文件编号
  //   3. 跳转到 VM1 的 PC 继续执行
  sret

  // 从此刻起，CPU 运行在 VS-mode（V=1）
  // VM1 的 OS 以为自己运行在普通的 S-mode

阶段 3：VM 运行中 —— VM 自己处理中断

  // VM1 的 OS 运行在 VS-mode，执行以下代码：
  // （VM 完全不知道自己在虚拟机中）

  csrr t0, stopei    // 看起来是读取 stopei...
                      // 但实际上硬件自动映射为读取 vstopei
                      // 即 Guest File 1 的 topei 寄存器
                      // 返回该文件中最高优先级的 pending 中断 ID

  // VM 处理中断后：
  csrw stopei, t0    // 写入 stopei 完成 claim
                      // 硬件自动映射为写入 vstopei（Guest File 1）

  // 整个过程 Hypervisor 完全不参与！

阶段 4：VM 调度换出时 —— Hypervisor 保存状态

  // 当 Hypervisor 决定切换到另一个 VM 时：
  // （通常由定时器中断触发 VM 换出）

  // 步骤 4a：CPU 因定时器中断从 VS-mode 陷入 HS-mode
  // （V 位自动清零，回到 HS-mode）

  // 步骤 4b：Hypervisor 可以读取 Guest File 1 的状态
  csrr t0, hgeip             // 检查是否有未处理的 pending 中断
  // 如果需要，可以通过间接 CSR 读取 Guest File 1 的 eie/eip 等状态

  // 步骤 4c：切换到下一个 VM（设置新的 VGEIN，执行 SRET）
```

> **关键 CSR 说明**：
> - **`hgeip`**（Hypervisor Guest External Interrupt Pending，CSR 0xE12，只读）：显示各 guest interrupt file 的 pending 状态，每个 bit 对应一个 guest 文件
> - **`hgeie`**（Hypervisor Guest External Interrupt Enable，与 hgeip 共享地址 0xE12，写操作）：控制各 guest external interrupt 的使能
> - **`VGEIN`**（Virtual Guest External Interrupt Number，`hstatus` 的 bits 17:12）：由 Hypervisor 设置，选择当前 VS-mode 使用的 guest interrupt file。VGEIN=0 表示未选中任何文件
> - VS-mode 软件通过 `vstopei`/`vsiselect`/`vsireg`（在 V=1 时自动替换 `stopei`/`siselect`/`sireg`）直接操作选中的 guest 文件，无需 Hypervisor 介入
>
> **`hgeip` 和 `hgeie` 为什么共享同一个 CSR 地址？**
> 这是 RISC-V CSR 空间的常见设计模式——读写分离（read-write aliasing）。
> 对地址 0xE12 执行 `csrr`（读）时，硬件返回 `hgeip`（pending 状态）；
> 执行 `csrw`（写）时，硬件写入 `hgeie`（enable 控制）。
> 这样可以用一个地址实现两个功能，节省 CSR 地址空间。

---

§14 介绍了 Guest 中断文件的概念——每个 VM 可以拥有独立的中断文件，直接接收中断。但有一个关键问题：虚拟机配置设备时使用的是**客户机物理地址（GPA）**，而 IMSIC 硬件只能识别**主机物理地址（HPA）**。如果设备直接写入 GPA，要么写入错误的内存位置，要么被 IOMMU 当作普通内存访问处理。我们需要一个机制将 GPA 转换为 HPA——这就是 IOMMU 中断重映射。

## 15. IOMMU 中断重映射【规范 §7】

### 15.1 为什么需要中断重映射？【规范 §7.1】

```
场景：VM 使用直通设备

VM 配置设备 MSI：
  MSI 地址 = GPA (Guest Physical Address)
  MSI 数据 = 中断 ID

问题：
1. 设备写入的是 GPA，不是真实物理地址
2. 直接写入会破坏内存
3. 需要转换为正确的 IMSIC 地址

解决方案：IOMMU 中断重映射

IOMMU 维护中断重映射表：
  输入 (GPA + 数据) ──> 输出 (HPA + 数据)

设备写入 GPA 时：
  IOMMU 拦截 ──> 查表转换 ──> 转发到正确的 IMSIC
```

### 15.2 中断重映射表结构【规范 §7.2】

```
RISC-V 使用 MSI 页表（MSI Page Table）而非 x86 风格的 IRTE：

MSI PTE（MSI Page Table Entry）：

┌──────────────────────────────────────────────────────────────┐
│                     MSI PTE (128-bit / 16 字节)              │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  Doubleword 0（64-bit）：                                    │
│  复用 RISC-V Sv39/Sv48/Sv57 叶页表项编码                     │
│  （Sv39/Sv48/Sv57 是 RISC-V 的三种页表格式，                 │
│    数字代表虚拟地址位数，详见 RISC-V 特权规范）              │
│  - D/A/G/U/X 位全为零                                        │
│  - W=R=1（可读可写）                                         │
│  - PPN 字段编码目标 IMSIC 的物理页号                         │
│                                                              │
│  Doubleword 1（64-bit）：                                    │
│  MSI 特定的额外信息                                          │
│  - 中断控制字段                                              │
│  - Guest 模式标识                                            │
│  - 其他控制位                                                │
└──────────────────────────────────────────────────────────────┘

特点：
1. MSI 页表使用与常规地址转换相同的页表遍历机制（Sv39/Sv48/Sv57）
2. MSI 页表与常规页表是独立的，不共享
3. 支持两种模式：基本翻译模式和 MRIF 模式
4. 每个 MSI PTE 大小为 16 字节（128 bit）
```

> **与 x86 的区别**：x86 使用专门的 Interrupt Remapping Table Entry (IRTE)，
> 而 RISC-V 复用了标准页表项的编码方式，通过 MSI 页表实现中断重映射。

§15 介绍了 IOMMU 中断重映射，解决了"虚拟机的 MSI 地址如何转换为物理地址"的问题。但还有一个可扩展性问题：每个 hart 最多只有 63 个 guest 中断文件（RV64），而大型系统可能同时运行数百甚至数千个虚拟机。当硬件 guest 文件不够用时怎么办？MRIF（Memory-Resident Interrupt File）提供了答案——将不活跃 VM 的中断状态保存到内存中，类似于操作系统的虚拟内存换入换出机制。

## 16. MRIF：内存驻留中断文件【规范 §8】

> **规范状态**：MRIF 是 AIA v1.0 规范（第 8 章）中正式定义的**可选特性**，
> 必须配合 IOMMU 使用。没有 IOMMU 的系统无法使用 MRIF。

### 16.1 什么是 MRIF？【规范 §8.1】

```
MRIF = Memory-Resident Interrupt File

问题：
- 每个 hart 最多支持 63 个 guest 中断文件（RV64，由 GEILEN 决定）
- 但系统可能有数千个 VM
- 硬件中断文件不够用

解决方案：
- 把不活跃的 VM 的中断文件放到内存中
- 调度到 CPU 时，加载到硬件中断文件
- 类似虚拟内存的换入换出

┌───────────────────────────────────────────────┐
│              MRIF 机制                        │
│                                               │
│  活跃的 VM：                                  │
│    中断文件在硬件 IMSIC 中                    │
│    ┌─────────────────────────────────────┐   ││
│    │  Guest File 0 (VM1)  ── 活跃       │   │ │
│    │  Guest File 1 (VM2)  ── 活跃       │   │ │
│    └─────────────────────────────────────┘   ││
│                                               │
│  不活跃的 VM：                                │
│    中断文件在内存中                           │
│    ┌─────────────────────────────────────┐   ││
│    │  VM3 中断文件 ── 内存区域 A          │  ││
│    │  VM4 中断文件 ── 内存区域 B          │  ││
│    │  VM5 中断文件 ── 内存区域 C          │  ││
│    │  ...                                │  │ │
│    │  VM1000 中断文件 ── 内存区域 Z       │  ││
│    └─────────────────────────────────────┘   ││
│                                               │
│  调度时：                                     │
│    VM3 被调度到 CPU ──> 加载中断文件到 IMSIC ││
│    VM1 被换出 ──> 保存中断文件到内存         ││
└───────────────────────────────────────────────┘
```

### 16.2 MRIF 的工作流程【规范 §8.2】

```
VM 换出：

1. Hypervisor 决定换出 VM1
2. 读取 VM1 的 guest 中断文件状态：
   - eidelivery
   - eithreshold
   - eie[0..63]
   - pending 状态
3. 保存到内存中的 MRIF 区域
4. 释放硬件 guest 中断文件

VM 换入：

1. Hypervisor 决定调度 VM3
2. 分配一个空闲的硬件 guest 中断文件
3. 从内存中的 MRIF 区域加载状态
4. 配置 IOMMU 中断重映射到新的 guest 文件
5. VM3 恢复运行

设备中断投递到换出的 VM：

1. 设备发送 MSI（写入 GPA）
2. IOMMU 查询 MSI 页表，发现目标 guest 文件对应的 MSI PTE
   标记为"MRIF 模式"（而非基本翻译模式）
3. IOMMU 根据 MSI PTE 中的指针，将中断 ID 写入内存中的 MRIF 区域
   （而非转发到硬件 IMSIC）
4. MRIF 区域中对应 VM 的 pending 位被置位
5. 当 Hypervisor 将该 VM 换入时：
   a. 从 MRIF 区域读取所有 pending 中断
   b. 加载到硬件 guest 中断文件
   c. VM 恢复运行后，硬件自动投递这些中断

> **关键细节**：IOMMU 如何知道 VM 已换出？答案是 Hypervisor 在换出 VM 时，
> 会更新对应的 MSI PTE，将其从"基本翻译模式"切换为"MRIF 模式"。
> 这样 IOMMU 在查表时就能自动判断目标 VM 的状态。
```

## 18. 代码示例

> 本节提供可直接使用的 C 代码示例，涵盖 IMSIC 初始化和 APLIC 配置。所有代码均基于 RV64 架构，使用 RISC-V 内联汇编访问 CSR。代码中的魔法数字（如 0x70、0x72、0xC0）均为 IMSIC 间接寄存器地址，详见 §17.4 的地址映射表。

### 18.1 初始化 IMSIC S-mode 中断文件

> **使用场景**：以下代码通常在 S-mode OS 的启动早期（如 Linux kernel 的 `init_IRQ()` 阶段）调用。
> 调用前提：M-mode 固件（如 OpenSBI）已经完成了 IMSIC 的 M-mode 初始化，
> 包括设置 M-mode 中断文件的 eidelivery 和配置 APLIC 的 MSI 地址。
> 每个 hart 需要独立调用一次 `imsic_s_init()`。

> **GCC 内联汇编语法速读**（如果你不熟悉 `asm volatile` 语法）：
> ```c
> asm volatile("csrw siselect, %0" :: "r"(ireg));
> // │       │                    │  │  └── 输入操作数：ireg 放入通用寄存器
> // │       │                    │  └── 约束符分隔（无输出操作数）
> // │       │                    └── %0 = 第一个操作数的占位符
> // │       └── 汇编指令模板（RISC-V 的 CSR 写入指令）
> // └── volatile：告诉编译器不要优化掉这条指令（即使看似无副作用）
> ```
> 其中 `"r"` 表示"将 C 变量放入通用寄存器"，`"=r"` 表示"将寄存器值输出到 C 变量"。

```c
// IMSIC S-mode 中断文件初始化

// 间接访问辅助函数
static inline void imsic_s_write(uint32_t ireg, uint64_t value) {
    asm volatile("csrw siselect, %0" :: "r"(ireg));
    asm volatile("csrw sireg, %0" :: "r"(value));
}

static inline uint64_t imsic_s_read(uint32_t ireg) {
    uint64_t value;
    asm volatile("csrw siselect, %0" :: "r"(ireg));
    asm volatile("csrr %0, sireg" : "=r"(value));
    return value;
}

// 使能中断投递
void imsic_s_enable_delivery(void) {
    imsic_s_write(0x70, 1);  // eidelivery = 1
}

// 设置中断阈值
void imsic_s_set_threshold(uint8_t threshold) {
    imsic_s_write(0x72, threshold);  // eithreshold
}

// 使能特定中断
void imsic_s_enable_interrupt(uint32_t interrupt_id) {
    uint32_t eie_index = interrupt_id / 64;
    uint32_t bit = interrupt_id % 64;
    uint32_t ireg = 0xC0 + eie_index;  // eie0 起始于 0xC0
    
    uint64_t current = imsic_s_read(ireg);
    current |= (1ULL << bit);
    imsic_s_write(ireg, current);
}

// 禁用特定中断
void imsic_s_disable_interrupt(uint32_t interrupt_id) {
    uint32_t eie_index = interrupt_id / 64;
    uint32_t bit = interrupt_id % 64;
    uint32_t ireg = 0xC0 + eie_index;  // eie0 起始于 0xC0
    
    uint64_t current = imsic_s_read(ireg);
    current &= ~(1ULL << bit);
    imsic_s_write(ireg, current);
}

// 获取最高优先级中断
uint32_t imsic_s_get_top_interrupt(void) {
    uint32_t interrupt_id;
    asm volatile("csrr %0, stopei" : "=r"(interrupt_id));
    return interrupt_id & 0xFFF;  // topei 返回值低 12 位为中断 ID（bits 11:0），详见 §11 中 topei 位布局说明
}

// 完成中断处理
void imsic_s_complete_interrupt(uint32_t interrupt_id) {
    asm volatile("csrw stopei, %0" :: "r"(interrupt_id));
}

// 完整初始化
void imsic_s_init(void) {
    // 1. 设置阈值为 0（接收所有优先级）
    imsic_s_set_threshold(0);
    
    // 2. 禁用所有中断（清除 eie0-eie63）
    for (int i = 0; i < 64; i++) {
        imsic_s_write(0xC0 + i, 0);  // eie0 起始于间接地址 0xC0
    }
    
    // 3. 使能中断投递
    imsic_s_enable_delivery();
}
```

### 18.2 初始化 APLIC

> **使用场景**：以下代码在 S-mode OS 初始化 APLIC 时调用。
> APLIC 的 MMIO 寄存器基地址通常从设备树（Device Tree）中获取，
> 本例中硬编码为 `0x0D000000`（QEMU virt 机器的默认值）。
>
> **结构体字段说明**：
> - `sourcecfg[1023]`：数组大小为 1023（不是 1024），因为 APLIC 的中断源 ID 从 1 开始，ID 0 被保留
> - `_reserved` 占位字段：保证结构体布局与硬件寄存器地址映射一致，不可省略
> - `source_id - 1`：代码中多处使用 `source_id - 1` 作为数组索引，原因就是 ID 从 1 开始而 C 数组从 0 开始
> - `setip` vs `setipnum`：`setip` 是位图操作（写 1 置位对应 bit），`setipnum` 是索引操作（写入中断 ID 号即可）

```c
// APLIC 寄存器结构
struct aplic_regs {
    volatile uint32_t domaincfg;
    volatile uint32_t sourcecfg[1023];
    volatile uint8_t _reserved1[0xBC0];
    volatile uint32_t mmsiaddrcfg;
    volatile uint32_t mmsiaddrcfgh;
    volatile uint32_t smsiaddrcfg;
    volatile uint32_t smsiaddrcfgh;
    volatile uint8_t _reserved2[0x30];
    volatile uint32_t setip[32];
    volatile uint8_t _reserved3[92];
    volatile uint32_t setipnum;
    volatile uint8_t _reserved4[0x20];
    volatile uint32_t in_clrip[32];
    volatile uint8_t _reserved5[92];
    volatile uint32_t clripnum;
    volatile uint8_t _reserved6[32];
    volatile uint32_t setie[32];
    volatile uint8_t _reserved7[92];
    volatile uint32_t setienum;
    volatile uint8_t _reserved8[32];
    volatile uint32_t clrie[32];
    volatile uint8_t _reserved9[92];
    volatile uint32_t clrienum;
    volatile uint8_t _reserved10[32];
    volatile uint32_t setipnum_le;
    volatile uint32_t setipnum_be;
    volatile uint8_t _reserved11[4088];
    volatile uint32_t genmsi;
    volatile uint32_t target[1023];
};

// APLIC 基地址 (S-mode)
#define APLIC_S_BASE 0x0D000000

// 获取 APLIC 寄存器指针
static inline struct aplic_regs *aplic_s(void) {
    return (struct aplic_regs *)APLIC_S_BASE;
}

// 配置 APLIC 域
void aplic_s_configure_domain(int msi_mode) {
    struct aplic_regs *aplic = aplic_s();
    
    // IE=1 (使能), DM=msi_mode, BE=0 (小端)
    aplic->domaincfg = (1 << 8) | (msi_mode << 2);
}

// 配置中断源
void aplic_s_configure_source(uint32_t source_id, 
                               uint32_t mode, 
                               uint32_t target_hart) {
    struct aplic_regs *aplic = aplic_s();
    
    // 配置源模式
    aplic->sourcecfg[source_id - 1] = mode;
    
    // 配置目标 hart
    aplic->target[source_id - 1] = target_hart;
}

// 使能中断源
void aplic_s_enable_source(uint32_t source_id) {
    struct aplic_regs *aplic = aplic_s();
    
    // 计算字节偏移和位偏移
    uint32_t word_index = (source_id - 1) / 32;
    uint32_t bit_index = (source_id - 1) % 32;
    
    // 设置中断使能位
    // setie 寄存器位于 offset 0x1C00 + word_index * 4
    volatile uint32_t *setie = (volatile uint32_t *)((uint8_t *)aplic + 0x1C00);
    setie[word_index] = (1 << bit_index);
}
```

## 19. QEMU 实践指南

> 本节介绍如何在 QEMU 中启用 AIA 功能并查看相关配置。QEMU 的 `virt` 机器类型支持 AIA，是学习和调试 AIA 的最佳仿真环境。

### 19.1 启动支持 AIA 的 RISC-V 虚拟机

```bash
# 使用 virt 机器类型，启用 AIA
qemu-system-riscv64 \
    -machine virt,aia=aplic-imsic \
    -cpu rv64 \
    -m 2G \
    -kernel your-kernel.bin \
    -nographic
```

**AIA 模式选项：**
- `aia=off`：禁用 AIA，使用传统 PLIC
- `aia=aplic`：仅启用 APLIC（有线中断模式）
- `aia=aplic-imsic`：启用 APLIC + IMSIC（完整 AIA 模式）

### 19.2 查看设备树中的 AIA 信息

```bash
# 在 Linux 中查看设备树
dtc -I fs /sys/firmware/devicetree/base > aia.dts

# 查看 APLIC 节点
cat aia.dts | grep -A 20 aplic

# 查看 IMSIC 节点
cat aia.dts | grep -A 20 imsic
```

**典型设备树片段：**
```dts
aplic@d000000 {
    compatible = "riscv,aplic";
    reg = <0x0 0xd000000 0x0 0x4000000>;
    interrupts-extended = <&cpu0_intc 0xffffffff>;
    riscv,ndev = <64>;
};

imsic@28000000 {
    compatible = "riscv,imsic";
    reg = <0x0 0x28000000 0x0 0x4000000>;
    interrupts-extended = <&cpu0_intc 0xffffffff>;
    riscv,guest-num = <7>;
};
```

**设备树属性说明：**
- `compatible`：驱动匹配标识，内核通过此字段加载对应的 APLIC/IMSIC 驱动
- `reg`：寄存器物理地址范围，格式为 `<地址高位 地址低位 大小高位 大小低位>`
- `interrupts-extended`：指向连接的 interrupt controller（通常是 CPU 的 Interrupt Controller）
- `riscv,ndev`：APLIC 支持的中断源数量（不含 ID 0）
- `riscv,guest-num`：IMSIC 支持的 guest interrupt file 数量（对应 GEILEN + 1）

## 20. 常见问题与调试

> 本节汇总了 AIA 开发中最常见的问题和排查方法。每个问题都提供了具体的检查步骤和代码片段，建议收藏备查。

### 20.1 中断没有投递到 CPU

**排查步骤：**

1. **检查 APLIC domaincfg 寄存器**
   ```c
   // IE 位必须为 1
   assert(aplic->domaincfg & (1 << 8));
   ```

2. **检查中断源是否使能**
   ```c
   // 检查 setie 寄存器
   uint32_t word_index = (source_id - 1) / 32;
   uint32_t bit_index = (source_id - 1) % 32;
   assert(aplic->setie[word_index] & (1 << bit_index));
   ```

3. **检查 IMSIC eidelivery**
   ```c
   // eidelivery 必须为 1（间接地址 0x70）
   assert(imsic_s_read(0x70) & 1);
   ```

4. **检查中断优先级阈值**
   ```c
   // eithreshold 应该小于中断优先级（间接地址 0x72）
   uint32_t threshold = imsic_s_read(0x72);
    uint32_t priority = source_id;  // IMSIC 隐式优先级：优先级 = 中断 ID（详见附录 A.1）
   assert(priority >= threshold);
   ```

### 20.2 虚拟化环境中 Guest 收不到中断

**常见原因：**

1. **IOMMU 中断重映射未配置**
   - 检查 IOMMU 是否启用了中断重映射
   - 验证 guest 中断文件地址映射是否正确

2. **Guest 中断文件未分配**
   - 确认 Hypervisor 已为 VM 分配了 guest 中断文件
   - 检查 `hgeip` 寄存器中的 pending 状态

3. **MRIF 状态未正确恢复**
   - VM 换入时，确保从 MRIF 区域加载了完整的中断状态

### 20.3 MSI 地址配置错误

**调试技巧：**

```c
// 打印 APLIC 的 MSI 地址配置
void dump_aplic_msi_config(void) {
    struct aplic_regs *aplic = aplic_s();
    
    printf("M-mode MSI addr: 0x%lx\n", 
           ((uint64_t)aplic->mmsiaddrcfgh << 32) | aplic->mmsiaddrcfg);
    printf("S-mode MSI addr: 0x%lx\n", 
           ((uint64_t)aplic->smsiaddrcfgh << 32) | aplic->smsiaddrcfg);
}

// 验证 IMSIC 地址是否匹配
void verify_imsic_address(void) {
    uint64_t expected_addr = 0x28000000;  // IMSIC 基地址，需根据实际硬件/设备树配置
    uint64_t actual_addr = ((uint64_t)aplic->smsiaddrcfgh << 32) | aplic->smsiaddrcfg;
    
    if (expected_addr != actual_addr) {
        printf("MSI address mismatch!\n");
        printf("Expected: 0x%lx\n", expected_addr);
        printf("Actual:   0x%lx\n", actual_addr);
    }
}
```

### 20.4 性能问题排查

**中断延迟过高：**

1. **检查中断优先级设置**
   - 高优先级中断被低优先级阈值阻塞
   - 调整 `eithreshold` 值

2. **检查中断嵌套配置**
   - 确认 `eidelivery` 允许中断嵌套
   - 验证中断处理程序是否正确保存/恢复上下文

3. **使用性能计数器**
   ```c
   // 读取机器级性能计数器
   uint64_t mcycle_start; asm volatile("csrr %0, mcycle" : "=r"(mcycle_start));
   handle_interrupt();
   uint64_t mcycle_end; asm volatile("csrr %0, mcycle" : "=r"(mcycle_end));
   
   printf("Interrupt handling took %lu cycles\n", 
          mcycle_end - mcycle_start);
   ```

## 附录 A：AIA 中断优先级与抢占机制

> **重要提示**：AIA 中 IMSIC 和 APLIC 使用不同的优先级机制，本附录分别说明。
>
> 如果你阅读正文时对"优先级"的描述感到困惑（例如 §7 说"ID 越小优先级越高"，而 §12 又提到 APLIC 可以"配置优先级"），这是因为两个组件的优先级机制完全不同。本附录将帮助你理清这些概念。

### A.1 IMSIC 的隐式优先级【规范 §3.3】

IMSIC 采用**隐式优先级**设计，这是与 x86 APIC 的一个重要区别：

```
x86 APIC（显式优先级）：
  每个中断有一个独立的优先级字段（0-15）
  软件可以自由配置每个中断的优先级
  优先级与中断向量号无关

RISC-V IMSIC（隐式优先级）：
  中断 ID 本身就决定了优先级
  ID 越小 → 优先级越高
  ID=1 优先级最高
  无法单独配置某个中断的优先级
  但软件可以通过分配 ID 来间接控制优先级
```

**规范原文**：
> "Within a single interrupt file, interrupt priorities are determined directly from
> interrupt identity numbers. Lower identity numbers have higher priority."
>
> "Because MSIs give software complete control over the assignment of identity numbers
> in an interrupt file, software is free to select identity numbers that reflect the
> relative priorities desired."

**设计影响：**
- 软件在分配中断 ID 时必须考虑优先级关系
- 高优先级设备应分配较小的中断 ID
- 例如：定时器 = ID 1（最高），键盘 = ID 10，网络 = ID 50

### A.2 APLIC 的显式优先级【规范 §4.5.7】

与 IMSIC 不同，APLIC 在直接投递模式下（domaincfg.DM=0），每个中断源有独立的可配置优先级字段：

```
APLIC 的优先级：
  每个中断源（source）有一个 IPRIOLEN 位的优先级字段
  IPRIOLEN 是实现定义的位宽（规范未规定具体值）
  优先级 0 = 最高，值越大优先级越低
  与中断 ID 无关，完全独立配置
```

**总结对比**：

| 特性 | IMSIC（MSI 模式） | APLIC（直接投递模式） |
|------|-------------------|---------------------|
| 优先级来源 | 中断 ID（隐式） | 独立字段（显式） |
| 可配置性 | 通过分配 ID 间接控制 | 直接配置优先级字段 |
| 优先级方向 | ID 越小越高 | 值越小越高 |
| 位宽 | 与 ID 相同（最大 11 位） | IPRIOLEN（实现定义） |

### A.3 中断抢占（Interrupt Preemption）

AIA 支持中断抢占，这是相对 PLIC 的重要改进：

```
PLIC：不支持抢占
  CPU 正在处理中断 A（优先级 5）
  中断 B（优先级 10）到来 → 必须等 A 处理完
  结果：高优先级中断被低优先级中断阻塞

AIA：支持抢占
  CPU 正在处理中断 A（ID=50，优先级低）
  中断 B（ID=10，优先级高）到来 → 立即抢占 A
  CPU 暂停处理 A，先处理 B
  B 处理完后，恢复处理 A
```

**抢占控制：**
- `eithreshold` 寄存器控制抢占行为
- 当 CPU 正在处理中断 ID=X 时，只有 ID < X 的中断才能抢占
- 设置 `eithreshold` 可以屏蔽低于阈值的中断

### A.4 与特权规范的中断机制协作

AIA 并没有改变 RISC-V 特权规范的基本中断处理流程，而是对其进行了扩展：

```
不变的部分：
├── Trap 进入/返回流程（保存 PC 到 mepc/sepc，设置 mcause/scause）
├── 中断 cause code（M-mode 外部中断 = 11，S-mode 外部中断 = 9）
├── mie/sie 中的 MEIE/SEIE 全局使能位
├── mideleg 中断委托机制
└── mstatus/sstatus 中的中断使能位（MIE/SIE）

AIA 新增/扩展的部分：
├── 通过 IMSIC 接收外部中断（设置 mip.MEIP / sip.SEIP）
├── 通过 *topei（Top Of Priority External Interrupt）获取具体的中断 identity（而非单一中断源）
├── 通过 *iselect（Indirect Select）/*ireg（Indirect Register）间接访问中断文件寄存器
├── 通过 eithreshold（External Interrupt Threshold）配置中断优先级阈值
├── Hypervisor 扩展（hgeip/hgeie、hvictl 等，全称见 §17.3）
└── 中断抢占支持
```

**关键理解**：AIA 扩展了"外部中断"的内涵——从 PLIC 的单一中断源变为最多 N 个不同的中断 ID（N 为实现定义，最大 2047）。
但外部中断触发 CPU 的方式不变（仍通过 MEIP/SEIP），中断处理的基本框架也不变。

## 附录 B：VS-mode 中断访问机制

> 本附录补充说明 VS-mode（虚拟机模式）下中断 CSR 的自动映射机制。这是 §14（Guest 中断文件）的延伸——§14 介绍了 Hypervisor 如何管理 guest 文件，而本附录从虚拟机软件的角度说明它如何透明地访问自己的中断文件。

当虚拟机运行在 VS-mode（V=1）时，中断访问的 CSR 会自动映射到被选中的 guest interrupt file：

```
VS-mode 下的 CSR 自动映射：

  stopei（Supervisor TOPEI）   →  vstopei（Virtual Supervisor TOPEI）
  siselect（Supervisor Indirect Select）  →  vsiselect（Virtual Supervisor Indirect Select）
  sireg（Supervisor Indirect Register）   →  vsireg（Virtual Supervisor Indirect Register）

  这些映射由硬件自动完成，VS-mode 软件无需知道自己在虚拟机中
```

**工作流程：**

```
1. Hypervisor（HS-mode）设置 hstatus.VGEIN = N
   → 选择 Guest Interrupt File N

2. Hypervisor 执行 SRET 进入 VS-mode
   → V=1 生效

3. VS-mode 软件执行 csrr t0, stopei
   → 硬件自动映射为读取 Guest File N 的 topei
   → 返回该 file 中最高优先级的 pending 中断

4. VS-mode 软件处理中断后写入 stopei
   → 硬件自动映射为完成 Guest File N 的中断

整个过程 Hypervisor 不需要介入！
```

> **注意**：VS-mode 软件无法直接修改 `hstatus.VGEIN`。
> 切换 guest interrupt file 必须由 Hypervisor 在 HS-mode 完成（通常在 VM 调度时）。

## 附录 C：与 x86 APIC 的对比

| 特性 | x86 APIC | RISC-V AIA |
|------|----------|------------|
| 中断控制器 | Local APIC + IO APIC | IMSIC + APLIC |
| MSI 支持 | 原生支持 | 原生支持（IMSIC） |
| 有线中断 | IO APIC 处理 | APLIC 处理 |
| 优先级 | 显式（0-15，可配置） | IMSIC 隐式（ID 越小越高）/ APLIC 显式（可配置） |
| 中断抢占 | TPR/PRCM 控制 | eithreshold 控制 |
| Claim/Complete | 分开（EOI 寄存器） | 合并（读 topei 自动 claim） |
| 虚拟化 | Posted Interrupt | Guest Interrupt File + IOMMU |
| 中断重映射 | IRTE（专用格式） | MSI PTE（复用页表格式） |
| 地址空间 | 固定 MMIO 地址 | CSR + 可配置 MMIO |

**x86 术语说明（供 RISC-V 开发者参考）：**
- **Local APIC**：x86 每个核心本地的中断控制器，功能类似 RISC-V 的 IMSIC + CLINT
- **IO APIC**：x86 的外部中断控制器，接收有线中断并转发到 Local APIC，功能类似 APLIC
- **TPR (Task Priority Register)**：x86 的中断优先级阈值寄存器，功能类似 IMSIC 的 eithreshold
- **EOI (End Of Interrupt)**：x86 中断完成信号，需要 CPU 显式写入 EOI 寄存器。RISC-V AIA 的 topei 读取时自动 claim，无需单独 EOI
- **Posted Interrupt**：x86 的虚拟化中断技术，将中断信息写入内存，VM 换入时自动注入，功能类似 MRIF
- **IRTE (Interrupt Remapping Table Entry)**：x86 IOMMU 的中断重映射表项格式，RISC-V 使用 MSI PTE 替代
